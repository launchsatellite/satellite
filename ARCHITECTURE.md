# Architecture

How Satellite is put together and where its security boundary runs. `SATELLITE.md` owns what the product does and `DESIGN.md` owns how it looks.

## Parts

| Part | Folder | What it does |
| --- | --- | --- |
| Background process | `src/main/` | Electron's main process. Full access to the machine. Owns the window, the `app://` protocol, the hardening, the bridge handlers, the state files, the project list, the workspaces and the platform module. |
| Preload | `src/preload/` | Runs in the sandboxed preload and exposes `window.satellite`, the only door between the interface and the background process. |
| Interface | `src/renderer/` | React and Tailwind in a sandboxed renderer with no Node. It draws the three columns and nothing else touches the machine. |
| Shared | `src/shared/` | Code both sides import, such as the bridge contract and the content security policy. |

electron-vite builds all three into `out/`. Electron starts `out/main/main.js`.

## Security boundary

The interface is treated as untrusted. Whatever it shows can never run a command or read a file.

- **Renderer settings.** `sandbox`, `contextIsolation` and `webSecurity` are on, `nodeIntegration` and `spellcheck` are off. The preload is CommonJS with its dependencies bundled, because a sandboxed preload cannot load ESM or `node_modules`.
- **Permissions.** Every permission request, permission check, device request and display media request on the default session is denied.
- **Navigation.** Every web contents refuses `will-navigate`, `will-frame-navigate` and `will-attach-webview`, and its window open handler denies every new window. The one exception is a main frame reload of the window's own entry, allowed only when the target's protocol, host and path equal the entry URL, so hot reload in development and a reload in production work while every other address stays refused.
- **Content security policy.** `default-src 'none'`, with scripts, styles, images, fonts, connections and workers only from the app itself, images and fonts also from `data:`, and `base-uri`, `form-action`, `frame-ancestors` and `object-src` all `'none'`. Styles allow `'unsafe-inline'` because the terminal and the diff editor insert style elements at run time. In development only, scripts allow `'unsafe-inline'` for the React refresh preamble and connections allow `ws://localhost:*` for hot reload. `src/shared/content-security-policy.ts` builds both, so the dev server and the protocol never drift.
- **The `app://` protocol.** The interface loads from `app://satellite/index.html`, a standard and secure scheme, never from `file://`. The handler answers only `GET` for host `satellite`, decodes the path and confines it to `out/renderer` with `resolveInside`, which follows symlinks before it checks. It serves regular files only, so a folder is never handed to the file loader. Anything refused gets a 404. Every response, the 404 included, carries the production policy and `X-Content-Type-Options: nosniff`.
- **Development server.** `ELECTRON_RENDERER_URL` points the window at the dev server only when the app is not packaged, so an environment variable can never aim a packaged app at remote content.
- **Satellite home.** All state lives in the Satellite home, `~/.satellite` or the path in `SATELLITE_HOME`, which must be fully qualified, with a drive letter or a share on Windows. It is created before the app is ready and set to mode `0700` on every start on macOS and Linux, so an older, looser folder is tightened. Electron's `userData` is `app-data` inside it, so caches and storage never land anywhere else.
- **State files.** Satellite's own state lives in three JSON files in the Satellite home, never in a repository, beside one settings file per running Claude Code session (State and Sessions below).
- **Repositories.** Satellite never writes a repository's working files. Making a workspace writes into the repository's `.git`, a branch, a worktree record and what a fetch brings, and archiving removes that worktree record, while the worktree folders themselves live in the Satellite home (Workspaces below). Every git run on a workspace goes through one helper, and runs with prompts, optional locks, fsmonitor, automatic maintenance, the `ext::` transport and submodule recursion off. Listing, inspecting and archiving start no program a repository names apart from a clean filter its config can give `git status`, while making a workspace runs the repository's own hooks, filters and transport programs by design, exactly as the same commands in the user's terminal would.
- **Menu.** A minimal menu built from roles only, with no links. The app menu on macOS (about, hide, quit), Edit (undo, redo, cut, copy, paste, select all) and Window (minimize, close). View with reload and developer tools exists only when the app is not packaged. The Edit roles are what make copy and paste work on macOS.
- **One instance per home.** The app takes Electron's single-instance lock, which Electron scopes to the `userData` folder, so to the Satellite home. A second launch on the same home quits at once and the first window comes to the front. Launches with their own `SATELLITE_HOME`, like every verify run, never collide.
- **Failed start.** If the Satellite home cannot be prepared, the window cannot be created or its entry cannot load, the background process logs one sentence and exits with code 1, so no process lingers without a window.

## Bridge

The preload exposes three functions on `window.satellite` and nothing else. `invoke(channel, payload)` sends one request over the IPC channel `satellite:bridge` and `onEvent(listener)` receives pushes from `satellite:event`. `src/shared/bridge-contract.ts` holds a zod schema for every request, answer and event.

`pathForFile(file)` answers the path of a file the user handed the page, by a drop on the window or any other way a page receives a file from disk, through Electron's `webUtils.getPathForFile`, which only a preload can call. It answers an empty string for anything that is not a `File` and on any error, and Electron itself answers an empty string for a `File` made in JavaScript, so a page learns no path the user did not hand it. It sends nothing anywhere. It answers the full path, which Electron's docs advise against where it can be avoided. Here the path has to reach the background process to add a project, and the page is Satellite's own interface, which loads no remote content of any kind, so no outside script ever reads it. The path is still untrusted and goes through `projects.drop` like any other request.

- **Sender check.** The background process answers only its own window's main frame, and only while that frame shows the app origin, `app://satellite` or the dev server in development, with no user info in the URL. Anything else, including a frame that is already gone, gets `refused-sender`.
- **Validation first.** Channels are looked up in a `Map`, so names like `__proto__` or `constructor` find nothing. Every payload is parsed with its strict schema before the handler runs, so a wrong type, a missing field or an extra key is refused with `invalid-request`.
- **Errors.** A handler throws `BridgeFailure` for outcomes the user sees, with a code from the contract and a sentence written for people. `not-found` names something the page does not own or that is gone, `tool-missing` a tool Satellite cannot find, `limit` a cap that is reached, 16 terminals across every workspace, 200 projects or 20 workspaces in a project, `refused` a request Satellite turns down on purpose, such as a folder that is not a repository, and `failed` anything that went wrong. Any other error is logged in the background process and answered as `failed` with no stack.
- **Trust nothing back.** The interface parses every answer and every event with the same contract, so it never acts on a shape it did not expect. One that fails is dropped and logged to the console with its channel or event name and the failing fields, never its payload, so the journeys catch contract drift. Error messages are at most 1000 characters.
- **Lifetime.** Each page load is one bridge owner. When the window is destroyed, its renderer dies or a new document commits in its main frame, the owner ends. Its cleanups run, a cleanup added later runs at once, its events are dropped, and the next page load gets a new owner. A navigation the hardening refuses never commits, so the page and everything it started keep running. A request the old page sends while a reload is still loading lands on the old owner, so nothing a page started outlives it, apart from a workspace creation or archive, which runs to its end so it never stops half made.

## State

The background process owns all state, in three JSON files in the Satellite home. None of it is ever written into a repository. `src/main/state/json-file.ts` reads and writes them.

| File | Holds |
| --- | --- |
| `projects.json` | `{ "version": 2, "projects": [{ "id", "path", "workspaces": [{ "id", "name", "path", "branch" }] }] }`, at most 200 projects of at most 20 workspaces, each id a random UUID, each project path the absolute real path of a working tree root and each workspace path the absolute real path of its worktree, each of at most 4096 characters, the name a workspace name and the branch the one it was made on, of 1 to 255 characters. Project ids and paths are unique, workspace ids are unique across the file and workspace paths too. A project's name is its folder's base name and is never stored. A version 1 file reads as version 2 with no workspaces and is written as version 2 on the next change |
| `interface.json` | `{ "version": 1, "selected", "columns": { "left", "right" }, "theme" }`, the selected workspace as a project id and `main` or a workspace id, or `null`, the column widths as bounded integers and the theme as `system`, `light` or `dark` |
| `sessions.json` | `{ "version": 1, "last": [{ "projectId", "workspace", "sessionId" }] }`, the last Claude Code session id of each workspace that took a prompt, ids only, at most 4200 entries, one per project and workspace pair, the oldest dropped beyond that. Changes run one at a time in order. A file that cannot be read is set aside like the others and only logged, since all it loses is resume offers |

- **Strict schemas.** Each file is read once through a strict zod schema whose `version` is a literal, the one integer a change of shape raises. `projects.json` reads versions 1 and 2 and `interface.json` version 1. Only a regular file of at most 32 MiB is read, and a write that would be larger is refused, so every file Satellite writes reads back. A `projects.json` that records one folder twice keeps the first record and drops the rest, because Satellite never writes one, while two projects on one folder still set the file aside.
- **Set aside, the newest five kept.** A file that fails to parse or match its schema, an unknown version included, or that is not a regular file of at most 32 MiB is renamed to `<name>.unreadable-<milliseconds>.json` beside it, only the newest five of those are kept, and the app starts from defaults and says so once in a toast. When that rename fails after its retries, or the file cannot be opened at all, it stays exactly as it is, the app starts from defaults, says so once, and writes nothing to that file for the rest of the run, so an unreadable file is never overwritten.
- **Atomic and serialised writes.** A write goes to `.<file>.<uuid>.tmp` in the same folder with mode `0600`, is synced, then renamed over the file, retried on `EPERM`, `EACCES` and `EBUSY`. Each file has one write in flight and at most one waiting, a newer value replaces the waiting one, and a failed write never stops the next. Quitting waits for the waiting writes inside the same bound as the terminals. Leftover temp files are deleted on the first read.
- **Theme before paint.** `interface.json` is read before the window opens, so the saved theme is applied before the first paint (Look below).

## Projects

A project is a folder the user added that git calls the root of a main working tree. `src/main/projects/repository-check.ts` decides it, the same way for the dialog and a drop.

- **Accepted.** An absolute path whose real path, symlinks followed, is a folder outside the Satellite home and is the toplevel of a non-bare repository's main working tree. It is stored by that real toplevel, so one repository reached by two spellings, a symlink or another letter case on macOS and Windows is added once.
- **Refused, with a sentence.** A relative path, a path that does not exist, a file, a folder inside the Satellite home, a plain folder, a bare repository, a folder inside `.git`, a linked worktree, a subfolder of a repository, a repository git distrusts because another user owns it, a git older than 2.31 and a git run that fails. A missing `git` answers `tool-missing`.
- **Reads.** Adding a project runs `git -C <folder> rev-parse` with fixed flags through `runTool`. Listing runs `git worktree list --porcelain -z`, or without `-z` on a git older than 2.36, `git for-each-ref` with the tracking format on the workspaces' branches, `git remote` and `git rev-list --count refs/heads/<branch> --not --remotes --` for a branch without an upstream, and `git status --porcelain=v1 -z --untracked-files=all --ignore-submodules=all --no-renames` in the main folder and each workspace, plus `git branch --show-current` when the worktree list fails. Every git command on a workspace, these and the ones below, goes through `src/main/workspaces/git-command.ts`, whose `gitArgs` puts `--no-optional-locks`, `-C <folder>`, `-c core.fsmonitor=`, `-c core.askPass=`, `-c credential.interactive=false`, `-c gc.auto=0`, `-c maintenance.auto=false`, `-c protocol.ext.allow=never` and `-c submodule.recurse=false` before its arguments and refuses a folder that is not fully qualified, and whose `runGit` runs it with its time limit, 5 seconds for every read. git's own security guidance says running any git command in a repository from an untrusted source is not safe, and `safe.directory` does not help for a repository the user owns. Satellite's safety rests on the commands chosen. No listing read touches a pager or a transport or runs a hook, and the optional index write and the fsmonitor hook are off, so a list writes nothing. `git status` is the one read that can start a program a repository's own config names, a clean filter driver when it rehashes a file, exactly as the same command in the user's terminal would. A repository's tracked files cannot define one, only its config can. Making a workspace adds the network, the hooks and the writes listed under Making a workspace, and archiving adds its own reads and one write, listed under Archiving. Every new git command needs its config-driven programs, such as `core.fsmonitor`, `diff.external`, textconv and filter drivers, its writes and its optional index lock reviewed and recorded here before it ships.
- **Listing.** Each list checks every folder with `stat` and `<root>/.git` with `lstat`, eight projects at a time. A folder that is gone reads as missing, one without `.git` as no longer a repository, and one whose checks do not answer within 6 seconds as missing for that list. Each project has at most one read pending, covering the checks and the git reads after them, so a hung drive never piles up reads however often the window regains focus. A project whose last checks ran past 6 seconds checks its folder again only through two shared slots, so a folder that keeps hanging starts no new thread-holding read beyond those two, while projects that answered last time and new ones read at once and stay healthy. A project leaves the slots as soon as its checks answer in time. A read that hangs still holds its thread until the drive answers, so four folders hanging on their first read can fill Node's four file threads, and saving `projects.json` gives up after 10 seconds with a sentence, so one hung write never holds back later changes.
- **Removing** forgets the project in `projects.json` and leaves its folder untouched. A project with workspaces is refused while its folder answers, and forgotten with its workspace records when its folder or `.git` is gone or does not answer within 6 seconds.

## Workspaces

A workspace is a branch with its own worktree, recorded under its project in `projects.json`. The main workspace is the project's own folder, has the key `main` and no record, so no request can name it for archive. `src/main/workspaces/` holds all of it, from the git helper to the bridge handlers.

- **Names and folders.** A name is 1 to 48 lowercase letters and digits in groups joined by single hyphens and never a name Windows keeps for a device, `con`, `prn`, `aux`, `nul`, `com0` to `com9` or `lpt0` to `lpt9`. `src/shared/workspace-name.ts` holds the rule, so both processes check it, and every name that passes is a valid branch and a valid folder on every system. The branch takes the same name. A name is also refused when a branch of that name exists, when a branch differs from it only by letter case or sits under it as `<name>/...`, which git cannot keep beside it on every system, or when its folder exists. The suggested name is two words from fixed lists that clash with nothing, with a number added when twenty random pairs are all taken. The folder is `<home>/worktrees/<project>/<name>`, where `<project>` is the project folder's base name with every character outside `A-Z`, `a-z`, `0-9`, `.`, `_` and `-` turned into `-`, cut to 48 characters, `project` when nothing is left and suffixed `-project` when it is a device name, so two projects of one folder name share that folder. Satellite makes `worktrees` and `<project>` with mode `0o700` and one `mkdir` each, never a recursive one, and refuses to go on unless each is a plain folder and the project folder's real path equals the Satellite home's real path joined with `worktrees/<project>`. On Windows a worktree path over 150 characters is refused, so the checkout keeps room under the path limit. Anything Satellite later reads from or deletes as a workspace folder must be its own real path, with no link at any level, whose grandparent is the real `<home>/worktrees`.
- **What it writes into a repository.** Making a workspace writes `refs/heads/<name>` with `git branch`, and `.git/worktrees/<id>/` plus the new folder's `.git` file with `git worktree add`. The default start also fetches one branch, which updates `refs/remotes/<remote>/<branch>` and the object store. Archive's `git worktree remove` deletes `.git/worktrees/<id>/`. A failed creation deletes its branch and worktree again, while the fetched objects and ref stay, as after any fetch. Satellite writes nothing else into a repository, never its working files, and never runs `git worktree prune`, `repair`, `lock` or `move`, so a user's own worktree on a drive that is not mounted keeps its record.
- **Older git.** Satellite needs git 2.31 to add a project. `git worktree list -z` arrived in 2.36, so Satellite asks for it, and when git answers that the switch is unknown it reads the list with newlines for the rest of the run. In that output a path holding a newline can forge a line, so on a git older than 2.36 nothing is dropped or adopted and archive is refused with a sentence asking to update git. Making a workspace still works there.
- **Workspaces in a list.** After its checks pass, a project reads its worktree list, then the tracking counts and one `git status` per workspace, at most 21, then for the branches without an upstream `git remote` and one `git rev-list` each. A branch with an upstream shows how far it is ahead of and behind it. A branch without one shows as ahead the commits that are on no remote and no behind, and in a repository with no remote it shows no count. The tracking, remote, count and status reads share eight slots across all projects, so at most eight of them run at once beside the worktree lists of the eight projects reading. A project's git reads answer within 15 seconds or the list shows that project's workspaces without branch or counts and keeps every record. The read keeps running and the next list waits on it instead of starting another, so a project has at most one read in flight. A late project can still be running its worktree list, which is two runs once per app on a git older than 2.36, or its branch read when the next batch starts, so the git processes in flight can briefly exceed sixteen, each bounded by its 5 second limit. A git that cannot be ended fences its folder, so it is never started there twice. With every git hanging to its limit a list answers in at most 21 seconds per batch of eight projects, 25 batches for 200 projects.
- **Dropping.** Each list compares the records with `git worktree list`. A record whose worktree is listed shows its branch and counts. Any other record is dropped only when its folder is gone and the Satellite home still answers as a folder, whether git lists it as prunable or not at all. Every workspace folder lives in the home's worktrees folder, on the home's own volume, and the home holds the state file just read, so a missing folder below it, the whole worktrees folder included, means deleted, not unmounted. A record outside it, which only a hand-edited file holds, needs the folder holding it to answer instead. A record whose folder is still there is never forgotten, even when git leaves it out or prints its path in another spelling, and its row shows its name with no branch and no counts, because that is all Satellite could read. A separate volume mounted inside the worktrees folder and then unmounted loses its records. The sentence says the folder was deleted outside Satellite when git still lists it as prunable, and that the worktree was removed otherwise, naming the folder that now holds its branch, if any. Several drops in one project become one sentence with their count and names. Nothing is dropped when the worktree list fails or times out, when git is older than 2.36 and the list had to be read without NUL separators, because a path holding a newline can forge lines there, while a workspace is being archived, or while `projects.json` cannot be written. Dropping removes only the record from `projects.json`, never a folder, a branch or anything in `.git`, and a failed save keeps every record in the list and says nothing. The folder checks of a record git does not list are not slotted, so a record folder on a hung drive holds one file thread per project, and the project's one pending read keeps it at one.
- **Adopting.** Each list also looks for worktrees git lists inside this project's own folder in the worktrees folder that have no record, with a branch, a folder name that passes the workspace name rule and a folder that passes the same plain folder rule creation uses, and adds a record for each, named after its folder, so a creation cut short or a worktree made there by hand shows up and can be archived. A record whose stored path reaches the same folder by a link or in another letter case counts as that folder's record. Nothing is adopted while a workspace of that project is being made or archived, when the worktree list fails or had to be read without NUL separators, beyond the 20 workspace limit, or while `projects.json` cannot be written. The save checks again against the latest records, so a creation that finishes in the meantime keeps its own record and no folder is recorded twice. Adopting writes only `projects.json`.
- **Making a workspace** runs five steps, the start, the branch, the worktree, the files and the record, reports each over `workspaces.step` and, when one fails, undoes every started step newest first, the failed one included. The branch comes before the worktree because `git worktree add -b` leaves its new branch behind when it fails, so each is made and undone on its own. The start step resolves a commit id once. A chosen ref is read with `show-ref --verify`. The default start uses `origin` or the only remote, its default branch from `symbolic-ref` or else `ls-remote` within 10 seconds, and fetches that one branch straight into `refs/remotes/<remote>/<branch>` within 15 seconds with no tags, no submodules and no automatic maintenance, so a remote with its own fetch refspec still starts from what was just fetched. A failed fetch starts from the copy fetched last and says so, pointing to a credential helper or an ssh agent when git could not sign in, since Satellite's git never prompts and drops `GIT_ASKPASS`. With no copy it stops with a sentence. With no remote it starts from the main folder's commit and says so, and an empty repository is refused. The branch step makes the branch with `git branch --no-track` from that commit, and its undo deletes it only with `update-ref -d` against the same commit, so a branch that existed before or moved since is never deleted. It is also kept when the worktree could not be removed, so the leftover worktree still has its branch. The worktree step refuses a folder git still lists from a worktree deleted by hand and points to `git worktree prune`, makes the folder itself with mode `0o700`, refusing one that already exists, remembers its device and inode, and runs `git worktree add` within 5 minutes. The repository's checkout hook runs, and a failing hook fails the step. The new folder must then be listed by git and still be the plain folder Satellite made. Its undo goes through the same removal as archive (Archiving below). When git lists the folder, it first walks it, stops at a folder on another drive or a walk that did not see the whole folder, and removes every link, then runs `git worktree remove --force`, forced twice when the worktree this run made is locked, and deletes the folder only while it is still that same folder, by 64-bit device and inode, inside the worktrees folder. A folder git does not list, from a `git worktree add` that failed before registering it, goes straight to Node's `fs.rm`, which never follows a link or junction. When the walk stops or a link cannot be removed, nothing is handed to git, the worktree and its branch stay, and the sentence names the folder in the Satellite home and what held it. The next list adopts that worktree. The files step reads `.worktreeinclude` only as a regular file of at most 64 KiB opened without following a link, lists the ignored files within 30 seconds and collects and copies within 2 minutes, a hung read included, checking the worktree folder again first. Quitting, or the user's Cancel through `workspaces.cancel`, stops a running creation, ends its git and undoes what it made, and the quit waits up to 20 seconds for that. An undo that takes longer, such as removing a very large checkout, is cut off at that point and leaves what a crash leaves. A crash of the whole app can leave a branch and a worktree with no record. The next list adopts the worktree (Adopting above), so the user sees it and can archive it. A branch left with no worktree stays, and a new workspace of that name is refused with the sentence that says a branch of that name exists.
- **Copying ignored files.** The files step matches the ignored list against `.worktreeinclude` with Satellite's own matcher. It keeps at most 1000 patterns of at most 4096 characters and 64 segments, and checks a path and every folder above it against every pattern in one pass. The copy visits at most 100000 entries and keeps at most 10000 files and 1 GiB. Collecting and copying share the step's 2 minute deadline and stop when the app quits. Names holding `..`, `.`, an empty part, a backslash or NUL are skipped, and on Windows so are names with a `:`, a trailing dot or space, or a device name. Links, pipes and devices are skipped and never followed. A source is read only when every folder above it is a plain folder by `lstat`. It opens without following a link, without blocking and without becoming a terminal. After the open its 64-bit device and inode must match the earlier check, its real path must still be inside the repository's real path, and that path must still name the same file. A destination folder is made one level at a time and must be a plain folder. The file opens with exclusive create, so a file the checkout made is never overwritten and nothing is written through a link. A folder Satellite may not read is skipped while collecting. A file that cannot be read or that shrinks while copying fails the step, which undoes the worktree.
- **What the copy cannot rule out.** Node opens by path, so a process that can write in the main folder, such as an agent sandboxed to it, could swap a folder above a matched file for a link and time it to the instant. If it swaps in before the check, out before the real path is read and in again before the last identity check, a file it cannot read itself is copied into the new worktree. Each single swap is caught, so it takes three exactly timed swaps during one file's copy. A hard link in the main folder is a regular file and is copied, whatever it links to. Agents in a checkout cannot write under the Satellite home, so the same window at the destination, and between choosing the folder and `git worktree add`, is accepted. Exclusive create may not hold on an older network file system, so a Satellite home on one loses the never-overwrite rule.
- **Where matching differs from git**, it copies fewer files, or more only among files that are already ignored inside the repository. Character classes like `[[:digit:]]` read as plain sets of characters. `?` and a class take one character where git takes one byte, so `?.txt` also matches a name like `é.txt`. Case always counts, and names are compared without Unicode normalisation, so a composed and a decomposed spelling never match. An unclosed `[` and a lone trailing backslash match nothing.
- **What a hook inherits.** The repository's hooks and filters run with the environment Satellite gives git, which is the user's login shell environment without the `ELECTRON_` variables and the variables that point git at another repository, without `GIT_ASKPASS` and `SSH_ASKPASS`, and with `LC_ALL=C`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=false` and `SSH_ASKPASS_REQUIRE=never`, plus the `SATELLITE_` verification variables when a verification run sets them, which hold paths and JSON and never a secret. git adds `GIT_CONFIG_PARAMETERS` with Satellite's `-c` values and `GIT_OPTIONAL_LOCKS=0`, so a git command the hook runs also has no askpass, no interactive credential helper, no automatic maintenance, no fsmonitor, no `ext::` transport and no submodule recursion unless it asks. Satellite holds no credential, so a hook gets nothing the user's terminal does not already have. It runs with no terminal and its input closed. On macOS and Linux it sits in git's own process group, which ends at the time limit or on quit, and on Windows git's process tree is ended by its id.
- **Inspecting.** Before archive the dialog asks what would be lost. git lists the worktree from the project's main folder, never from the worktree, whose `.git` file a process inside could point elsewhere, and it must be one of that project's linked worktrees, not bare and not prunable. Then, in the worktree, `git status` gives the uncommitted files, `ls-files -z -v -s` the files git skips with assume-unchanged or skip-worktree and the submodule entries, `rev-parse --git-path modules` where git keeps submodule history, and `rev-list` with `log --no-show-signature` the commits on no remote, or on a detached head on no branch, remote or tag. The answer carries a fingerprint, a SHA-256 over the folder's device and inode, HEAD, the raw status, everything shown and the count of Satellite's terminals there, so the user confirms exactly what they saw. Anything Satellite cannot read or count is shown as a loss it cannot rule out, with the danger button.
- **Archiving** inspects again and refuses unless the fingerprint matches, refuses a locked worktree and one with submodules checked out or not checkable, stops Satellite's terminals in the folder, then inspects once more and refuses on any change. The dialog shows the lock and the submodules first and offers no confirm for them. Removal follows git's own rules for `git worktree remove`. It removes only clean worktrees with no submodules, and `--force` once removes an unclean one, or one with submodules, while a locked one needs `--force` twice. git's removal walks the folder with its own `lstat`, which on Windows reports an NTFS junction as a folder, so git could walk into a junction and empty the folder it points to, such as a checkout that `npm link` joined into `node_modules`. So Satellite never trusts git's removal across a link on any system. After the last inspection, Satellite walks the worktree itself without following any link, with `opendir` and `lstat`, and on Windows it also counts a folder whose real path differs from its own as a link. A folder whose device differs from the worktree's is another file system mounted there, such as a network or FUSE mount, and the walk stops at it, so archive is refused before anything is removed, with a sentence that names it. The inspection walks the same way and names that folder, or says why it could not see the whole folder, and the dialog offers no confirm for either. It removes each link it found with `unlink`, falling back to `rmdir`, which removes a junction itself, never what it points to. A link it cannot remove stops the archive before git runs and names the link. Archive and the creation undo share this one removal in `worktree-removal.ts`. A folder it cannot read is passed over and the walk goes on, so every mount it can reach is still found. The walk is bounded at 1000000 entries, 256 folders deep and 60 seconds, and a walk still running at 60 seconds, such as one stuck on a mount whose server stopped answering, is abandoned at that point. On every system, a walk that did not see the whole folder, because a folder was unreadable, a bound was reached or a folder did not answer, refuses the removal before git runs, with a sentence that says why and what to do. On macOS and Linux `lstat` reports every link as a link, so git and Node's `fs.rm` would not follow one anyway, but only the whole walk rules out a mount. Node's documentation says `lstat` describes a link itself and `unlink` removes a link without touching its target, and it says nothing about junctions. The unit tests and the `workspaces` journey prove a junction on Windows and a symbolic link elsewhere, on all three systems. Satellite then runs `git worktree remove` without `--force`, which removes a clean worktree, ignored files included. Only when git answers that the worktree holds modified or untracked files does it run once more with `--force`, never twice. Satellite never forces a worktree with submodules checked out, because `--force` would delete a submodule's own history in `.git/worktrees/<id>/modules` with it, and git still refuses submodules itself on the first run. git deletes the folder, then forgets the worktree even when some files could not be deleted, such as files another process holds open on Windows. Satellite then deletes what is left with Node's `fs.rm`, three tries 200 milliseconds apart, and only while the folder is still the plain folder it inspected, by device and inode, inside `<home>/worktrees/<project>`. A folder that still holds files is named to the user and its record is forgotten, because git no longer knows it. When git still lists the worktree afterwards the record stays, and the sentence says the folder is as it was only when nothing was forced and no link removed. When git runs past 2 minutes, the sentence says some files may be gone and the record stays for the next list to judge. Quitting waits up to 20 seconds for a running archive. The one write is `worktree remove`, whose clean check runs `git status --ignore-submodules=none`, so a repository's own clean filter can run there, as in the user's terminal.
- **What archive cannot rule out.** The fingerprint covers the folder's identity, HEAD, the branch, the lock, `git status`, the counts and the terminals, so it catches a new file, a new commit or a new terminal. It does not catch further edits to a file the dialog already listed, which the user has agreed to lose, or edits to files git skips with assume-unchanged or skip-worktree, which the dialog counts and names as lost. A process with the user's rights that writes in the worktree between the last inspection and git's removal loses that write unseen, and one that swaps the worktree folder or a folder inside it for a link after the walk and before git opens it gets git to walk into the link. Both windows are a few milliseconds, and only something already running as the user can use them. A mount made after the inspection is caught by the walk, after Satellite's terminals there have stopped. A bind mount of a folder from the same file system has the same device, so the walk cannot tell it from a plain folder, and on Windows a mounted volume is a junction and is removed as a link.

## Look

The theme is Electron's `nativeTheme.themeSource`, set to the saved choice at start and on every `interface.save`. With `light` or `dark` it overrides the system, and `system` follows it. Chromium then answers `prefers-color-scheme` with the choice in the window, so the CSS tokens, the terminal and the diff switch with no extra signal, and the native folder dialog and menus follow too. The window's background colour at creation reads `nativeTheme.shouldUseDarkColors`, so the window opens in the colour of the chosen theme.

## Platform

`src/main/platform/` is the only code that knows about executables, shells and platform differences.

- **File system rules.** `file-system.ts` holds the file name rule for copied files, which on Windows refuses a `:`, a trailing dot or space and device names, the 150 character limit on a workspace folder on Windows, and on Windows a folder whose real path differs from its own counting as a link, plus the error code, folder identity and open flag helpers the features share.

- **Overrides.** `SATELLITE_GH` and `SATELLITE_CLAUDE` hold a JSON array of strings, the executable then its leading arguments, and replace the search for that tool. Anything else is logged with a sentence that names the variable, and the tool reads as missing, as does an override whose fully qualified executable is not a file. `git` has no override.
- **Login shell environment.** An app started from the Dock, Finder or a desktop menu inherits a minimal `PATH`. On macOS and Linux Satellite runs the user's login shell once in the home folder, so no project's shell hooks run, interactive with a 5 second limit, reads its environment between two markers and merges it over its own. Whenever both markers come back the block is used, even if the shell exits with an error. Otherwise Satellite falls back to the app's own environment. Windows uses the app's environment as it is.
- **Search.** Tools are found by walking `PATH` and skipping empty and relative entries, so the current folder is never searched. A match must be a regular file, and executable on macOS and Linux. On Windows surrounding quotes are stripped, an entry needs a drive letter or a network share, and only `.exe` and `.com` files count, because batch files need a shell that re-parses arguments.
- **Running.** Tools run with an argument array and no shell, a 16 MiB output limit and the user's environment without any `ELECTRON_` variable or the variables an AppImage and Electron add on Linux, with the desktop name Electron rewrote put back. Past its time limit, 30 seconds unless the caller asks for less, its whole process tree ends. On macOS and Linux each tool starts in its own process group, which gets `SIGHUP` and two seconds later `SIGKILL` for anything still running. On Windows the tree is ended at once. `git` also runs without `GIT_DIR`, `GIT_WORK_TREE` and the other variables git lists in `git rev-parse --local-env-vars`, so a variable from the login shell never points a read at another repository, and with `LC_ALL=C` and no `LANGUAGE`, so its messages read the same in every locale. It never waits on a prompt of its own. `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=false` and `SSH_ASKPASS_REQUIRE=never` are set and `GIT_ASKPASS` and `SSH_ASKPASS` are dropped, so a sign-in a credential helper already stores keeps working and anything that would prompt fails or ends at the time limit instead. Two waits remain possible, both ended by the time limit. On Windows, where a tool gets no session of its own, ssh can wait on the hidden console, and on macOS a credential helper can make the system show its own keychain dialog, which belongs to the system rather than to git. Satellite needs git 2.31 or newer for `rev-parse --path-format`, and an older git gets a sentence asking to update it. A run that cannot be ended, such as one stuck on a dead network drive, still answers as timed out within five seconds of its limit. For git Satellite then starts no other run in that folder until the stuck one exits, and every read there answers as failed at once. Errors name the tool or the override variable, never its arguments.
- **Folder dialog.** `folder-dialog.ts` opens the native folder dialog as a sheet on the window. When `SATELLITE_VERIFY_FOLDER_DIALOG` holds an absolute path, the dialog never opens and that file's trimmed content is the answer, a missing or empty file meaning canceled. Verification sets it on every launch. A packaged app reads it too, so the journeys can prove a release, and it grants nothing new. Whoever sets a variable for Satellite can already set `SATELLITE_CLAUDE` to any program, and the answered folder still meets the full repository check.
- **Quiet verification.** `src/main/window/verification.ts` reads the same variable together with `SATELLITE_VERIFY_DRIVER_PID`, the process id of the driver that launched the app. Only when both are set and that process is alive at start does the app run quietly on macOS. It then takes the `accessory` activation policy before any window exists, so it gets no Dock icon or menu bar and never comes to the front, and the window is never shown. It still renders, because `paintWhenInitiallyHidden` keeps the page painting and `backgroundThrottling` is off for that window, and the driver turns on the protocol's focus emulation, so focus, keys, screenshots, drops and resizes behave as in a focused window. `SATELLITE_VERIFY_FOREGROUND=1` shows the window as a normal app for a person who wants to watch, and the release workflow sets it on macOS and Windows so a packaged app is proven as users see it. Windows and Linux always show the window. The app also starts quitting within a second once that driver process is gone, so a driver that dies, even by `SIGKILL`, never leaves an app running. A leftover variable with no live driver behind it changes nothing, so a user's own Satellite is never hidden, and a normal launch sets neither variable.
- **Install commands.** `installCommand(tool)` in `install-commands.ts` answers the fixed step the first run check shows for a missing tool on this platform, a command, or on Linux for `git` and `gh` the address of each project's official install instructions, because no one package command is right on every distribution.

## Terminal

The right column runs the real Claude Code in a terminal Satellite owns. The background process holds the pseudo terminal and the interface draws it with xterm.js.

- **Ownership.** The interface picks a fresh UUID each time it mounts a terminal, so a remount never reuses one, subscribes to its events, and only then asks to start it, so no early output is lost. A terminal belongs to the page load that started it. Write, resize and close from any other page answer `not-found`, and a duplicate id is refused.
- **Cleanup.** When the owner ends, through a reload, a crash or a closed window, its terminals are killed, even one still starting. On macOS and Linux a kill lists processes once with `ps`, taken from `/bin` or `/usr/bin` and never searched in `PATH`, then sends `SIGHUP` to the terminal's process group and to every descendant. When the terminal has exited and nothing from that list is left, the kill is done. Otherwise, two seconds after it began, everything from the list that still runs, and anything those processes started since, gets `SIGKILL`. A process is matched by its pid and start time, so a reused pid is never signalled. On Windows `taskkill /T /F` ends the tree, then the kill waits up to two seconds for the pseudo terminal to report the exit. Only when it never does is node-pty's own kill called, because that kill starts a helper with `fork`, which the packaged app's run-as-Node fuse turns into a second Satellite. The single-instance lock makes such a launch quit at once. node-pty's spawn, write, resize, pause and resume never fork.
- **Workspaces.** Each terminal remembers its workspace and the folder it started in. Archiving counts and stops the terminals that started inside the workspace's folder, through two methods, `countInside` and `stopInside`, which wait until each process tree has ended and its settings file is gone. A terminal still starting there is stopped before it spawns. Removing a project stops the terminals in its folder and in the folders of the workspace records it forgets, so a project nested inside another project's folder loses its terminals too when the outer one is removed.
- **Quit.** Quitting refuses new terminals and waits until every terminal has been killed this way and cleaned up, then saves `sessions.json` and exits. The wait is bounded by the kill's own worst case, the two second grace plus two process listings of at most a second each, plus half a second. So Claude Code, its tools and anything that ignores `SIGHUP` end with Satellite. A process that fully detaches before the kill, by leaving the process group and losing its parent to the system, is out of reach and survives.
- **Limits.** 16 terminals at once, a terminal still being killed included. Input is split into writes of at most 65536 characters and sent through one queue per terminal, so a large paste arrives whole and in order. Scrollback keeps 5000 lines.
- **Output flow.** The background process gathers output for 8 milliseconds and sends it in events of at most 65536 characters. The interface acknowledges each event once xterm.js has processed it. With more than 256 KiB of output unacknowledged the pseudo terminal is paused, and it resumes once that falls to 32 KiB, so a flood of output never piles up in memory. A terminal that ends is resumed first, so a page that is gone never holds a process paused.
- **Failures.** A failed start or an ended session shows one sentence in a status region, so screen readers announce it, and a button that starts a fresh terminal. Focus moves to that button, because xterm.js takes Tab as input and would otherwise hold the keyboard. A spawn failure says that Claude Code couldn't start and nothing in the project changed.
- **Links.** A click on a link in terminal output does nothing, so output can never open a dialog, a window or the browser.
- **Environment.** Claude Code starts in its workspace's folder with the user's environment plus `TERM=xterm-256color` and `COLORTERM=truecolor`. It drops what names whatever started Satellite, Claude Code's own markers for its children, the IDE port and entry point, the terminal program, tmux, screen and every `VSCODE_` variable, matched without regard to case on Windows. `GIT_ASKPASS` goes with them only when it sits in the same folder as `VSCODE_GIT_ASKPASS_MAIN`, because that helper cannot reach its editor once the editor's variables are gone, while an askpass of the user's own stays.
- **DOM renderer.** xterm.js draws with its default DOM renderer. A GPU renderer would need another dependency, and Claude Code's own terminal guidance turns GPU acceleration off in embedded terminals because it garbles text.
- **Terminal font.** The DOM renderer draws block and box characters from the font, and Geist Mono's block glyphs are shorter than its line box, which leaves seams between rows in Claude Code's logo. The terminal uses Geist Mono under its own family name with ascent and descent overrides that match the block glyphs, so blocks join with no gap and lines sit tight. A taller line height was rejected because it brings the seams back.
- **Unicode 11.** The unicode11 addon is active, so emoji and wide characters take the same cell widths Claude Code expects. The graphemes addon was rejected because it is experimental.
- **Shift+Enter.** xterm.js has no extended keyboard protocol, so Shift+Enter with no other modifier sends ESC then CR, the sequence Claude Code reads as a new line, and the key's own events are swallowed.
- **The spawn helper.** node-pty ships its macOS `spawn-helper` without the executable bit, which fails every spawn with `posix_spawnp failed`. The postinstall step restores the bit. `npm rebuild node-pty` does not, and the node-pty beta that fixes it was rejected because it is a beta. node-pty stays out of the bundle because it is a runtime dependency, and `src/main/platform/pty.ts` is the only file that imports it.

## Sessions

Each terminal is one launch of the user's own `claude` in a workspace. `src/main/terminal/terminal-sessions.ts` runs a launch and `src/main/sessions/` holds its parts.

- **The folder.** The page names a workspace, never a folder. At start the background process looks the project up in `projects.json` and takes its path for `main` or the workspace record's path otherwise. A workspace being archived is refused, the folder must answer as a folder within 6 seconds, and a workspace's folder must also pass the plain folder rule inside `<home>/worktrees/<project>` with no link at any level. The record is read again after those checks, so a project removed meanwhile is refused, and the terminal remembers the folder at once, so an archive or removal that begins later stops it before or after it spawns.
- **The launch.** A new session gets a UUID the background process makes and `--session-id <uuid>`. A resume reads the one id `sessions.json` holds for that workspace and gets `--resume <uuid>`, refused when there is none or a running terminal holds it, since resuming one session twice at once corrupts its transcript. Every launch gets its own launch UUID, its own 32 byte secret and `--settings <home>/sessions/<launch id>.json`. Claude Code gets the environment above and nothing from the page.
- **The settings file.** It holds only HTTP hooks for `SessionStart`, `UserPromptSubmit`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `Stop` and `StopFailure`, each posting to `http://127.0.0.1:<port>/hook/<launch id>/<event>` with the secret as a literal `Authorization: Bearer` header and a 5 second timeout. The folder has mode `0700`, the file is created exclusively with mode `0600` and never through a link, and on Windows it inherits the Satellite home's access list. The secret is never on an argument list, in an environment, a log or an event. Claude Code merges these hooks with the user's own and writes nothing to the user's settings. The file is removed when its process exits, and the first start of each run sweeps leftovers by name and kind, logging and passing over any it cannot remove.
- **The listener.** One `node:http` server on `127.0.0.1`, port `0`, started before the bridge. It answers `405` to anything but `POST`, `404` to any other path, `403` to a `Host` other than `127.0.0.1:<port>` and to any `Origin`, `401` unless the secret matches that launch in constant time, `415` to a type other than JSON and `429` past 100 events per launch per second, counted only after the secret. Every answer is `204` or a refusal with no body, no CORS header and `Connection: close`, so it never decides anything for Claude Code. It holds 64 connections, headers within 5 seconds and a request within 10. It keeps at most 64 KiB of a `SessionStart` or `Notification` body and 1 MiB of a tool event's, and drains every other body unread. From a body it reads only `session_id` as a UUID, `source` and `notification_type` of at most 64 characters and `agent_id` of 1 to 128 characters, and stores only the session id and the agents that are asking. When it cannot start, sessions run without `--settings`, stay idle and the error is logged once.
- **Status.** Each event moves the session through `idle`, `working`, `needs-you`, `done` and `stopped`. Every agent asking at once is remembered, up to 16, and needs you lasts until each has had a tool finish, the turn ends or the user prompts again. Events for a launch that has ended do nothing. A `UserPromptSubmit` records the session's current id in `sessions.json`, the id of its last `SessionStart`, so `/clear` moves the record on.
- **Every end cleans up.** A normal exit, a crash, closing the tab, archiving the workspace, removing the project, reloading or closing the page and quitting each end the process tree as the Terminal section says, then mark the session stopped, drop its secret from the listener, so its file is useless, remove its settings file and tell the page how it ended. A resumed launch that exits with a failure before any hook arrived, and that Satellite did not end, forgets its record, since `claude` could not find that session. A process that does not report its exit within a second of its tree being ended is cleaned up anyway.
- **The listener outlives every launch.** Anyone who answers on the hook port receives that launch's secret and can answer with a decision Claude Code acts on, so the listener stops only after every `claude` it configured has exited, and a process that cannot be ended keeps it running. At quit it stops after every terminal has ended. A process that escapes the kill, by leaving the process group and losing its parent, outlives Satellite, and once Satellite exits another local account could take the freed port and answer that process's hooks.
- **What a hostile local process can do.** Another account can find the port but not the secret, which sits in a `0600` file in a `0700` folder, and each guess is 256 bits. A web page cannot send the request, because the header and content type force a preflight that is refused, and DNS rebinding fails the host check. A process running as the user, the agent included, can read a settings file and post events, so it can make a status lie or set the recorded session id, and nothing else through the listener. Such a process can already do anything the user can.

## Diff

The centre column shows a read-only side by side diff of two texts with Monaco's diff editor, the component the Changes and Pull request views grow from.

- **Only the editor API.** The interface imports `monaco-editor/editor/editor.api` and its codicon styles, with no languages, so every text is plain text. The diff's gutter markers are codicons, which the bare API leaves out.
- **The worker.** The editor worker is bundled by Vite as its own file and served from `app://satellite` like every other asset, so it loads under the production policy's `worker-src 'self'` with no fallback to the main thread.
- **Read only.** Both sides are read only, the DOM included, and the revert gutter menu is off, so the diff can show changes but never make them.
- **Always side by side.** The diff stays in two columns at any width, because the editor's narrow-width inline view would hide which side a line belongs to.
- **Theme.** The `satellite` theme reads the app tokens, `bg`, `fg`, `dim`, `add` and `del` for lines, `addfg` and `delfg` at low alpha for changed words, `ctl` for scrollbars, `line` for the fill where a side has no line, `sel` for selection and `accent` for the focus border, and is rebuilt on every colour scheme change. Each token goes through a canvas to come back as six digit hex, because the built stylesheet shortens colours like `#ffffff` to `#fff` and Monaco accepts only the long form.
- **Models.** Each text becomes a model, replaced when the texts change and disposed with the editor.

## Packaging and fuses

electron-builder packages `out/` and `package.json` into `release/` from `electron-builder.yml`, with the icon from `packaging/`. macOS gets a dmg and a zip for arm64 and x64, Windows an NSIS installer for x64, Linux an AppImage and a deb for x64. The renderer is minified. Main and preload stay readable, since they are small and their stack traces land in logs.

- **Unsigned.** macOS builds are ad-hoc signed after the fuses flip, because an arm64 Mac refuses to launch a modified binary with no signature. Windows and Linux builds carry no signature.
- **ASAR.** The app ships as `app.asar`, and Electron loads it from nowhere else. Only node-pty's native files, its builds and the macOS spawn helper, are unpacked into `app.asar.unpacked`, because they must be real files, so its JavaScript stays inside the archive under integrity validation. Smart unpacking is off, so electron-builder never unpacks a whole module by itself. node-pty is N-API, so packaging never rebuilds it. On macOS and Windows it ships its own builds, and on Linux `npm ci` compiles it on the build machine, so the Linux package links against that machine's glibc and needs a distribution at least as new as the release runner's Ubuntu 24.04. Each package carries only the node-pty build for its own platform and architecture, without node-pty's sources, tests, source maps or `node-addon-api`.
- **Licences.** Vite's `build.license` lists every package bundled into the renderer, and `scripts/third-party-licenses.ts` adds the runtime dependencies that ship outside the bundle, the fonts and Monaco's own third-party notices. The file ships as `third-party-licenses.md` in the app's resources folder and beside the installers in a release. The `app://` protocol's confinement works unchanged inside the archive, because Electron's file system reads the archive's paths like folders.
- **Fuses.** Running as Node, `NODE_OPTIONS`, the Node inspector arguments and extra `file://` privileges are off. ASAR integrity validation and loading the app only from the ASAR are on. Integrity is checked on macOS and Windows, and Linux has no such check. Cookie encryption is off, because Satellite stores no cookies and loads no remote content, and turning it on gives each build a keychain item that an ad-hoc signature, new with every build, can make macOS ask about.
- **Checksums.** `node scripts/checksums.ts <folder> <label>` writes `SHA256SUMS-<label>.txt` in `sha256sum` format for every package directly in the folder.

The release workflow, `.github/workflows/release.yml`, runs the unit tests and packages on macOS, Windows and Linux at once, reads the fuses, runs the journeys against the packaged app built for each runner's own processor and writes the checksums and the licence notices beside the packages. A failing journey uploads `verify-output/`, which the release never picks up. A pushed version tag runs it and, once all three pass, drafts a GitHub release with the packages, one `SHA256SUMS.txt` and `third-party-licenses.md`. A push to a `platforms/` branch or a manual run, even on a tag, builds and proves without publishing, and a branch push is how the matrix runs before a merge, because a manual run only exists for workflows on the default branch. On Linux the journeys run under `xvfb`, with unprivileged user namespaces allowed so Chromium keeps its own sandbox on Ubuntu 24.04. A new push to the same branch cancels the run before it, while a tag run always finishes and installs without the shared npm cache. Every step runs in bash, Windows included.

## Decisions

| Chosen | Rejected | Why |
| --- | --- | --- |
| electron-vite | Plain Vite, the Vite plugin of Electron Forge | One config builds main, preload and renderer with hot reload, keeps runtime dependencies out of the main bundle and bundles the sandboxed preload as CommonJS. Plain Vite needs that setup built by hand, and the Forge plugin ties the build to Forge. |
| electron-builder | Electron Forge | It makes the dmg, zip, NSIS installer, AppImage and deb itself, flips the fuses and ad-hoc signs from one file. Forge has no first-party AppImage maker. |
| Stable node-pty with the spawn helper fix in postinstall | The node-pty beta that fixes the helper, forks of node-pty | A stable N-API release with builds for macOS and Windows that runs in Node and Electron alike, compiled at install on Linux. The beta is a beta, and a fork adds another party to trust in a native module. |
| xterm.js's DOM renderer | The WebGL renderer | No extra dependency, and Claude Code's own terminal guidance turns GPU acceleration off in embedded terminals because it garbles text. |
| The unicode11 addon | The graphemes addon | It gives the cell widths Claude Code expects, and the graphemes addon is experimental. |
| A driver over the Chrome DevTools Protocol, `--remote-debugging-port=0` | Playwright's `_electron.launch` | `_electron.launch` waits for the Node inspector, which the inspect arguments fuse turns off, so it could never drive the packaged app the release proves. |
| The `app://` protocol | `file://` | A standard, secure scheme with one handler that confines every path to `out/renderer` and sets the policy on every response. `file://` reaches the whole disk and has no real origin for the sender check. |
| The TypeScript compiler written in TypeScript | The native TypeScript compiler | Typed lint needs the JavaScript compiler API, which only the compiler written in TypeScript offers, and typescript-eslint supports only that one. |
| Terminal ids chosen by the interface, which subscribes before it starts | The background process buffering early output until the interface asks | Nothing is lost and nothing has to be held or bounded in between. |
| Output batching with `terminal.ack` and a paused pseudo terminal | Streaming output with no flow control | It is the only way to bound memory when a command floods the terminal. |
| Only `.exe` and `.com` on Windows | Running `.cmd` and `.bat` shims | A batch file needs a shell that re-parses its arguments, so a branch or file name could become a command. A shim install shows as missing. |
| React state | A state library | The window holds a few independent parts that each own their state, and the bridge client is the only thing they share. |
| Links in terminal output do nothing | Opening them | Opening one needs the scheme and host check before the system browser, which belongs to spec 004 with the sessions. |
| One instance per Satellite home | Several windows on the same home | Two apps on one home would fight over its state, and the lock also stops node-pty's forking kill helper from opening a second window. |
| Ad-hoc signing on macOS, no signature on Windows and Linux | Unsigned macOS builds, paid certificates | An arm64 Mac refuses a modified binary with no signature, and Satellite loads no remote content and holds no credentials, so nothing depends on a certificate. |
| The cookie encryption fuse off | On | Satellite stores no cookies, and an ad-hoc signature that changes with every build can make macOS ask about the keychain item. |
| A dropped folder's path read by one preload function and sent through `projects.drop` | Dropping only through the dialog, a drop handled in the background process, a preload function that sends the dropped file itself and keeps its path from the page | Electron answers a dropped file's path only in a preload, and the interface never holds Node. A preload that sent the path itself would follow Electron's advice to keep full paths from web content, but `invoke` could still send any path, so it would close nothing, and the interface loads no remote content. One narrow function that answers a string and the same repository check as the dialog keep the boundary where it was. |
| The theme through `nativeTheme.themeSource` | A data attribute on the root that switches the tokens | One setting reaches the CSS, the terminal, the diff, the native dialog and the window background. An attribute would repeat the dark tokens in CSS and give the terminal and the diff a second signal to rebuild on. |
| Plain JSON files in the Satellite home, validated on read | A database | Readable, small and enough for a list of paths and a few preferences, with no native module. |
| Shortcuts on Cmd on macOS and on Ctrl+Shift on Windows and Linux, everywhere, the terminal included | Plain Ctrl shortcuts that stay with the terminal while it has focus, Satellite taking plain Ctrl+K and Ctrl+P | On Windows and Linux plain Ctrl+K, Ctrl+P and Ctrl+O edit the line in Claude Code, which must keep every key it has, and a keyboard user must always be able to leave the terminal. A terminal cannot tell Ctrl+Shift+letter from Ctrl+letter, so Claude Code loses nothing. A terminal sends no Cmd keys, so on macOS Satellite catches a Cmd shortcut before the terminal sees it. Plain Ctrl+K, Ctrl+P and Ctrl+O do nothing outside the terminal. |
| Our own fuzzy matcher for the command menu and the switcher | A fuzzy search library | A few dozen lines rank a few hundred short titles and names, with no dependency to keep current. |
| The branch made with `git branch`, then the worktree added on it | `git worktree add -b` | A failed `add -b` leaves its new branch behind, so making and undoing each on its own is what keeps a failure from leaving anything half made. |
| `git branch --no-track` from a commit id | Letting git track the remote branch the workspace started from | A workspace's branch gets an upstream only when the agent pushes it, so until then its ahead count is its commits on no remote, never its distance from the default branch. |
| Never running `git worktree prune` | Pruning on each list | Prune also forgets the user's own worktrees on a drive that is not mounted, and git prunes on its own schedule. The drop sentence says when to run it. |
| The repository's hooks and filters run during creation | Turning them off for Satellite's git | Setup belongs to the user's hooks, and creation is `git worktree add` exactly as the user would run it in a terminal. The dialog says so before the user creates. |
| A project with workspaces cannot be removed while its folder answers | Forgetting it and leaving its worktrees behind | No worktree is orphaned in the user's `.git`. Archive first, and a project whose folder is gone still leaves the list. |
| Archive refuses unless the inspection's fingerprint still matches | Archiving whatever is there when the user confirms | The user confirms exactly what they saw, and an agent that keeps writing makes the dialog show the latest. |
| Satellite removes every link inside a worktree before git removes it | Trusting git's removal | git on Windows reads a junction as a folder and could empty what it points to. Removing the links first holds on every system for the cost of one bounded walk. |
| `git worktree list -z`, and on a git older than 2.36 newline output with nothing dropped, adopted or archived | Parsing newline output everywhere, refusing an older git outright | A path holding a newline can forge a line in newline output, and listing and making a workspace stay safe on git 2.31 to 2.35. |
| The renderer minified, main and preload readable | Everything minified, nothing minified | The renderer carries Monaco and is large, while main and preload are small and their stack traces land in logs. |
