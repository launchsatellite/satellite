# Architecture

How Satellite is put together and where its security boundary runs. `SATELLITE.md` owns what the product does and `DESIGN.md` owns how it looks.

## Parts

| Part | Folder | What it does |
| --- | --- | --- |
| Background process | `src/main/` | Electron's main process. Full access to the machine. Owns the window, the `app://` protocol, the hardening, the bridge handlers, the state files, the project list, the workspaces and the platform module. |
| Preload | `src/preload/` | Runs in the sandboxed preload and exposes `window.satellite`, the only door between the interface and the background process. |
| Interface | `src/renderer/` | React and Tailwind in a sandboxed renderer with no Node. It draws the three columns and nothing else touches the machine. |
| Shared | `src/shared/` | Code both sides import, such as the bridge contract and the content security policy. |

electron-vite builds all three into `out/`. Electron starts `out/main/main.js`.

## Security boundary

The interface is treated as untrusted. Whatever it shows can never run a command or read a file.

- **Renderer settings.** `sandbox`, `contextIsolation` and `webSecurity` are on, `nodeIntegration` and `spellcheck` are off. The preload is CommonJS with its dependencies bundled, because a sandboxed preload cannot load ESM or `node_modules`.
- **Permissions.** Every permission request, permission check, device request and display media request on the default session is denied, every download is cancelled before a save dialog can show, and a Bluetooth device choice is cancelled rather than left to pick the first device.
- **A crashed page.** When the page's process ends for any reason but a clean exit, its owner ends as on a reload, and the window loads its entry again once. A second crash shows a system dialog that says so and quits Satellite.
- **Navigation.** Every web contents refuses `will-navigate`, `will-frame-navigate` and `will-attach-webview`, and its window open handler denies every new window. The one exception is a main frame reload of the window's own entry, allowed only when the target's protocol, host and path equal the entry URL, so hot reload in development and a reload in production work while every other address stays refused.
- **Content security policy.** `default-src 'none'`, with scripts, styles, images, fonts, connections and workers only from the app itself, images and fonts also from `data:`, and `base-uri`, `form-action`, `frame-ancestors` and `object-src` all `'none'`. Styles allow `'unsafe-inline'` because the terminal and the diff editor insert style elements at run time. In development only, scripts allow `'unsafe-inline'` for the React refresh preamble and connections allow `ws://localhost:*` for hot reload. `src/shared/content-security-policy.ts` builds both, so the dev server and the protocol never drift.
- **The `app://` protocol.** The interface loads from `app://satellite/index.html`, a standard and secure scheme, never from `file://`. The handler answers only `GET` for host `satellite`, decodes the path and confines it to `out/renderer` with `resolveInside`, which follows symlinks before it checks. It serves regular files only, so a folder is never handed to the file loader. Anything refused gets a 404. Every response, the 404 included, carries the production policy and `X-Content-Type-Options: nosniff`.
- **Development server.** `ELECTRON_RENDERER_URL` points the window at the dev server only when the app is not packaged, so an environment variable can never aim a packaged app at remote content.
- **Satellite home.** All state lives in the Satellite home, `~/.satellite` or the path in `SATELLITE_HOME`, which must be fully qualified, with a drive letter or a share on Windows. It is created before the app is ready and set to mode `0700` on every start on macOS and Linux, so an older, looser folder is tightened. When it cannot be made or its path is not fully qualified, a native error box names the folder and the reason before Satellite exits with code 1, except while `SATELLITE_VERIFY_FOLDER_DIALOG` is set, when the exit stays silent. Electron shows no box on Linux this early, so there the same words go to stderr. Electron's `userData` is `app-data` inside it, so caches and storage never land anywhere else.
- **State files.** Satellite's own state lives in three JSON files in the Satellite home, never in a repository, beside one settings file per running Claude Code session (State and Sessions below).
- **Repositories.** Satellite never writes a repository's working files. Making a workspace writes into the repository's `.git`, a branch, a worktree record and what a fetch brings, and archiving removes that worktree record, while the worktree folders themselves live in the Satellite home (Workspaces below). Every git run on a workspace goes through one helper, and runs with prompts, optional locks, fsmonitor, automatic maintenance, the `ext::` transport and submodule recursion off. Listing, inspecting and archiving start no program a repository names apart from a clean filter its config can give `git status` and the list's `git diff`, while making a workspace runs the repository's own hooks, filters and transport programs by design, exactly as the same commands in the user's terminal would.
- **Pull requests.** Every `gh` run Satellite starts for a pull request is one of four constant argument lists, the view, the view by number, the graph query and the job log, with seven checked values, a host, an owner, a repository, a number, a head branch, a boolean and a job id, runs from the workspace folder with a hardened environment, reaches only the host of the checked pull request address, apart from GitHub's own redirect to its log storage for a job log, and starts no program a repository chose. What a pull request says never reaches an argument, a prompt or a notification, and is drawn as Markdown with no HTML element, no image and confirmed links (Pull request below).
- **Menu.** A minimal menu built from roles only, with no links. The app menu on macOS (about, hide, quit), Edit (undo, redo, cut, copy, paste, select all) and Window (minimize, close). View with reload and developer tools exists only when the app is not packaged. The Edit roles are what make copy and paste work on macOS. On Windows and Linux the window hides its menu bar, so no native strip shows above the columns. Electron's shortcut guide says accelerators can work while menu items are hidden and says nothing about a hidden bar, so the menu's keys there rest on Electron's behaviour rather than a documented promise. No top-level label carries a mnemonic and the bar does not auto-hide, so Alt never brings it back.
- **One instance per home.** The app takes Electron's single-instance lock, which Electron scopes to the `userData` folder, so to the Satellite home. A second launch on the same home quits at once and the first window comes to the front. Launches with their own `SATELLITE_HOME`, like every verify run, never collide.
- **Failed start.** If the Satellite home cannot be prepared, the window cannot be created or its entry cannot load, the background process logs one sentence and exits with code 1, so no process lingers without a window.

## Bridge

The preload exposes three functions on `window.satellite` and nothing else. `invoke(channel, payload)` sends one request over the IPC channel `satellite:bridge` and `onEvent(listener)` receives pushes from `satellite:event`. `src/shared/bridge-contract.ts` holds a zod schema for every request, answer and event.

`pathForFile(file)` answers the path of a file the user handed the page, by a drop on the window or any other way a page receives a file from disk, through Electron's `webUtils.getPathForFile`, which only a preload can call. It answers an empty string for anything that is not a `File` and on any error, and Electron itself answers an empty string for a `File` made in JavaScript, so a page learns no path the user did not hand it. It sends nothing anywhere. It answers the full path, which Electron's docs advise against where it can be avoided. Here the path has to reach the background process to add a project, or is typed into Claude Code's prompt as a dropped file, and the page is Satellite's own interface, which loads no remote content of any kind, so no outside script ever reads it. The path is still untrusted and goes through `projects.drop` like any other request.

- **Sender check.** The background process answers only its own window's main frame, and only while that frame shows the app origin, `app://satellite` or the dev server in development, with no user info in the URL. Anything else, including a frame that is already gone, gets `refused-sender`.
- **Validation first.** Channels are looked up in a `Map`, so names like `__proto__` or `constructor` find nothing. Every payload is parsed with its strict schema before the handler runs, so a wrong type, a missing field or an extra key is refused with `invalid-request`.
- **Errors.** A handler throws `BridgeFailure` for outcomes the user sees, with a code from the contract and a sentence written for people. `not-found` names something the page does not own or that is gone, `tool-missing` a tool Satellite cannot find, `limit` a cap that is reached, 16 terminals across every workspace, 200 projects, 20 workspaces in a project, 16 changes reads waiting, 16 files reads waiting, 200 pull request reads waiting, 4 pull request log reads waiting or a process stop already running, `refused` a request Satellite turns down on purpose, such as a folder that is not a repository, and `failed` anything that went wrong. Any other error is logged in the background process and answered as `failed` with no stack.
- **Trust nothing back.** The interface parses every answer and every event with the same contract, so it never acts on a shape it did not expect. One that fails is dropped and logged to the console with its channel or event name and the failing fields, never its payload, so the journeys catch contract drift. Error messages are at most 1000 characters.
- **Lifetime.** Each page load is one bridge owner. When the window is destroyed, its renderer dies or a new document commits in its main frame, the owner ends. Its cleanups run, a cleanup added later runs at once, its events are dropped, and the next page load gets a new owner. A navigation the hardening refuses never commits, so the page and everything it started keep running. A request the old page sends while a reload is still loading lands on the old owner, so nothing a page started outlives it, apart from a workspace creation or archive, which runs to its end so it never stops half made.

## State

The background process owns all state, in three JSON files in the Satellite home. None of it is ever written into a repository. `src/main/state/json-file.ts` reads and writes them.

| File | Holds |
| --- | --- |
| `projects.json` | `{ "version": 2, "projects": [{ "id", "path", "workspaces": [{ "id", "name", "path", "branch" }] }] }`, at most 200 projects of at most 20 workspaces, each id a random UUID, each project path the absolute real path of a working tree root and each workspace path the absolute real path of its worktree, each of at most 4096 characters, the name a workspace name and the branch the one it was made on, of 1 to 255 characters. Project ids and paths are unique, workspace ids are unique across the file and workspace paths too. A project's name is its folder's base name and is never stored. A version 1 file reads as version 2 with no workspaces and is written as version 2 on the next change. A file whose `version` is an integer above 2 comes from a newer Satellite and is never renamed or written, so the run shows no projects, says so once, and refuses to add or remove a project |
| `interface.json` | `{ "version": 4, "selected", "columns": { "left", "right" }, "theme", "notifications", "guideSeen", "files": [{ "projectId", "workspace", "paths", "active" }] }`, the selected workspace as a project id and `main` or a workspace id, or `null`, the column widths as bounded integers, the theme as `system`, `light` or `dark`, notifications as `true` or `false` and `guideSeen` as `true` or `false`, and `files` the open file tabs, one entry per workspace of 1 to 12 distinct relative paths and the index of the active one, at most 50 entries. The page prunes them on every change, so a workspace that left the project list loses its tabs, the most recently used 50 stay and an opened thirteenth tab pushes out the oldest. A version 1 file has no `notifications` and reads with notifications on, a version 1 or 2 file has no `files` and reads with none, and every file before version 4 reads as guide seen, so an update is never a first run. Any of them is written as version 4 on the next save. An older build sets a newer file aside as an unknown version and starts from defaults. The saved tabs are untrusted when loaded, so each path must pass the path rule, at most 1024 characters and no control character, a workspace that is no longer on record is dropped (all are kept when the project list cannot be read, and nothing is written back for that), and a file whose active index or counts are out of range is set aside |
| `sessions.json` | `{ "version": 1, "last": [{ "projectId", "workspace", "sessionId" }] }`, the last Claude Code session id of each workspace that took a prompt, ids only, at most 4200 entries, one per project and workspace pair, the oldest dropped beyond that. Every pair `projects.json` no longer holds is dropped, when it loads and after each save, so archived workspaces, removed projects and dropped workspaces leave no record. This runs only in a run whose `projects.json` existed and parsed, never against the empty list that stands in for a missing, set-aside or unreadable one. Changes run one at a time in order. A file that cannot be read is set aside like the others and only logged, since all it loses is resume offers, and one whose `version` is above 1 is left as it is and not written for the run |

- **Strict schemas.** Each file is read once through a strict zod schema whose `version` is a literal, the one integer a change of shape raises. `projects.json` reads versions 1 and 2 and writes version 2, and `interface.json` reads versions 1 to 4 and writes version 4. A file of an older version reads as guide seen, and so does one that was set aside or could not be opened, so only a missing file starts with the guide unseen. A file that was set aside is followed at once by a save of the fresh state, so the guide stays seen at the next launch. Only a regular file of at most 32 MiB is read, and a write that would be larger is refused, so every file Satellite writes reads back. A `projects.json` that records one folder twice keeps the first record and drops the rest, because Satellite never writes one, while two projects on one folder still set the file aside.
- **Set aside, the newest five kept.** A file that fails to parse or match its schema, or that is not a regular file of at most 32 MiB is renamed to `<name>.unreadable-<milliseconds>.json` beside it, only the newest five of those are kept, and the app starts from defaults and says so once in a toast. When that rename fails after its retries, or the file cannot be opened at all, it stays exactly as it is, the app starts from defaults, says so once, and writes nothing to that file for the rest of the run, so an unreadable file is never overwritten. `projects.json` and `sessions.json` with a `version` above the newest this build knows are never set aside either, so going back to an older build loses nothing, while `interface.json`, which holds only layout and theme, is set aside as an unknown version.
- **Atomic and serialised writes.** A write goes to `.<file>.<uuid>.tmp` in the same folder with mode `0600`, is synced, then renamed over the file, retried on `EPERM`, `EACCES` and `EBUSY`. Each file has one write in flight and at most one waiting, a newer value replaces the waiting one, and a failed write never stops the next. Quitting waits for the waiting writes inside the same bound as the terminals. Leftover temp files are deleted on the first read.
- **Theme before paint.** `interface.json` is read before the window opens, so the saved theme is applied before the first paint (Look below).

## Projects

A project is a folder the user added that git calls the root of a main working tree. `src/main/projects/repository-check.ts` decides it, the same way for the dialog and a drop.

- **Accepted.** An absolute path whose real path, symlinks followed, is a folder outside the Satellite home and is the toplevel of a non-bare repository's main working tree. It is stored by that real toplevel, so one repository reached by two spellings, a symlink or another letter case on macOS and Windows, or on macOS a composed or decomposed accent as git's `core.precomposeUnicode` prints it, is added once.
- **Refused, with a sentence.** A relative path, a path that does not exist, a file, a folder inside the Satellite home, a plain folder, a bare repository, a folder inside `.git`, a linked worktree, whose sentence says when its repository is bare that Satellite needs a repository with its own checkout, a subfolder of a repository, a repository git distrusts because another user owns it, a git older than 2.31 and a git run that fails. A missing `git` answers `tool-missing`.
- **Reads.** Adding a project runs `git -C <folder> rev-parse` with fixed flags through `runTool`. Listing runs `git worktree list --porcelain -z`, or without `-z` on a git older than 2.36, `git for-each-ref` with the tracking format on the workspaces' branches, `git remote` and `git rev-list --count refs/heads/<branch> --not --remotes --` for a branch without an upstream, and `git status --porcelain=v1 -z --untracked-files=all --ignore-submodules=all --no-renames` in the main folder and each workspace, plus `git branch --show-current` when the worktree list fails. Every git command on a workspace, these and the ones below, goes through `src/main/workspaces/git-command.ts`, whose `gitArgs` puts `--no-optional-locks`, `-C <folder>`, `-c core.fsmonitor=`, `-c core.askPass=`, `-c credential.interactive=false`, `-c gc.auto=0`, `-c maintenance.auto=false`, `-c protocol.ext.allow=never` and `-c submodule.recurse=false` before its arguments and refuses a folder that is not fully qualified, and whose `runGit` runs it with its time limit, 5 seconds for every read. git's own security guidance says running any git command in a repository from an untrusted source is not safe, and `safe.directory` does not help for a repository the user owns. Satellite's safety rests on the commands chosen. No listing read touches a pager or a transport or runs a hook, and the optional index write and the fsmonitor hook are off, so a list writes nothing. `git status` and the changes list's `git diff` are the reads that can start a program a repository's own config names, a clean filter driver when they rehash a file, exactly as the same commands in the user's terminal would. A repository's tracked files cannot define one, only its config can. The changes reads, `diff --raw --numstat -z`, `ls-files --others` and `ls-files --unmerged`, `hash-object --no-filters`, `cat-file -s` and `cat-file blob`, `rev-parse`, `branch --show-current`, `symbolic-ref`, `merge-base` and the trial `merge-tree --write-tree`, each with the flags that keep it from starting a program, are listed under Changes, and their one write is the scratch folder of the trial merge in the Satellite home. The Files reads, `check-ignore -z --stdin` and `ls-files -z --cached --others --exclude-standard`, run with the same `gitArgs` and start no program a repository names, and neither writes, so they are listed under Files. Making a workspace adds the network, the hooks and the writes listed under Making a workspace, and archiving adds its own reads and one write, listed under Archiving. Every new git command needs its config-driven programs, such as `core.fsmonitor`, `diff.external`, textconv and filter drivers, its writes and its optional index lock reviewed and recorded here before it ships.
- **Listing.** Each list checks every folder with `stat` and `<root>/.git` with `lstat`, eight projects at a time. A folder that is gone reads as missing, one without `.git` as no longer a repository, and one whose checks do not answer within 6 seconds as missing for that list. Each project has at most one read pending, covering the checks and the git reads after them, so a hung drive never piles up reads however often the window regains focus. A project whose last checks ran past 6 seconds checks its folder again only through two shared slots, so a folder that keeps hanging starts no new thread-holding read beyond those two, while projects that answered last time and new ones read at once and stay healthy. A project leaves the slots as soon as its checks answer in time. A read that hangs still holds its thread until the drive answers, so four folders hanging on their first read can fill Node's four file threads, and saving `projects.json` gives up after 10 seconds with a sentence, so one hung write never holds back later changes.
- **Refresh.** The page asks for one `projects.list` of every project on `refresh-schedule.ts`, the schedule the Changes header uses, at once when the window takes focus or shows again, when a session anywhere finishes a turn and after a project is removed, never while the window is hidden, and it keeps the drawn list when the answer did not change. Focus asks at once like the header's, with at most one list in flight. A list costs a `git worktree list` and a tracking read per project and a status read per workspace, so three projects of four workspaces run about 18 git commands a list, every 2 to 8 seconds while agents keep changing files and every 30 once nothing changes, and none while hidden. A failed list says so once until a list answers again.
- **Removing** forgets the project in `projects.json` and leaves its folder untouched. A project with workspaces is refused while its folder answers, and forgotten with its workspace records when its folder or `.git` is gone or does not answer within 6 seconds.

## Workspaces

A workspace is a branch with its own worktree, recorded under its project in `projects.json`. The main workspace is the project's own folder, has the key `main` and no record, so no request can name it for archive. `src/main/workspaces/` holds all of it, from the git helper to the bridge handlers.

- **Names and folders.** A name is 1 to 48 lowercase letters and digits in groups joined by single hyphens and never a name Windows keeps for a device, `con`, `prn`, `aux`, `nul`, `com0` to `com9` or `lpt0` to `lpt9`. `src/shared/workspace-name.ts` holds the rule, so both processes check it, and every name that passes is a valid branch and a valid folder on every system. The branch takes the same name. A name is also refused when a branch of that name exists, when a branch differs from it only by letter case or sits under it as `<name>/...`, which git cannot keep beside it on every system, or when its folder exists. The suggested name is two words from fixed lists that clash with nothing, with a number added when twenty random pairs are all taken. The folder is `<home>/worktrees/<project>/<name>`, where `<project>` is the project folder's base name with every character outside `A-Z`, `a-z`, `0-9`, `.`, `_` and `-` turned into `-`, cut to 48 characters, `project` when nothing is left and suffixed `-project` when it is a device name, so two projects of one folder name share that folder. Satellite makes `worktrees` and `<project>` with mode `0o700` and one `mkdir` each, never a recursive one, and refuses to go on unless each is a plain folder and the project folder's real path equals the Satellite home's real path joined with `worktrees/<project>`. On Windows a worktree path over 150 characters is refused, so the checkout keeps room under the path limit. Anything Satellite later reads from or deletes as a workspace folder must be its own real path, with no link at any level, whose grandparent is the real `<home>/worktrees`.
- **What it writes into a repository.** Making a workspace writes `refs/heads/<name>` with `git branch`, and `.git/worktrees/<id>/` plus the new folder's `.git` file with `git worktree add`. The default start also fetches one branch, which updates `refs/remotes/<remote>/<branch>` and the object store. Archive's `git worktree remove` deletes `.git/worktrees/<id>/`. A failed creation deletes its branch and worktree again, while the fetched objects and ref stay, as after any fetch. Satellite writes nothing else into a repository, never its working files, and never runs `git worktree prune`, `repair`, `lock` or `move`, so a user's own worktree on a drive that is not mounted keeps its record.
- **Older git.** Satellite needs git 2.31 to add a project. `git worktree list -z` arrived in 2.36, so Satellite asks for it, and when git answers that the switch is unknown it reads the list with newlines for the rest of the run. In that output a path holding a newline can forge a line, so on a git older than 2.36 nothing is dropped or adopted and archive is refused with a sentence asking to update git. Making a workspace still works there.
- **Workspaces in a list.** After its checks pass, a project reads its worktree list, then the tracking counts and one `git status` per workspace, at most 21, then for the branches without an upstream `git remote` and one `git rev-list` each. A branch with an upstream shows how far it is ahead of and behind it. A branch without one shows as ahead the commits that are on no remote and no behind, and in a repository with no remote it shows no count. The tracking, remote, count and status reads share eight slots across all projects, so at most eight of them run at once beside the worktree lists of the eight projects reading. A project's git reads answer within 15 seconds or the list shows that project's workspaces without branch or counts and keeps every record. The read keeps running and the next list waits on it instead of starting another, so a project has at most one read in flight. A late project can still be running its worktree list, which is two runs once per app on a git older than 2.36, or its branch read when the next batch starts, so the git processes in flight can briefly exceed sixteen, each bounded by its 5 second limit. A git that cannot be ended fences its folder, so it is never started there twice. With every git hanging to its limit a list answers in at most 21 seconds per batch of eight projects, 25 batches for 200 projects.
- **Dropping.** Each list compares the records with `git worktree list`. A record whose worktree is listed shows its branch and counts. Any other record is dropped only when its folder is gone and the Satellite home still answers as a folder, whether git lists it as prunable or not at all. Every workspace folder lives in the home's worktrees folder, on the home's own volume, and the home holds the state file just read, so a missing folder below it, the whole worktrees folder included, means deleted, not unmounted. A record outside it, which only a hand-edited file holds, needs the folder holding it to answer instead. A record whose folder is still there is never forgotten, even when git leaves it out or prints its path in another spelling, and its row shows its name with no branch and no counts, because that is all Satellite could read. A separate volume mounted inside the worktrees folder and then unmounted loses its records. The sentence says the folder was deleted outside Satellite when git still lists it as prunable, and that the worktree was removed otherwise, naming the folder that now holds its branch, if any. Several drops in one project become one sentence with their count and names. Nothing is dropped when the worktree list fails or times out, when git is older than 2.36 and the list had to be read without NUL separators, because a path holding a newline can forge lines there, while a workspace is being archived, or while `projects.json` cannot be written. Dropping removes only the record from `projects.json`, never a folder, a branch or anything in `.git`, and a failed save keeps every record in the list and says nothing. The folder checks of a record git does not list are not slotted, so a record folder on a hung drive holds one file thread per project, and the project's one pending read keeps it at one.
- **Adopting.** Each list also looks for worktrees git lists inside this project's own folder in the worktrees folder that have no record, with a branch, a folder name that passes the workspace name rule, a folder that passes the same plain folder rule creation uses and a `rev-parse --git-common-dir` that names this project's repository, so a copy of a repository folder never adopts the original's worktrees, and adds a record for each, named after its folder, so a creation cut short or a worktree made there by hand shows up and can be archived. A worktree git still holds under the lock reason `initializing` is a checkout that died with git, by a power cut or a killed process group, and is never adopted, since nearly every file of it shows as a staged deletion. The list names its folder once per run in a notice and leaves it as it is, and `git worktree remove --force --force` clears it. A record whose stored path reaches the same folder by a link or in another letter case counts as that folder's record. Nothing is adopted while a workspace of that project is being made or archived, when the worktree list fails or had to be read without NUL separators, beyond the 20 workspace limit, or while `projects.json` cannot be written. The save checks again against the latest records, so a creation that finishes in the meantime keeps its own record and no folder is recorded twice. Adopting writes only `projects.json`.
- **Making a workspace** runs five steps, the start, the branch, the worktree, the files and the record, reports each over `workspaces.step` and, when one fails, undoes every started step newest first, the failed one included. The branch comes before the worktree because `git worktree add -b` leaves its new branch behind when it fails, so each is made and undone on its own. The start step resolves a commit id once. A chosen ref is read with `show-ref --verify`. The default start uses `origin` or the only remote, its default branch from `symbolic-ref` or else `ls-remote` within 10 seconds, and fetches that one branch straight into `refs/remotes/<remote>/<branch>` within 15 seconds with no tags, no submodules and no automatic maintenance, so a remote with its own fetch refspec still starts from what was just fetched. When the remote answers that it no longer has that branch, as after a rename of its default branch, the step asks the remote for its default with `ls-remote --symref` and fetches that one instead, saying so, and since Satellite never moves the remote's `HEAD` ref itself, it keeps naming the old branch, so every later creation pays that second fetch and the Branch view of Changes keeps the old base until the user runs `git remote set-head <remote> --auto`. It stops with a sentence that names `git remote set-head <remote> --auto` when the remote names no other. Any other failed fetch starts from the copy fetched last and says so, pointing to a credential helper or an ssh agent when git could not sign in, since Satellite's git never prompts and drops `GIT_ASKPASS`. With no copy it stops with a sentence. With no remote it starts from the main folder's commit and says so, as it does with several remotes none of which is `origin`, saying that instead, and an empty repository is refused. The branch step makes the branch with `git branch --no-track` from that commit, and its undo deletes it only with `update-ref -d` against the same commit, so a branch that existed before or moved since is never deleted. It is also kept when the worktree could not be removed, so the leftover worktree still has its branch. The worktree step refuses a folder git still lists from a worktree deleted by hand and points to `git worktree prune`, makes the folder itself with mode `0o700`, refusing one that already exists, remembers its device and inode, and runs `git worktree add` within 5 minutes. The repository's checkout hook runs, and a failing hook fails the step. The new folder must then be listed by git and still be the plain folder Satellite made. Its undo goes through the same removal as archive (Archiving below). When git lists the folder, it first walks it, stops at a folder on another drive or a walk that did not see the whole folder, and removes every link, then runs `git worktree remove --force`, forced twice when the worktree this run made is locked, and deletes the folder only while it is still that same folder, by 64-bit device and inode, inside the worktrees folder. A folder git does not list, from a `git worktree add` that failed before registering it, goes straight to Node's `fs.rm`, which never follows a link or junction. When the walk stops or a link cannot be removed, nothing is handed to git, the worktree and its branch stay, and the sentence names the folder in the Satellite home and what held it. The next list adopts that worktree. The files step reads `.worktreeinclude` only as a regular file of at most 64 KiB opened without following a link, lists the ignored files within 30 seconds and collects and copies within 2 minutes, a hung read included, checking the worktree folder again first. Quitting, or the user's Cancel through `workspaces.cancel`, stops a running creation, ends its git and undoes what it made, and the quit waits up to 20 seconds for that. An undo that takes longer, such as removing a very large checkout, is cut off at that point and leaves what a crash leaves. A crash of the whole app can leave a branch and a worktree with no record. The next list adopts the worktree (Adopting above), so the user sees it and can archive it. A branch left with no worktree stays, and a new workspace of that name is refused with the sentence that says a branch of that name exists.
- **Copying ignored files.** The files step matches the ignored list against `.worktreeinclude` with Satellite's own matcher. It keeps at most 1000 patterns of at most 4096 characters and 64 segments, and checks a path and every folder above it against every pattern in one pass. The copy visits at most 100000 entries and keeps at most 10000 files and 1 GiB. Collecting and copying share the step's 2 minute deadline and stop when the app quits. Names holding `..`, `.`, an empty part, a backslash or NUL are skipped, and on Windows so are names with a `:`, a trailing dot or space, or a device name. Links, pipes and devices are skipped and never followed. A source is read only when every folder above it is a plain folder by `lstat`. It opens without following a link, without blocking and without becoming a terminal. After the open its 64-bit device and inode must match the earlier check, its real path must still be inside the repository's real path, and that path must still name the same file. A destination folder is made one level at a time and must be a plain folder. The file opens with exclusive create, so a file the checkout made is never overwritten and nothing is written through a link. A folder Satellite may not read is skipped while collecting. A file that cannot be read or that shrinks while copying fails the step, which undoes the worktree. Before anything is copied, `git check-ignore -z --stdin` runs in the new worktree over the chosen files, 5000 at a time within 30 seconds each, and only the files the new worktree ignores as well are copied, so a file the start branch does not ignore never arrives there as a new file git could commit. A file the new worktree does not ignore but already holds, such as one its branch tracks, counts as already in the checkout. A batch git refuses because a path in it sits behind a link or inside a submodule of the new branch is asked again in halves, at most 16 more runs a batch, and what is still refused after that is left out. The step's sentence counts the files it left out, for each reason, and names the first three. When git fails in any other way or does not answer in time, the step fails and undoes the worktree.
- **What the copy cannot rule out.** Node opens by path, so a process that can write in the main folder, such as an agent sandboxed to it, could swap a folder above a matched file for a link and time it to the instant. If it swaps in before the check, out before the real path is read and in again before the last identity check, a file it cannot read itself is copied into the new worktree. Each single swap is caught, so it takes three exactly timed swaps during one file's copy. A hard link in the main folder is a regular file and is copied, whatever it links to. Agents in a checkout cannot write under the Satellite home, so the same window at the destination, and between choosing the folder and `git worktree add`, is accepted. Exclusive create may not hold on an older network file system, so a Satellite home on one loses the never-overwrite rule.
- **Where matching differs from git**, it copies fewer files, or more only among files that are already ignored inside the repository and in the new worktree. Character classes like `[[:digit:]]` read as plain sets of characters. `?` and a class take one character where git takes one byte, so `?.txt` also matches a name like `é.txt`. Case always counts, and names are compared without Unicode normalisation, so a composed and a decomposed spelling never match. An unclosed `[` and a lone trailing backslash match nothing.
- **What a hook inherits.** The repository's hooks and filters run with the environment Satellite gives git, which is the user's login shell environment without the `ELECTRON_` variables and the variables that point git at another repository, without `GIT_ASKPASS` and `SSH_ASKPASS`, and with `LC_ALL=C`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=false` and `SSH_ASKPASS_REQUIRE=never`, plus the `SATELLITE_` verification variables when a verification run sets them, which hold paths and JSON and never a secret. git adds `GIT_CONFIG_PARAMETERS` with Satellite's `-c` values and `GIT_OPTIONAL_LOCKS=0`, so a git command the hook runs also has no askpass, no interactive credential helper, no automatic maintenance, no fsmonitor, no `ext::` transport and no submodule recursion unless it asks. Satellite holds no credential, so a hook gets nothing the user's terminal does not already have. It runs with no terminal and its input closed. On macOS and Linux it sits in git's own process group, which ends at the time limit or on quit, and on Windows git's process tree is ended by its id.
- **Inspecting.** Before archive the dialog asks what would be lost. git lists the worktree from the project's main folder, never from the worktree, whose `.git` file a process inside could point elsewhere, and it must be one of that project's linked worktrees, not bare and not prunable, whose own `rev-parse --git-common-dir` names the project's repository, so a copied repository folder whose `.git` still lists the original's worktrees never inspects or archives them. A record whose folder is still there but that git no longer lists, or lists as prunable, because its `.git` file or the repository's `.git/worktrees` entry went or another repository took the project's place, is refused with a sentence that names its folder in the Satellite home and says that moving the folder out lets the next list forget it. A record whose folder is gone from the Satellite home is refused with a sentence that names where it should be. Then, in the worktree, `git status` gives the uncommitted files, `ls-files -z -v -s` the files git skips with assume-unchanged or skip-worktree and the submodule entries, `rev-parse --git-path modules` where git keeps submodule history, and `rev-list` with `log --no-show-signature` the commits on no remote, or on a detached head on no branch, remote or tag. The answer carries a fingerprint, a SHA-256 over the folder's device and inode, HEAD, the raw status, everything shown and the count of Satellite's terminals there, so the user confirms exactly what they saw. Anything Satellite cannot read or count is shown as a loss it cannot rule out, with the danger button.
- **Archiving** inspects again and refuses unless the fingerprint matches, refuses a locked worktree and one with submodules checked out or not checkable, stops Satellite's terminals in the folder, walks the worktree for links and mounts, then inspects once more and refuses on any change, and only then removes the links and runs git. The dialog shows the lock and the submodules first and offers no confirm for them. Removal follows git's own rules for `git worktree remove`. It removes only clean worktrees with no submodules, and `--force` once removes an unclean one, or one with submodules, while a locked one needs `--force` twice. git's removal walks the folder with its own `lstat`, which on Windows reports an NTFS junction as a folder, so git could walk into a junction and empty the folder it points to, such as a checkout that `npm link` joined into `node_modules`. So Satellite never trusts git's removal across a link on any system. Before the last inspection, Satellite walks the worktree itself without following any link, with `opendir` and `lstat`, and on Windows it also counts a folder whose real path differs from its own as a link. A folder whose device differs from the worktree's is another file system mounted there, such as a network or FUSE mount, and the walk stops at it, so archive is refused before anything is removed, with a sentence that names it. The inspection walks the same way and names that folder, or says why it could not see the whole folder, and the dialog offers no confirm for either. It removes each link it found with `unlink`, falling back to `rmdir`, which removes a junction itself, never what it points to. A link it cannot remove stops the archive before git runs and names the link. Archive and the creation undo share this one removal in `worktree-removal.ts`. A folder it cannot read is passed over and the walk goes on, so every mount it can reach is still found. The walk is bounded at 1000000 entries, 256 folders deep and 60 seconds, and a walk still running at 60 seconds, such as one stuck on a mount whose server stopped answering, is abandoned at that point. On every system, a walk that did not see the whole folder, because a folder was unreadable, a bound was reached or a folder did not answer, refuses the removal before git runs, with a sentence that says why and what to do. On macOS and Linux `lstat` reports every link as a link, so git and Node's `fs.rm` would not follow one anyway, but only the whole walk rules out a mount. Node's documentation says `lstat` describes a link itself and `unlink` removes a link without touching its target, and it says nothing about junctions. The unit tests and the `workspaces` journey prove a junction on Windows and a symbolic link elsewhere, on all three systems. Satellite then runs `git worktree remove` without `--force`, which removes a clean worktree, ignored files included. Only when git answers that the worktree holds modified or untracked files, and the last inspection listed uncommitted files the user agreed to lose, does it run once more with `--force`, never twice. When the last inspection was clean, that answer means something appeared since, so the archive stops and says so. Satellite never forces a worktree with submodules checked out, because `--force` would delete a submodule's own history in `.git/worktrees/<id>/modules` with it, and git still refuses submodules itself on the first run. git deletes the folder, then forgets the worktree even when some files could not be deleted, such as files another process holds open on Windows. Satellite then deletes what is left with Node's `fs.rm`, three tries 200 milliseconds apart, and only while the folder is still the plain folder it inspected, by device and inode, inside `<home>/worktrees/<project>`. A folder that still holds files is named to the user and its record is forgotten, because git no longer knows it. When git still lists the worktree afterwards the record stays, and the sentence says the folder is as it was only when nothing was forced and no link removed. When git runs past 2 minutes, the sentence says some files may be gone and the record stays for the next list to judge. Quitting waits up to 20 seconds for a running archive. The one write is `worktree remove`, whose clean check runs `git status --ignore-submodules=none`, so a repository's own clean filter can run there, as in the user's terminal.
- **What archive cannot rule out.** The fingerprint covers the folder's identity, HEAD, the branch, the lock, `git status`, the counts and the terminals, so it catches a new file, a new commit or a new terminal. It does not catch further edits to a file the dialog already listed, which the user has agreed to lose, or edits to files git skips with assume-unchanged or skip-worktree, which the dialog counts and names as lost. A process with the user's rights that writes in the worktree between the last inspection and git's removal of a worktree the dialog showed with uncommitted files loses that write unseen, a window that holds the removal of the links found, git's start and the scan of the first `git worktree remove`, a few milliseconds for a small worktree with few links. In a worktree the dialog showed clean, git itself refuses such a write and the archive stops. One that swaps the worktree folder or a folder inside it for a link, or mounts a drive there, after the walk and before git opens it gets git to walk into it, a window as long as the last inspection. `git worktree remove` has no dry run, so the links go once that last inspection has found the worktree listed by git, unlocked and sharing this repository's common folder, and a refusal git makes after that, such as a lock taken in that window or a write error, leaves the worktree without its links, which the failure sentence says. Only something already running as the user can use either window. A bind mount of a folder from the same file system has the same device, so the walk cannot tell it from a plain folder, and on Windows a mounted volume is a junction and is removed as a link.

## Platform

`src/main/platform/` is the only code that knows about executables and shells, and it holds every platform difference apart from the five small branches skill `satellite-stack` names in The platform module.

- **File system rules.** `file-system.ts` holds the file name rule for copied files, which on Windows refuses a `:`, a trailing dot or space and device names, the 150 character limit on a workspace folder on Windows, a folder whose real path differs from its own counting as a link on Windows, the Windows short name test the change path rule adds and the owner-only mode of the sessions folder, plus the error code, folder identity and open flag helpers the features share.

- **Overrides.** `SATELLITE_GH` and `SATELLITE_CLAUDE` hold a JSON array of strings, the executable then its leading arguments, and replace the search for that tool. Anything else is logged with a sentence that names the variable, and the tool reads as missing, as does an override whose fully qualified executable is not a file. `SATELLITE_GIT` does the same for git, which only verification sets, to put a stand-in in front of it.
- **Login shell environment.** An app started from the Dock, Finder or a desktop menu inherits a minimal `PATH`. On macOS and Linux Satellite runs the user's login shell once in the home folder, so no project's shell hooks run, interactive with a 5 second limit, reads its environment between two markers and merges it over its own. Whenever both markers come back the block is used, even if the shell exits with an error. Otherwise Satellite falls back to the app's own environment. Windows uses the app's environment as it is.
- **Search.** Tools are found by walking `PATH` and skipping empty and relative entries, so the current folder is never searched. A match must be a regular file, and executable on macOS and Linux. On Windows surrounding quotes are stripped, an entry needs a drive letter or a network share, and only `.exe` and `.com` files count, because batch files need a shell that re-parses arguments.
- **Running.** Tools run with an argument array and no shell, a 16 MiB output limit and the user's environment without any `ELECTRON_` variable or the variables an AppImage and Electron add on Linux, with the desktop name Electron rewrote put back. Past its time limit, 30 seconds unless the caller asks for less, its whole process tree ends. On macOS and Linux each tool starts in its own process group, which gets `SIGHUP` and two seconds later `SIGKILL` for anything still running, and a tool that already exited is never signalled by its own id, only through its group, whose id the system cannot hand out again while a member lives. On Windows the tree is ended at once with the start-checked stop below, from a fresh table read, and then the tool itself through Node's own handle to it if it still runs, so a table read that fails on a slow machine still ends the tool, and a tool that already exited is not ended at all, since its id may belong to another process by then. `git` also runs without `GIT_DIR`, `GIT_WORK_TREE` and the other variables git lists in `git rev-parse --local-env-vars`, so a variable from the login shell never points a read at another repository, and with `LC_ALL=C` and no `LANGUAGE`, so its messages read the same in every locale. It never waits on a prompt of its own. `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=false` and `SSH_ASKPASS_REQUIRE=never` are set and `GIT_ASKPASS` and `SSH_ASKPASS` are dropped, so a sign-in a credential helper already stores keeps working and anything that would prompt fails or ends at the time limit instead. Two waits remain possible, both ended by the time limit. On Windows, where a tool gets no session of its own, ssh can wait on the hidden console, and on macOS a credential helper can make the system show its own keychain dialog, which belongs to the system rather than to git. `git` runs also take a closed list of six variables by name through the `gitVariables` option, `GIT_NO_LAZY_FETCH`, `GIT_NO_REPLACE_OBJECTS`, `GIT_GRAFT_FILE`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM`, and the option does nothing for `gh` or `claude`. The reads of workspaces, branches and the pull request set `GIT_NO_LAZY_FETCH`, the reads behind Changes, Files and the pull request's files, and the ahead and behind counts the sidebar and the Changes header show, also set `GIT_NO_REPLACE_OBJECTS` and point `GIT_GRAFT_FILE` at a path under the null device that cannot exist, so a replace ref or a graft file in the shared `.git`, which one command in any workspace can write, never hides or changes what they show, and only the conflict check sets the last three. The `cwd` option sets a run's working folder, which the pull request runs pass as the workspace folder, and for `gh` the environment is the one under Pull request below. The `input` option hands a run text on its standard input, written and closed at once, and a tool that stops reading early cannot raise an error in Satellite. Only `git check-ignore --stdin` uses it, and a run given none has no standard input. Satellite needs git 2.31 or newer for `rev-parse --path-format`, and an older git gets a sentence asking to update it. A run that cannot be ended, such as one stuck on a dead network drive, still answers as timed out within five seconds of its limit on macOS and Linux and within 13 on Windows, where the stop reads the process table and runs its script first. For git Satellite then starts no other run in that folder until the stuck one exits, and every read there answers as failed at once. Errors name the tool or the override variable, never its arguments.
- **Folder dialog.** `folder-dialog.ts` opens the native folder dialog as a sheet on the window. When `SATELLITE_VERIFY_FOLDER_DIALOG` holds an absolute path and the live driver check below passes, the dialog never opens and that file's trimmed content is the answer, a missing or empty file meaning canceled. Verification sets it on every launch. A packaged app reads it too, so the journeys can prove a release, and it grants nothing new. Whoever sets a variable for Satellite can already set `SATELLITE_CLAUDE` to any program, and the answered folder still meets the full repository check.
- **Notifications.** `system-notices.ts` is the only code that shows a system notification, sets the app icon count or sets the Windows app identity. `showNotice`, `setAppBadge` and `prepareSystemNotices` take Satellite's own sentences with cleaned names and a count, never a page's text (Inbox and notifications below).
- **Quiet verification.** `src/main/window/verification.ts` reads the same variable together with `SATELLITE_VERIFY_DRIVER_PID`, the process id of the driver that launched the app. The live driver check passes when both are set and Satellite can signal a process with that id, which proves a live process of the same user, not that it is the driver. Only when it passes at start does the app run quietly on macOS. The folder dialog answer and `SATELLITE_VERIFY_LINKS`, which writes each opened link to a file instead of the browser, are honoured only while it passes. `SATELLITE_VERIFY_NOTICES` records every notification and app icon count to a file and makes the window count as not in front. It is honoured when the check passes at its first call, and that answer holds for the whole run (Inbox and notifications below). It then takes the `accessory` activation policy before any window exists, so it gets no Dock icon or menu bar and never comes to the front, and the window is never shown. It still renders, because `paintWhenInitiallyHidden` keeps the page painting and `backgroundThrottling` is off for that window, and the driver turns on the protocol's focus emulation, so focus, keys, screenshots, drops and resizes behave as in a focused window. `SATELLITE_VERIFY_FOREGROUND=1` shows the window as a normal app for a person who wants to watch, and the release workflow sets it on macOS and Windows so a packaged app is proven as users see it. Windows and Linux always show the window. The app also starts quitting within a second once that driver process is gone, so a driver that dies, even by `SIGKILL`, never leaves an app running. A leftover variable with no live process of the user's behind it changes nothing, so a user's own Satellite is never hidden, and a normal launch sets neither variable.
- **Install commands.** `installCommand(tool)` in `install-commands.ts` answers the fixed step the first run check shows for a missing tool on this platform, a command, or on Linux for `git` and `gh` the address of each project's official install instructions, because no one package command is right on every distribution.
- **Process table.** `process-table.ts` is the one reader of what runs, and session cleanup, listing and stopping all use it. On macOS and Linux it runs `/bin/ps`, else `/usr/bin/ps`, as `-A -ww -o pid= -o ppid= -o pgid= -o stat= -o lstart=` and the short program name (`ucomm=` on macOS, `comm=` on Linux), never the command, with the environment replaced by `LC_ALL=C` and `TZ=UTC`, so the start column parses the same everywhere, in 1 second, 16 MiB and with stdin closed. On Windows it runs Windows PowerShell from `%SystemRoot%` with `-NoLogo -NoProfile -NonInteractive` and one constant script that asks CIM for `Win32_Process` with only the process id, the parent id, the creation date and the name, in 5 seconds with no window and no execution policy switch, and the answer is JSON. `readCommands` is a second bounded read of the full command for given processes, with the same pinned environment, `ps -p` with `lstart=` on macOS and Linux and a constant script with the ids in an environment variable that also answers each creation date on Windows. A command counts only when its start matches the table's start for that id, so an id reused between the two reads shows the short name instead of another process's command line. A row that does not parse is dropped alone, a process id that appears twice loses every row, a failed or timed out run is an empty table, and a start that cannot be read is `null`, which nothing is ever listed or signalled on. A parent link counts only when the parent has a start no later than its child's, since an id can be reused, and `subtreeOf` walks down from a process on those links and never through an ancestor of it.
- **Listening ports.** `listening-ports.ts` asks only after something is listed, for at most 500 process ids, every listed row's own process first and then their subtrees, so one large subtree cannot use up the bound before another row's own port, in 3 seconds and 16 MiB. macOS runs `/usr/sbin/lsof -nP -iTCP -sTCP:LISTEN -a -p <ids> -F pPnt` with `LC_ALL=C` and reads its output whatever its exit code, since it exits 1 when one id listens on nothing. Linux runs the first `ss` found in `/usr/bin`, `/usr/sbin`, `/sbin` and `/bin` as `-H -l -t -n -p`. Windows runs a second PowerShell for `MSFT_NetTCPConnection` in `root/StandardCimv2` with `State = 2`, a class and not the `Get-NetTCPConnection` script module that the default execution policy refuses. Only a numeric host and a port from 1 to 65535 pass, and the answer is cut to the ids asked.
- **Ending a subtree.** `endSubtree` in `process-tree.ts` signals one process id at a time and never a process group. It reads a table, finds the target by process id plus start time, takes that process and its descendants without id 1 or Satellite's own, and prepares a delivery for them. On macOS that is `SIGTERM` to each, checked 300 milliseconds later, and after the 2 second grace a read and `SIGKILL` to what still runs of it and to anything it started since. On Linux each process's start ticks from `/proc/<id>/stat` are recorded right after the first table read and compared again right before each signal, the forced round included, which signals only processes the first round recorded, so a process started since then or one whose ticks could not be read is left and the stop says something survived, and a Linux that cannot read them refuses. On Windows the delivery is one constant PowerShell script that gets `id:start` pairs in an environment variable, 200 at a time, opens each process, then reads the creation dates from CIM with the same conversion the table read uses, and kills a process through its open handle only when that start equals the listed one to the millisecond, so both sides of the comparison come from one source. An open process holds its id, so the date read for that id is its own. It never uses `taskkill`. A final read must show nothing of the subtree left under the same id and start, or the stop fails. An empty table at any read throws, so a failed read signals nothing and never counts as nothing left.

## Terminal

`src/main/terminal/` runs each Claude Code session in a pseudo terminal through `src/main/platform/pty.ts`, and `src/renderer/terminal/` draws it with xterm.js.

- **Cleanup.** When the owner ends, through a reload, a crash or a closed window, its terminals are killed, even one still starting. On macOS and Linux a kill lists processes once with `ps`, taken from `/bin` or `/usr/bin` and never searched in `PATH`, then sends `SIGHUP` to the terminal's process group and to every descendant. When the terminal has exited and nothing from that list is left, the kill is done. Otherwise, two seconds after it began, everything from the list that still runs, and anything those processes started since, gets `SIGKILL`. A process is matched by its pid and start time, so a reused pid is never signalled. On Windows a fresh process table read finds the terminal's own process, takes it and what it started, a child counting only when it started no earlier than its parent, so a process whose parent id was reused is never included, and ends them with the same start-checked script a stop uses, within 5 seconds for the read and 5 for the script, then the kill waits up to two seconds for the pseudo terminal to report the exit. A terminal that already exited is not ended again. Only when it never does is node-pty's own kill called, because that kill starts a helper with `fork`, which the packaged app's run-as-Node fuse turns into a second Satellite. The single-instance lock makes such a launch quit at once, and the running Satellite does not bring its window forward for a launch that carries node-pty's helper script. node-pty's spawn, write, resize, pause and resume never fork.
- **Workspaces.** Each terminal remembers its workspace and the folder it started in. Archiving counts and stops the terminals that started inside the workspace's folder, through two methods, `countInside` and `stopInside`, which wait until each process tree has ended and its settings file is gone, bounded by the kill's worst case. A terminal still starting there is stopped before it spawns, and one already being ended, by a closed tab or a reload, is counted and waited for too. A terminal counts as running from its start until its process reports its exit, so a session is never resumed while a process that holds it may still be alive. Removing a project stops the terminals in its folder and in the folders of the workspace records it forgets, so a project nested inside another project's folder loses its terminals too when the outer one is removed. When the list drops a workspace whose worktree went away outside Satellite, the terminals in its folder are stopped the same way, the page closes its tabs, and one toast says Claude Code stopped there, naming every workspace that left at once, or their count past three.
- **Quit.** Closing the window quits Satellite, on every system. While sessions run, quitting or closing first asks in a system dialog that counts them, Quit Satellite or Cancel, and Cancel leaves everything running. A verify run started by a live driver never asks. Quitting then refuses new terminals, saves `sessions.json` with every change still waiting in line, and waits until every terminal has been killed this way and cleaned up, then exits. The wait is bounded by a session's whole end chain, the kill's worst case of four seconds, the two second grace plus two process listings of at most a second each, or on Windows the 5 second table read and the 5 second script plus the two second wait for the exit, then the second a process gets to report its exit, then half a second, plus another half second. So every settings file is removed and every secret dropped from the listener before Satellite exits. Another quit during the wait is held too, so it never cuts the wait short. So Claude Code, its tools and anything that ignores `SIGHUP` end with Satellite. A process that fully detaches before the kill, by leaving the process group and losing its parent to the system, is out of reach and survives.
- **Running roots.** `roots()` answers each running session with its page, its workspace, the process id of its pseudo terminal's process and the moment Satellite spawned it, which `PtyProcess.pid` provides. The processes feature trusts a root only while its start is no later than 2 seconds after that moment.
- **Limits.** 16 terminals at once, a terminal still being killed included. Input is split into writes of at most 65536 characters and sent through one queue per terminal, so a large paste arrives whole and in order. Scrollback keeps 5000 lines.
- **Output flow.** The background process gathers output for 8 milliseconds and sends it in events of at most 65536 characters. The interface acknowledges each event once xterm.js has processed it. With more than 256 KiB of output unacknowledged the pseudo terminal is paused, and it resumes once that falls to 32 KiB, so a flood of output never piles up in memory. A terminal that ends is resumed first, so a page that is gone never holds a process paused.
- **Tabs.** Each workspace holds its sessions as tabs, at most 16 across the app. A start past that bound opens no tab and says so, in the empty pane of a workspace with no session and as a toast beside other tabs. Every tab's terminal stays mounted for the page load and only the selected workspace's active tab is shown, so a hidden session keeps taking output and its screen. A hidden terminal never fits, and when it is shown again it fits, sends its size and takes focus. The command menu goes to the next or previous session of the workspace, wrapping around, so the keyboard can leave a terminal for another tab.
- **Failures.** A failed start or an ended session shows one sentence in a status region, so screen readers announce it, and a button that starts a fresh terminal. Focus moves to that button, because xterm.js takes Tab as input and would otherwise hold the keyboard. A spawn failure says that Claude Code couldn't start and nothing in the project changed. When Claude Code is missing, the tab closes. With no other tab in the workspace the empty pane says so, with the install step for this system and Start Claude Code, and beside other tabs the same sentence comes as an error toast. The sentence stays until a start anywhere works.
- **Links.** Terminal output is untrusted, and links are where it reaches outside the app. A plain click on a link does nothing. Cmd+click on macOS, or Ctrl+click elsewhere, on a plain-text address or a hyperlink escape sequence always asks first, since a hyperlink can show any text and output can hide part of a plain address, by concealed text or text coloured like the background. The dialog names the site and the full address as the parser writes it, in Geist Mono, wrapping at any character and scrolling inside its own box. A look-alike host shows in its `xn--` form, a numeric host in its dotted form, and the site sits above the address, so no long address pushes it out of view. The dialog opens only from the user's own click. Like the other dialogs it puts Cancel first, on the left, and focus starts there, so an Enter meant for the terminal cancels, and Tab then Enter or a click on Open in browser opens the link. A refused open keeps the dialog and says why. Link text the page cannot parse as an address is refused there with the same sentence and never reaches `links.open`. Only `http` and `https` reach either handler, and the background process checks again (Bridge above). Electron's security checklist warns against passing untrusted content to `shell.openExternal`, and only that checked address ever reaches it.
- **Option on macOS.** xterm.js's `macOptionIsMeta` stays off, so Option types the characters the keyboard layout puts there, the `@` and `#` of many European layouts included, and Claude Code's Option shortcuts such as Option+Enter and Option+P do nothing. A new line is Shift+Enter, which Satellite sends itself.
- **Text paste.** Every paste into a terminal, from the clipboard, a drop or Send to Claude Code, goes through one path that removes ESC and every other control character (C0, DEL, C1) except tab, line feed and carriage return, then hands the text to xterm.js's paste. So a copied page or file that holds `ESC [201~` cannot end Claude Code's bracketed paste early and submit what follows as a prompt. Line breaks stay, so a pasted line break still acts as Enter while Claude Code has bracketed paste off, as it does before its prompt first shows.
- **Image paste.** Claude Code reads the clipboard itself, on `Ctrl+V`, or `Alt+V` on Windows. A paste event that holds a file and no text, such as Cmd+V of a copied image on macOS, sends that key instead of a paste, so Claude Code picks the image up. Satellite looks only at the kinds of what the clipboard holds and never reads its content.
- **Dropped files.** A drop of up to 20 files on a terminal types their paths after the prompt, separated by spaces, with one space after, and never submits. Each path comes from `pathForFile`, is at most 4096 characters and holds none of the characters Send to Claude Code removes, else a toast says why and nothing is typed. A path of plain characters, with no backslash, stays as it is, any other sits in double quotes with each quote escaped and the backslashes before a quote or the end doubled, so no name can close its quotes early. The text goes through xterm.js's paste, which brackets it when Claude Code asks for bracketed paste.
- **Send to Claude Code.** `sendToClaudeCode(text)` dispatches the window event `satellite:send-to-claude-code`, and the sessions pane is its one listener. The pane cleans the text with `promptText`, which reads at most its first 12800 characters, so a huge input never stalls the interface. Line breaks, tabs and the Unicode line and paragraph separators become spaces. Every other control character (C0, DEL, C1), lone surrogate, format character (direction marks, zero-width characters, tag characters and the rest of `\p{Cf}`) and supplementary variation selector is removed, apart from a zero-width joiner between two emoji and a zero-width joiner or non-joiner between two letters of the Arabic or Indic scripts, which Persian and Hindi words are written with. The result is cut to 800 characters on a whole character, because Claude Code folds a longer paste into a placeholder the user cannot read before pressing Enter. It types only into the shown session of the selected workspace. With no live session there, a toast asks to start one. Until a hook from that session has arrived, a toast says Satellite sends there only after Claude Code reports the user's first request and nothing is typed, since its trust question may be on screen. Claude Code holds back every settings file hook until its trust question is answered and runs no HTTP hook at session start, so the first hook is the first prompt the user submits, and when Claude Code's settings block hooks, or the listener could not start, Send stays refused for that session. While that session needs you a toast asks to answer it first, since text typed into a permission question could choose an answer. The text goes through xterm.js's paste, which turns line feeds into Enter and does not filter escapes, so the cleaning is what keeps it from submitting. With bracketed paste on, no escape is left to end the bracket early, and with it off every byte is a printable character, so neither way submits. Focus moves to the terminal after the current event, so a key press that triggered the send never lands in the prompt, and only when no text field, dialog or the command menu outside the sessions pane holds focus at that moment. Otherwise focus stays where the user is typing and the text waits in the prompt, so a send that lands late can never turn the user's next Enter into a submit. Characters that draw as blank but are no format characters, such as the Hangul fillers, blank braille, the combining grapheme joiner and the wide spaces, stay, since none can submit, reorder or carry a hidden message the way tag characters do. Text that starts with `!`, `/`, `@` or `#` switches Claude Code's input mode or opens a menu, so a caller that sends text someone else wrote, such as a review comment, puts Satellite's own words first.
- **Theme.** Every mounted terminal, shown or hidden, takes its colours from the app tokens and follows each theme change. Claude Code asks the terminal's background when it starts, so a running session keeps the theme it chose then.
- **Environment.** Claude Code starts in its workspace's folder with the user's environment plus `TERM=xterm-256color` and `COLORTERM=truecolor`. It drops what names whatever started Satellite, by exact name, matched without regard to case on Windows. Those are the markers Claude Code sets in the processes it starts, as seen in their environment, among them `CLAUDECODE`, `CLAUDE_PID`, `CLAUDE_CODE_SESSION_ID` and `CLAUDE_CODE_EXECPATH`, the IDE port and entry point, the terminal program, tmux, screen and every `VSCODE_` variable, so a Satellite started from inside a Claude Code session or an editor still gives the user normal sessions. Everything else passes, the user's own Claude Code variables and `AI_AGENT` included. When an HTTP or HTTPS proxy is set in the environment, `127.0.0.1` joins `NO_PROXY`, so the hooks reach the listener directly. A proxy set in the `env` of Claude Code's own settings files is outside this rule, so its hooks may go through that proxy, carrying the launch's secret, or fail and leave the session idle. `GIT_ASKPASS` goes with them only when it sits in the same folder as `VSCODE_GIT_ASKPASS_MAIN`, because that helper cannot reach its editor once the editor's variables are gone, while an askpass of the user's own stays.
- **DOM renderer.** xterm.js draws with its default DOM renderer. A GPU renderer would need another dependency, and Claude Code's own terminal guidance turns GPU acceleration off in embedded terminals because it garbles text.
- **Terminal font.** The DOM renderer draws block and box characters from the font, and Geist Mono's block glyphs are shorter than its line box, which leaves seams between rows in Claude Code's logo. The terminal uses Geist Mono under its own family name with ascent and descent overrides that match the block glyphs, so blocks join with no gap and lines sit tight. A taller line height was rejected because it brings the seams back.
- **Unicode 11.** The unicode11 addon is active, so emoji and wide characters take the same cell widths Claude Code expects. The graphemes addon was rejected because it is experimental.
- **Shift+Enter.** xterm.js has no kitty keyboard protocol, so Shift+Enter with no other modifier sends ESC then CR, the sequence Claude Code reads as a new line, and the key's own events are swallowed.
- **Held keys.** Each time the terminal takes focus, by a click, a shown tab, an inbox row or a command, it drops repeated key presses until the first fresh one. Enter held on a row that opens a session would otherwise repeat into Claude Code's permission question and pick the highlighted answer. A dropped key press is also kept from typing through the browser's own input path.
- **The spawn helper.** node-pty ships its macOS `spawn-helper` without the executable bit, which fails every spawn with `posix_spawnp failed`. The postinstall step restores the bit. `npm rebuild node-pty` does not, and the node-pty beta that fixes it was rejected because it is a beta. node-pty stays out of the bundle because it is a runtime dependency, and `src/main/platform/pty.ts` is the only file that imports it.
- **Windows pseudo terminal.** On Windows `terminal.start` answers with the backend node-pty uses, ConPTY from build 18309 and winpty before it, and the Windows build number from `os.release()`. The terminal view hands both to xterm's `windowsPty` option, which xterm's docs ask for when the pty runs on Windows, so xterm applies its ConPTY handling when rows grow and turns reflow off where ConPTY can't reflow. Elsewhere the answer is null.

## Sessions

Each terminal is one launch of the user's own `claude` in a workspace. `src/main/terminal/terminal-sessions.ts` runs a launch and `src/main/sessions/` holds its parts.

- **The folder.** The page names a workspace, never a folder. At start the background process looks the project up in `projects.json` and takes its path for `main` or the workspace record's path otherwise. A workspace being archived is refused, the folder must answer as a folder within 6 seconds, and a workspace's folder must also pass the plain folder rule inside `<home>/worktrees/<project>` with no link at any level. The record is read again after those checks, so a project removed meanwhile is refused, and the terminal remembers the folder at once, so an archive or removal that begins later stops it before or after it spawns.
- **The launch.** A new session gets a UUID the background process makes and `--session-id <uuid>`. A resume reads the one id `sessions.json` holds for that workspace and gets `--resume <uuid>`, refused when there is none or a running terminal holds it, since resuming one session twice at once corrupts its transcript. Every launch gets its own launch UUID, its own 32 byte secret and `--settings <home>/sessions/<launch id>.json`. Claude Code gets the environment above and nothing from the page.
- **The settings file.** It holds only HTTP hooks for `UserPromptSubmit`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `Stop` and `StopFailure`, each posting to `http://127.0.0.1:<port>/hook/<launch id>/<event>` with the secret as a literal `Authorization: Bearer` header and a 5 second timeout. The folder has mode `0700`, the file is created exclusively with mode `0600` and never through a link, and on Windows it inherits the Satellite home's access list. The secret is never on an argument list, in an environment, a log or an event. Claude Code merges these hooks with the user's own and writes nothing to the user's settings or the repository. Claude Code runs only command and MCP tool hooks at session start, so Satellite registers no hook there. The file is removed when its process exits, and the first start of each run sweeps leftovers by name and kind, logging and passing over any it cannot remove.
- **The listener.** One `node:http` server on `127.0.0.1`, port `0`, started before the bridge. It answers `405` to anything but `POST`, `404` to any other path, `403` to a `Host` other than `127.0.0.1:<port>` and to any `Origin`, `401` unless the secret matches that launch in constant time, `415` to a type other than JSON and `429` past 100 events per launch per second, counted only after the secret. Every answer is `204` or a refusal with no body, no CORS header and `Connection: close`, so it never decides anything for Claude Code. It holds 64 connections, headers within 5 seconds and a request within 10. It keeps at most 64 KiB of a `Notification` body, refusing a larger one with `413`, and 1 MiB of any other, taking a larger one as its event with no session id or agent. A body that is not a JSON object of the expected shape gets `400`. From a body it reads only `session_id` as a UUID, `notification_type` of at most 64 characters and `agent_id` of 1 to 128 characters, and keeps only the session id and the agents that are asking, never a prompt, a tool's input or output, or a message. When it cannot start, sessions run without `--settings`, stay idle and the error is logged once.
- **Status.** Each event moves the session through `idle`, `working`, `needs-you`, `done` and `stopped`.

  | Event | Moves the session to |
  | --- | --- |
  | `UserPromptSubmit` | `working` |
  | `PermissionRequest`, or a `Notification` of `permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog`, `agent_needs_input` or `quota_auto_resume_stale`, which Claude Code sends when it waits for Enter after a usage limit reset | `needs-you`, remembering which agent asked |
  | `PostToolUse` or `PostToolUseFailure` | `working`, or while needs you only once every agent that asked has had a tool finish |
  | A `Notification` of `elicitation_complete` or `elicitation_response` | `working` from needs you |
  | A `Notification` of `idle_prompt` | `done` from working or needs you |
  | A `Notification` of `quota_auto_resume_fired`, which Claude Code sends when it carries on after a usage limit | `working` |
  | Enter, Escape or a digit typed alone into that session's terminal | `working` from needs you, every agent that asked let go |
  | A `Notification` of any other type | nothing changes |
  | `Stop` or `StopFailure` | `done` |
  | The process ends | `stopped`, which nothing leaves |

  Every agent asking at once is remembered, up to 16. A session stays `idle` until its first hook, so it reads idle before the trust question is answered and for its whole life when Claude Code's settings block hooks. Those include a repository's own `.claude/settings.json` once the user trusts the folder, since `disableAllHooks` takes the value left after settings precedence and `allowedHttpHookUrls` filters every HTTP hook by a merged list. Satellite overrides neither, because a `disableAllHooks` of false in its settings file would also turn back on hooks the user turned off. Such a session never shows needs you, never reaches the inbox and raises no notification, and Send to Claude Code stays refused there. No hook fires when the user answers a permission question, so the keys that answer Claude Code's question count as the answer. A digit picks an option, Enter takes the highlighted one and Escape declines, and each arrives as one write of its own, while arrows, letters and pastes change nothing. So an approved tool that runs for minutes reads working, and a declined one reads working until the turn ends. The keys are a guess, so a digit or Enter typed into an MCP server's form also reads as working, and the next hook sets the status right either way, a new ask included. Satellite's `Stop` hook runs beside the user's own, so done can show while slower `Stop` hooks of the user's are still running. Events for a launch that has ended do nothing.
- **The resume record.** Every accepted hook carries Claude Code's current session id, and the launch takes it as its own, since a new conversation after `/clear`, `/resume` or `/branch` has a new id. Each `UserPromptSubmit` records that id in `sessions.json`, so the offer resumes the conversation the user last prompted in. The id is validated as a UUID, a hook can only move the record of its own launch, which its path and secret name, and the id never reaches the page.
- **Every end cleans up.** Closing the tab, archiving the workspace, removing the project, reloading or closing the page and quitting each end the process tree as the Terminal section says. After a normal exit or a crash `claude` is already gone and Satellite ends nothing more, so a child it started that ignores the hang-up signal keeps running, after Satellite quits too. Every end then marks the session stopped, drops its secret from the listener, so its file is useless, removes its settings file and tells the page how it ended, unless that page closed it itself. A resumed launch that exits with a failure before any hook arrived, and that Satellite did not end, forgets its record, since `claude` could not find that session. The first hook is usually the first prompt, so a resumed session that crashes before one forgets its record too. Without a listener no hook can arrive, so such a launch reads as stopped unexpectedly and keeps its record. Declining the trust question makes Claude Code exit with a failure before any hook, so a new session reads as stopped unexpectedly under Claude Code's own explanation. A process that does not report its exit within a second of its tree being ended is cleaned up anyway. When Satellite itself crashes or is force-quit, no end runs. Only the closed pseudo terminal ends `claude`, through the hang-up on macOS and Linux and ConPTY's close on Windows, and anything it started in a process group of its own keeps running with no record, so the Processes view can no longer list it. The next launch sweeps only the settings files left behind.
- **The listener outlives every launch.** Anyone who answers on the hook port receives that launch's secret and can answer with a decision Claude Code acts on, so the listener stops only after every `claude` it configured has exited, and a process that cannot be ended keeps it running. At quit it stops after every terminal has ended, or the quit's bound runs out first and the exit of Satellite closes it. A process that escapes the kill, by leaving the process group and losing its parent, outlives Satellite, and once Satellite exits another local account could take the freed port and answer that process's hooks.
- **What a hostile local process can do.** Another account can find the port but not the secret, which sits in a `0600` file in a `0700` folder, and each guess is 256 bits. A web page cannot send the request, because the header and content type force a preflight that is refused, and DNS rebinding fails the host check. Another account can also open the listener's 64 connections and hold each one until its time limit, again and again, so real hooks are turned away and every session stays idle. A process running as the user, the agent included, can read every running launch's settings file and post as any of them, so it can make any session's status lie or set the session id any of their workspaces resumes, and nothing else through the listener. Such a process can already do anything the user can.

## Inbox and notifications

`src/renderer/inbox/` draws the inbox, `src/main/inbox/` decides when to notify and with which words, and `src/main/platform/system-notices.ts` is the only file that touches the system's notifications, the app icon count and the Windows app identity.

- **Derived, never stored.** Nothing about the inbox is saved. The page builds its rows from the statuses `sessions.status` already brings, one row per listed workspace with a session whose status is `needs-you`, newest first by when the workspace started needing the user, counted by a number that lives for the page load and never by a clock. The background process builds the same set from its own session states and hands every change to the controller in `notices.ts`. Both sides decide needing with `needsYou` from `src/shared/needs-you.ts`, the background process also leaving out sessions that ended and the page leaving out workspaces it no longer lists, and the `inbox` journey compares the inbox's count with the app icon count at every step, so a drift between the two sides fails there. A pull request is a second reason, and the background process is its one source. Whenever the set changes, and when a reloaded page first asks about a workspace, it sends each page `pullRequests.needing` with that page's workspaces whose last answer for an open pull request that is not a draft carries a need (a failed check, requested changes on the head commit or conflicts), the same set that counts toward the app icon and notifications, so its own slow sweep while the window is hidden reaches the inbox too. A need leaves the moment a later answer carries none, a transient failure keeps the last answer unless the read found the workspace on another branch, so a rate limit or a branch that could not be read keeps it, and a branch switch lets the old pull request and its needs go even when the read fails. The tab keeps showing the last answer through a transient failure the same way, by the branch the sidebar lists. The two kinds of reason share one counter, `nextNeed()`, so rows sort by when each began, and a workspace with both is one row led by the older. A reason ends with its session or its need and every one ends with its page load, so nothing is worth keeping. The page's rows can trail the app icon count by the 100 millisecond status gap.
- **Who decides.** The background process derives the workspaces that need the user from its own sessions, one entry per workspace with a session whose status is `needs-you`, the same rule the page's inbox uses, joined by the workspaces whose pull request needs the user, the sessions first so a workspace that already needs the user for a session gets no second notification and the pull request ones second. A workspace entering that set while notifications are on and the window is not in front gets one notification, and none more while it stays there, however many sessions or agents ask inside it. The window is in front when it is visible, not minimised and focused. A need that begins while it is in front is never announced later, and the window taking focus drops every notification still waiting. At most one notification is shown every 5 seconds, and the workspaces that enter during the gap come as one when it ends, naming the workspace for one, and for several the count of every workspace that needs the user at that moment, since it replaces the one before, while a workspace answered in the meantime drops out. A notification's words are Satellite's fixed sentences, for a pull request `The pull request needs you in <project>.` or for the main workspace `The pull request in the main workspace needs you.` with no number, title or anything else the pull request says, with the workspace name and the project folder name, plus its parent folder's name when another project's name reads the same once cleaned and normalised, as the inbox row shows it, and the user's home folder reads as your home folder wherever it is a project or a project's parent, recognised by its path or its real path, resolved once per run, and in any letter case on macOS and Windows, so its own name never reaches a notification or a row, each reduced to letters, marks, digits, spaces and `._+()-` and cut to 32 characters, 16 for the parent, without splitting a letter, a name with no letter or digit left becoming a plain fallback, so no markup, control or direction character and nothing a session wrote reaches the system.
- **The system calls.** `Notification.isSupported()` guards every notification. A system without support, a denied permission or a refused show, which macOS reports for an unsigned app, is logged once per run, never retried and never throws, and the inbox and the count keep working. Showing a notification closes the one before, a notification closes once every workspace it named or counted was answered, turning notifications off closes the one shown, and quitting stops the controller before the terminals end, for good, so nothing saved afterwards turns it back on, and ending the terminals closes what is still shown and sets the count to zero. The count is the inbox's size, clamped to 0 to 4200 in the platform module, the most workspaces 200 projects can hold, so it never caps below the inbox, set only when it changes and cleared at start on Linux. On Windows Satellite sets the app identity `app.satellite.desktop`, the `appId` electron-builder writes into the installer's shortcuts, which notifications need. It changes neither the data folder nor the single instance lock, which follow the user data folder.
- **What each system needs.** On macOS a notification needs an app the system accepts as signed and the user's permission, and the release is ad-hoc signed, so a release build may show none. The Dock count needs that permission too. On Windows a notification needs the Start Menu shortcut the installer makes, which carries the app identity, so a development run shows none, a click on a notification that already moved into the notification centre may do nothing, and the taskbar shows no count. On Linux a notification needs a server that follows the Desktop Notifications Specification, and the count shows only on launchers that support it and never for the AppImage, which installs no desktop file. A denied or refused notification is never retried and never explained, because the system's own setting is the user's answer. A right-to-left name displays right to left, since no direction mark may reach the text to isolate it.
- **A click.** It is input from outside the app. It restores, shows and focuses the window and sends `notices.open` with the workspace a single notification named while it still needs the user, and otherwise the newest workspace that needs the user, to the page that owns its asking session. It never types or submits, and the terminal that takes focus drops held keys like any other.
- **What a page running hostile script can do.** It cannot raise a notification directly, set the count or move focus, because no channel does any of those. A notification's words are Satellite's own sentences plus a workspace name and a project name, so a page can still put characters it chose into one, by creating a workspace whose name it picks within the name rule, lowercase letters, digits and hyphens, of which the first 32 reach the title, or by adding an existing repository by its path, which picks the folder name the body shows, and nothing else. That is less than it can already do by typing into a session. It can drive a session into asking again and again through `terminal.write`, which it can already do, and gets at most one notification every 5 seconds and a count of at most 16 from sessions, since it cannot make a pull request need the user. It can turn notifications off or on through `interface.save`. A process running as the user that forges hooks gets the same bounded notifications.
- **Verification.** When `SATELLITE_VERIFY_NOTICES` holds an absolute path and the live driver check passes at the first call, every notification, close and count is appended to that file as a JSON line instead of reaching the system, starting with a count of 0 at every launch so a journey can tell the recorder answers before anything could notify, and quitting waits within its bound for the lines the ended sessions wrote, and the window always counts as not in front, so no run ever raises a real notification or count and every system gives the same answer.

## Changes

The Changes view reads what a workspace changed. Everything runs in the background process, `src/main/changes/`, and the page only ever asks for a list or for one file of that list.

- **Reads.** A list runs `rev-parse --verify --quiet HEAD^{commit}`, `branch --show-current`, the base lookup (`remote`, `symbolic-ref --quiet refs/remotes/<remote>/HEAD` and `rev-parse --verify --quiet <ref>^{commit}`, with `branch --show-current` in the main folder when there is no remote default), the tracking reads the sidebar uses, `merge-base <head> <base>` for Branch, then together `git -c diff.autoRefreshIndex=false diff --raw --numstat -z -M --no-abbrev --no-ext-diff --no-textconv --no-color --no-relative --ignore-submodules=dirty <commit> --`, `ls-files --others --exclude-standard -z` and `ls-files --unmerged -z`, so a file in the middle of a merge lists as `U`. A modified file that git lists as binary with no content name yet, which is what a file only touched looks like, is hashed with `hash-object --no-filters -- <path>`, never `-w`, only to compare the hash with the committed one and drop the file from the list when its bytes did not change, for at most 50 files and 32 MiB a list. A file read runs `rev-parse --show-object-format`, `cat-file -s <object>` and `cat-file blob <object>`. Every one of them, and the sidebar's tracking reads, the `remote` read, the cached default lookup and the trial merge's object folder lookup, sets `GIT_NO_LAZY_FETCH=1`, so a partial clone never reaches its remote, which works from git 2.45 and is ignored before it, where a partial clone can still reach the remote its config names. A list answers `not-local` only when git says it could not fetch an object from the promisor remote, or prints that lazy fetching is disabled and then that it is unable to read an object, any other failure stays `failed`, and a committed side whose object git cannot find answers `not-local`. `--no-optional-locks` does not stop `git diff` from refreshing and writing the index, which would run the repository's `post-index-change` hook, so `diff.autoRefreshIndex=false` is what keeps the index and that hook alone. Core fsmonitor is off, and external diff drivers and text conversion are off, and `hash-object` and `cat-file` never get `--filters` or `--textconv`. The git versions are 2.31 for every read, 2.38 for the conflict check, which has no safe fallback and says so, and 2.45 for the no-fetch switch, which an older git ignores. The diff can still run the clean or process filter a repository's own config and attributes name on a file whose stat changed, exactly as `git status` can (Projects, Reads), so a hostile `.git` folder is outside what the flags can close, and one that sets `core.worktree` or is a `.git` file naming another repository can aim a list at files or objects outside the workspace, which shows as line counts or text of what that folder holds, and in git's own words inspecting a clone is safe while running commands in an untrusted `.git` folder is not. No other read starts a program the repository chose. The user's own global and system config applies to the list and file reads, since it carries what the user sees, and a program it defines can start when a repository's attributes select it. A repository owned by another user is refused by git and shows as unreadable, and `safe.directory` and `safe.bareRepository` are read only from protected config, so Satellite never sets them. A git parser fault on hostile objects stays outside what flags remove. A variable the user exports, such as an external diff or a pager, is the user's own and is not scrubbed.
- **Conflicts with the base.** When the base has moved past the merge base of the branch and the base (a merge base other than the base itself), the list also asks `conflict-check.ts`, outside the four read slots, for a trial merge of the two commits. It makes `<home>/quarantine/<uuid>`, a bare repository holding a `HEAD`, empty `objects` and `refs`, and a `config` only for a sha256 repository, and runs `git --git-dir <scratch> merge-tree --write-tree --name-only --no-messages -z <head> <base>` in it, addressed explicitly so no rule about bare repositories can refuse it and git never looks for a parent repository, with `GIT_ALTERNATE_OBJECT_DIRECTORIES` naming the repository's object folder, so git reads the commits from the repository and writes every new object into the scratch folder. `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` name an empty file inside the scratch folder for this run alone, since no null device path means the same on every system, so it reads none of the user's config either, runs no driver the user defined and cannot be aborted by a global merge setting, and its answer can differ from the user's real merge in a repository that sets `merge.renormalize` or `core.autocrlf` locally. Having no remote and none of the repository's config, the trial needs no `GIT_NO_LAZY_FETCH`, which every other read of the list, the base and the tracking sets. The repository's config, its `.gitattributes`, its `.git/info/attributes`, its hooks and any remote it names are never read, so no merge driver, filter, text conversion, external diff, hook, credential or ask-pass helper, pager, editor or network call can start (`--attr-source` alone does not close this, since git still reads `.git/info/attributes` and `core.attributesFile`, which a test shows). The folder is removed when the check ends for any reason, and the first check of a run removes `<home>/quarantine` whole, never following a link, so a crash leaves nothing for long. Only the names git prints for conflicted files are read, `-z` separated, at most 1,000,000 counted and 5 sent, and every conflict kind (content, add and add, rename and rename, delete and edit, folder against file, binary, submodule, type) is a name on that list. A shallow clone's own `shallow` file is copied into the scratch folder, bounded to 1 MiB with every line an object name, so git stops where the repository's history was cut, and one that cannot be copied, like a repository whose path holds the list separator, answers `unchecked` and the banner says it cannot check. Histories with no common commit, a name that is not a commit of the repository's hash length, a failed read and a branch already merged say nothing. One check runs at a time across the app, under 15 seconds, stopped with the list and at quit, and its answer is kept for the pair of commit names, so a huge merge is tried once, except a failed or timed out one, which is tried again after 30 seconds. A git older than 2.38, which has no `merge-tree --write-tree`, answers the trial with a usage error, which answers `old-git` for 10 minutes before the next list tries once more, so an upgraded git is found, a check that ran out of time answers `slow`, and the Branch view says each in one sentence and never claims there is no conflict.
- **The worktree side.** A path is read only when git's own rule for it holds, no empty, `.` or `..` segment, no `.git` in any case or with the characters macOS ignores in names, nothing absolute, no Windows short name. Every folder on the way is checked with `lstat` from the worktree root down, so no link or junction is ever followed, not even to resolve a path, and the real path of its parent folder must then equal the worktree's real path joined with that parent. The file itself is opened without following a link, without blocking and without becoming a terminal, must be the regular file its `lstat` named and must not change while it is read. A link shows its target text and a pipe or device is never opened. A local process that can already read a file could get it shown once by swapping a parent folder for a link and back between the check and the open, since Node has no `openat` to pin the folder. A hard link inside the worktree to a file outside is read like any other file, since git never makes one and only a process that could read that file itself can.
- **Ownership.** Reads belong to the page that asked. A list for a workspace, view and base already running shares its answer, a running list of the page for the same view with another workspace or base stops first while a list of the other view runs on beside it, and a new file read stops the page's older one, each answering `refused` with a sentence the page never shows. Past that the archive goes ahead. A read still waiting then holds no git, since stopping killed it, only a file call on a stalled drive, and its answer is dropped, so the worst it does is keep one file open, which Windows cannot delete until the drive answers. A stopped read kills its git and starts nothing more, no further line count, stamp or tracking read.
- **Bounds.** Four reads run at once across the app and up to 16 wait, a waiting read that is stopped leaves the queue at once, and the sidebar's own reads have their own slots, so changes never starve it. The diff, the untracked list, the unmerged list and each `hash-object` of the touched pass have 15 seconds each, and every other read 5, the stamps of one list 5 in total. The touched pass hashes up to 50 files and each untracked file is counted with up to 5 seconds, up to 200 of them, one after another, so no list has one bound of its own, and on a drive that is slow but answers one list can hold its read slot for minutes. Output past 16 MiB answers `too-many`, and a list whose git ran out of time, or found git still stuck in that folder, answers `hung`. Each page caches at most its last 8 lists and about 8 million characters of paths, the oldest dropped first.
- **Names the reader refuses.** A name git lists but Satellite will not read, a backslash, a Windows short name or text that is not UTF-8, stays in the list with its own letter and a stamp ending `refused`, and its file answers `unreadable`. Names that are not UTF-8 and decode to the same text list as one row and count the rest in `more`. An unmerged file is never dropped by the touched file check, and an untracked link lists as an added file showing its target text, where only a tracked link or mode change gets its own sentence.
- **Names.** A file, branch or base name draws through `VisibleName` in `src/renderer/ui/`, its revealed characters in the diff's dashed style, so a name holding `[U+202E]` typed literally never reads as one holding the character, and each letter of another script inside a Latin word outlined. Where a name can only be plain text, in the switcher and the new workspace dialog's list, `visibleLabel` adds "(look-alike letters)" instead. The folder part of a listed path gives way from its start, so the nearest folder and the whole file name stay in view. Names written wholly in look-alike letters, such as a Cyrillic `соре`, are outlined in the diff and not in the list, the banner or the header, which mark only a letter of another script inside a Latin word. Two names that differ only in composed against decomposed letters, or in digits the bidirectional algorithm reorders around a right-to-left letter, still draw alike, and their tooltip and accessible name hold the full path.
- **Focus.** The list is a `listbox` of `option` rows, and the arrows, Home and End move the selection with focus. A refresh never moves focus. When the element holding focus inside the view goes away, a layout control that a one-sided file hides or a row that left, focus moves to the selected row, or to the panel when nothing is listed, which then takes focus itself.
- **The bar.** The tab strip, `from <base>` in the Branch view, `Send lines`, the view switch and the layout control sit in one bar that wraps instead of clipping or hiding anything, down to the 960 pixel window. When the controls do not fit beside the tab they move to a second row as a group, right aligned, and inside it the layout control wraps first, then the view switch, then `Send lines`. The base, which the header drops in a narrow window, has a minimum width of 14 characters and wraps with the rest, so at 960 and 1024 pixels the bar takes two rows and elsewhere one, and the Uncommitted view keeps the base's place unseen, so the bar's height does not change with the view. `Send lines` stays and is disabled while no text diff shows. The layout control exists only while a text diff has room for two sides, so the bar never reserves a place for it, and it never changes height with the selected file. Every control also has its command in the command menu.
- **Conflict banner.** A grey `bg-side` strip under the bar, in a polite live region that takes no space while it has nothing to say and at least 36 pixels while it shows, so a base that moved pushes the content down by one strip and nothing is ever left empty. Its sentence and its button wrap onto a second line in a narrow column, the files give way with an ellipsis, and the button never clips. It names the base, the count and up to five files through `VisibleName`, and `Send to Claude Code` types `Update this branch from <base> and resolve the conflicts.` into the prompt without submitting, naming the base only when it holds no space, quote or hidden character.
- **Line reference.** `Send lines`, or Cmd+L on macOS and Ctrl+Shift+L elsewhere, while a text diff shows, types Satellite's own sentence into the prompt through Send to Claude Code, `Lines 12 to 18 of src/app.ts in this workspace. `, `Line 3 of ...` for one, and for the committed side `as of the last commit` in Uncommitted or `at the merge base with <base>` in Branch, naming the old path of a renamed file. Only line numbers and the path are sent, never a file's content. The numbers are the file's own lines on the side the selection sits in, one side only, the focused one side by side and the modified one inline, a selection ending at the start of a line leaves that line out, and a caret with nothing selected names no line, so the file's own last line is the most it can name. Removed lines drawn inline sit in view zones that cannot be selected, so inline only modified lines are referenced, and an added file always names the modified side and a deleted one the original. Nothing selected, or no text diff, says so in a toast or leaves the command out of the command menu. The path goes in quotes as dropped paths do. A path that holds any character the diff would write out as `[U+XXXX]`, hidden, blank or written like one, or that holds an `@` anywhere but directly after a letter, a digit or `/`, which Claude Code could read as a file mention, is refused with a sentence, and a base name like that falls back to the wording without it. A reference over 800 characters, the path too long to fit with the sentence, is refused with another, so neither is cut into a name of another file, and a test proves the text is never changed by the cleaner. It follows every rule of Send to Claude Code, the shown session of this workspace, only after its first reported request, never submitted, focus as that rule says, and the page chooses nothing but the text. A file name is words an agent will read, so a hostile name can still try to instruct the agent in plain language. The user sees exactly what was typed before they press Enter, and Satellite never submits. The shortcut acts only with focus in the diff, where the command registry takes it before Monaco sees it and Monaco's own Cmd+L is not bundled. With focus anywhere else, the terminal included, it goes on to that element, so Claude Code keeps Ctrl+L, which a terminal cannot tell from Ctrl+Shift+L, and the button and the command menu send from anywhere. No menu item of the app and no key Satellite already takes uses it.
- **Refresh.** No file watcher. The schedule lives in `src/renderer/ui/refresh-schedule.ts` and `useChanges` in `src/renderer/changes/`, `useFiles` in `src/renderer/files/` and `useProjects` in `src/renderer/projects/` run on it. `useChanges` asks for the shown list again after each answer, at most one list in flight per view, while the document is visible. The wait is four times as long as the last list took, at least 2 seconds and at most 30, and each answer in a row that holds no file list or that equals the one before doubles it from 2 seconds (2, 4, 8, 16 then 30), so a slow, failing or idle repository is asked every 30 seconds at worst. A changed list, returning visible, the window taking focus and a session in the workspace turning done reset that doubling, the last three asking at once, and switching the shown file resets it to the 2 second floor, and a hidden window, another workspace or view, or another centre view stops the timer at once. An idle visible tab on a small repository runs 2 lists a minute once it has settled, 10 git commands each, and a hidden one none. One list shares its `git remote` read between the base and the tracking counts and remembers the merge base of a head and base pair. A list equal to the one shown keeps the shown one, so nothing redraws, and a list that hung or failed keeps the last good list on screen with its sentence until a list answers again. The shown file is read again when its stamp changes (its size, modification time and change time, so a rewrite that restores the modification time still changes it, since no process can set the change time back, and only a file system that has none goes unseen), and its model is replaced only when its text did. A file answer that changed while read, hung or failed is never cached and is asked again after 2 seconds, doubling up to 30, once the window is visible. While a newly selected file is read, the previous file's diff stays dimmed and marked busy, so it never reads as the selected one.
- **What a page running hostile script can do.** Read the changed and untracked files, not ignored, of any workspace Satellite lists, and since `projects.drop` takes any path, of any repository on disk it adds first, a home folder kept in git included, and their committed versions, each side at most 1 MiB, which the user's own agent already reads and the same page could read through `terminal.write` and Claude Code's shell. Learn the size, modification time and change time of those files through the stamps. A stamp walks every folder above the file with `lstat` before and after it reads the file's own, one file after another under one 5 second limit for the whole list, so a file below a link or junction stamps as gone. A local process that can already read the file could still get its size and time stamped by swapping a folder for a link and back between those two walks, the same window a read has. A pass that runs out of time stops after the call in flight and marks the worktree stuck like a hung read, so no later list or read starts another call there until that call answers. Keep four git reads busy, fewer than typing into Claude Code can. It cannot name another path, an object, a ref, a git argument or a program, cannot reach `.git`, a folder outside the worktree or a workspace that is not on record, and writes nothing anywhere.

## Diff

The Changes tab shows a read-only diff of two texts with Monaco's diff editor, `DiffView` in `src/renderer/diff/`. It is its own chunk, loaded the first time a diff shows, so the window's start never pays for the editor. An added or deleted file shows its one side in a plain read-only editor, `SideView`, every line marked added or removed, with no empty side opposite. Given no side it is the plain file view of the Files tab, with no side mark, the same hidden character and look-alike marks on every line, and the test id `file-text` in place of `diff`. The options that keep every editor read only live in `read-only-options.ts`, which a test pins. Both load together, and until they have, the pane says the diff is opening. If they cannot load, an error boundary says so in one sentence and the rest of the window stays. It takes the two texts, the file's path, inline or side by side and the two sides' accessible labels, and hands its owner the selected lines and their side.

- **Only what a read-only diff needs.** The interface imports `monaco-editor/editor/editor.api`, its codicon styles, the diff editor's own contribution, which brings the accessible diff viewer on F7 and Shift+F7, and the language registrations. Monaco's unicode highlighter is not imported, because its boxes switch off past 1000 results. No hover, link, context menu, code action, suggestion, go to, find, clipboard menu, drag and drop or command palette is imported, and the options turn links, the context menu, dragging and dropping off as well, so nothing in a file can become markup, a link, a command or a hover. The bundle carries none of those actions. Copy works through the browser's own copy of the selection.
- **Languages load when used.** Each language registers only its name, extensions and file names, and its Monarch tokenizer is its own chunk that loads the first time a model of that language is made. A file's language is the first whose file names hold its name or whose extensions hold its lowercased extension, else plain text. No language service or language worker runs, so nothing evaluates a string, and the tokenizers build their patterns with `RegExp`, which `script-src 'self'` allows.
- **The worker.** The editor worker, which computes the diff, is bundled by Vite as its own file and served from `app://satellite` like every other asset, so it loads under the production policy's `worker-src 'self'` with no fallback to the main thread.
- **Read only.** Both sides are read only, the DOM included, and the revert gutter menu is off, so the diff can show changes but never make them. Revert Block and Revert Selection need a writable side, so they never show.
- **Hidden characters show.** A side whose bytes are not UTF-8 is never decoded, both readers answer `not-utf8` and the pane shows one sentence, so two different byte sequences never read as the same text. Before a text becomes a model, `revealLines` writes every default ignorable code point, every control, format, surrogate, separator and space other than the plain space, and the blank braille, object replacement and the few unassigned characters Monaco lists as invisible, as `[U+XXXX]`, the same set and the same kept joiners as names, taken from Unicode properties rather than a hand list and swept over every code point by a test, and a carriage return as `␍`, while a `␍` written in the file reads `[U+240D]` and a `[` that opens what would read as an escape, such as the `[` of a literal `[U+200B]`, reads `[U+005B]`, so no two different texts reveal to the same text. A variation selector or joiner that changes nothing, after an emoji that already draws as one, is kept and draws alike, and its line still shows as changed. On changed lines, and every line of a one-sided file, each revealed run draws dim inside a dashed outline, up to 10,000 runs a side, so a revealed character never reads as the same text typed into the file. Only `\n` breaks a line and a tab stays a tab, so the diff's lines are git's lines, a change of line endings or of a byte order mark is a changed line, and nothing depends on how many such characters a file holds. On every changed line, and on every line of a one-sided file, the app outlines each look-alike character Monaco's own confusable table knows for no locale, taken from `monaco-editor/base/common/strings`, which the package exports but does not document, so a test imports it and a Monaco upgrade that moves it fails the check. It follows Monaco's rule, so a whole word of look-alikes in another script such as `соре`, a Latin look-alike such as `ɡ` or `ı`, a fullwidth letter, the Greek question mark and foreign digits are marked, while a word that holds a letter with no Latin twin, an ordinary Russian or Greek word, is not. Every letter of another script inside a word that also holds Latin letters is marked as well. There is no cap, the work is bounded by the changed lines, and unchanged lines carry no marks, since they did not change. Inline, removed lines draw in Monaco's view zones, which carry no marks, so a removed line's marks show side by side only, and the marks are visual, so a screen reader hears the characters but not that they were marked. Where git itself turns `\r\n` into `\n` on commit, through `core.autocrlf` or a `text` attribute, the worktree side is compared the way git stores it, so a checkout with conversion on shows only real changes. `git ls-files --eol` decides per file from the index, the attributes and the bytes on disk, and a file git would not convert, one with a lone carriage return, one marked `-text` or one whose committed text already holds `\r\n`, shows its bytes as they are. Whitespace changes at a line's ends count as changes. Unchanged regions longer than three lines fold away with three lines of context, opened twenty lines at a time.
- **Side by side or inline.** The owner chooses the layout, side by side or inline, but a pane under 700 pixels wide draws inline whatever was chosen, because two sides in that space are clipped, and the layout control shows only where the pane is wide enough to use it. Monaco's own switch at a narrow width stays off, so the change happens only by that one rule, and a side by side diff that has room keeps the choice. A diff that takes over 5 seconds marks the rest of the range changed. A change far to the right of a long line can sit off screen until the diff is scrolled sideways, since lines do not wrap and the sentence shows only past 10,000 characters. A line draws its first 10,000 characters, and when a changed line runs longer one sentence above the diff says only its start shows.
- **Keyboard.** Tab moves focus out of the diff instead of typing a tab, the app's shortcuts reach it because the command registry listens first, and F7 opens the accessible diff viewer for a screen reader. Each side carries its label, Before and After with the file's path.
- **Theme.** The `satellite` theme reads the app tokens and inherits no rules from Monaco's own themes. The colours it names come from tokens, and anything it leaves out, such as the folded region bars and the accessible viewer, takes Monaco's defaults for a light or dark theme. `bg`, `fg`, `dim`, `add` and `del` for lines, `addfg` and `delfg` at low alpha for changed words, `ctl` for scrollbars, `line` for the fill where a side has no line, `sel` for selection, `sigfg` for the look-alike outline, set off from a changed word's fill by a ring of `bg`, `dim` for the dashed outline of revealed characters and `accent` for the focus border. Syntax keeps colour for state, keywords in `fg` bold, types in `fg`, strings, numbers and patterns in `fg2` and comments in `dim` italic, and brackets are not coloured by pair, an option each model carries. It is rebuilt on every colour scheme change. Each token goes through a canvas to come back as six digit hex, because the built stylesheet shortens colours like `#ffffff` to `#fff` and Monaco accepts only the long form.
- **Thread marks.** The pull request's Files section hands the diff a list of lines, each marked open or resolved, and a callback. The modified side draws them in its glyph margin only, a click there names the line, and a handle can scroll one into view, so review threads never put Markdown inside the editor. Side by side the original side has no glyph margin, so only threads on the new side mark. Unchanged regions stay unfolded only while the list holds a mark.
- **Models.** Each text becomes a model of the file's language, replaced when the texts change and disposed with the old ones and with the editor. A new text for the same path keeps the scroll, the selection and the opened regions, restored once the new diff is computed.

## Files

The Files tab shows a workspace's folder as it is on disk and opens files read only. Everything runs in the background process, `src/main/files/`, on the confined reader of Changes (`src/main/changes/file-sides.ts`), the git helper and a read queue of its own. The page asks for the entries of up to 16 folders, for one file by its path or for names, and never names an absolute path, an option or a program.

- **The path rule.** A path from the page is read only after five steps. The name rule `isChangePath` refuses an empty, `.` or `..` segment, `.git` in any case or with the characters macOS ignores, anything absolute, a drive letter, a backslash, a NUL or replacement character and more than 4096 characters, and on Windows a short name, a device name, a colon and a trailing dot or space. Every folder on the way is then checked with `lstat` from the workspace root down, so no link or junction is ever followed. The real path of the parent must equal the root's real path joined with it. The file is opened without following a link, without blocking and without becoming a terminal, and must be the regular file its `lstat` named. After the read the parent folder is resolved again and must still be the same folder. A link is never followed and shows its target as text, and a pipe, socket or device is never opened. The same folder check refuses the Satellite home and everything inside it, unless the workspace's own folder is inside it as a worktree is, so a project that contains the home, as a home folder kept in git does, never lists or reads Satellite's state files or the hook secrets in its session settings. Changes reads through the same check, and its stamps do too, so such a project's list of changes still names the state files git reports, with no size, time or content.
- **What it lists.** A listing is a plain `opendir` of one confined folder, so it costs that folder's entries whatever the repository's size. It scans at most 5000 entries, answers `too-many` past that with no count, and lists every file, folder and link, dot files and ignored ones included, with a repository of its own marked as such. Only `.git` and a name the name rule refuses, a backslash, a replacement character or more than 255 characters, are left out, the second kind counted in `more`. Pipes, sockets and devices are left out. Folders sort first, then files, each by code unit, at most 1000 entries per folder and the rest counted in `more`. A folder that is gone answers `missing`, one reached through a link or that cannot be opened `unreadable`, and a call that outlasts 5 seconds `hung`, which marks the workspace stuck for every Changes and Files read until it settles. The confinement is checked before the scan and again after it.
- **Ignored entries, listed and readable.** Satellite shows what is on disk, so an ignored entry is dimmed and never hidden, and `files.read` does not ask git. The flag comes from one `git check-ignore -z --stdin` run for every folder of a call, paths relative to the workspace root and sent as NUL separated standard input, in runs of at most 5000 paths with 2 seconds each. In its default mode it reports a path only when git's rules ignore it and it is not tracked, so a tracked file that matches a pattern is never dimmed, and a path under an ignored folder is dimmed because git reports each full path. The flag only dims, so every doubt shows the entry plain. A run that fails, hangs or prints a path it was not asked for, a run of more than 5000 paths and an empty or NUL path all leave its entries plain, and so does a repository git cannot read. A path inside a submodule makes git fail that run with a fatal error, so a run that fails is repeated once per folder, and only the folder that fails shows plain. A run that hangs ends the checks of that call, so a blocking ignore file costs one bound and not one per chunk. A name that starts with `:` is sent as `./name` so git reads it literally. A compromised page can therefore list and read any file inside a recorded workspace's folder except `.git`, ignored files included, and learn their names, kinds, sizes and times, and since `projects.drop` takes any path, it can first record any repository on disk. Claude Code, which that page can already type into, reads the same files.
- **Open by name.** One `git ls-files -z --cached --others --exclude-standard` lists tracked files and untracked files git does not ignore, so a dependency folder never floods the search. It has 15 seconds, answers `too-many` past 200,000 names or 16 MiB of output, dedupes with a `Set`, drops a nested repository's `dir/` line and every name that fails the name rule, and is kept 5 seconds per page and folder. The ranking runs in the background process in turns of 2000 names with the shared fuzzy matcher and a bounded top 50, a match in the file's own name outranking one that needs its folders, and stops when its read is replaced. Of the 50 best, every name whose folders the reader would refuse or that is not in the workspace folder is dropped and the next best take its place, which keeps a Windows junction's files out and every name git lists from somewhere else, as a `core.worktree` or a `.git` file pointing at another repository makes it do. Git's own view follows the repository's administrative files, so the Changes list reads the same redirected view, a limit older than Files. The finder draws each result's name and folder through `visibleText`, the folder giving way from its start so the nearest folders stay readable, with the full path in the tooltip and the accessible name, and a newer query always wins over an older answer.
- **Git runs.** Both go through `gitArgs`, so `--no-optional-locks`, `core.fsmonitor=` and the other safe options apply, with `GIT_NO_LAZY_FETCH=1` and arguments as an array. Paths only travel on standard input and in output, so nothing from a page or a repository is ever an option or a revision. Neither command writes, a test checks that a listing leaves the sizes and times in `.git` as they were, and neither starts a program a repository chose. A test with a hostile repository, a marker program wired to fsmonitor, the pager, the editor, `core.sshCommand`, `core.gitProxy`, an external diff, textconv, clean, smudge and process filters, a credential helper and executable hooks, shows both reads start nothing while a control `git status` starts it, and a run without `core.fsmonitor=` started the fsmonitor program. These commands hash no file and show no diff, so filters, textconv, the pager and the editor have no part in them, and the safe options close the one that does. The user's own global and system config applies, which is what makes the user's global ignore file count. Two leaks stay and are small, since a page can do more through `terminal.write`. A repository's own `core.excludesFile` makes git test names against a file outside the workspace, and git 2.31, the floor, reads an ignore file that is a link as patterns, so either shows a page only whether a name matches a pattern there, as a dimmed entry or a name in the search. A global ignore file that blocks, a named pipe for instance, makes a listing show its entries plain after the 2 second bound and the name list answer `hung` after its 15, never longer.
- **Files.** `files.read` answers text up to 1 MiB and 20,000 lines, CRLF kept, and otherwise `large`, `binary` for a NUL in the first 8000 bytes, `not-utf8`, or `gone`, `changing` when the file moved while read, `hung` and `unreadable`. A stamp is the size, modification time and change time, and when the page sends the stamp it shows, the answer is the word `same` and no byte is read. A hard link inside the workspace to a file outside it reads as text, since a hard link is the same file under two names and nothing in the folder tells them apart. A local process that can write in the folder can swap a folder for a link and back between the checks before and after a read, since the check follows paths and Node has no `openat`, as in Changes.
- **Images.** PNG, JPEG, GIF and WebP, whose headers are read from the first 64 KiB, so their width and height are known before any more is read. A GIF takes the larger of its logical screen and its first image descriptor, since decoders grow the canvas to a bigger first frame, and answers `binary` when the head holds no descriptor. A JPEG whose marker scan meets anything but a known segment marker before the frame header answers `binary`, since a decoder resynchronises where a strict parser cannot follow. PNG and WebP read the canvas size their decoders enforce, a frame beyond it being refused by the decoder. An image is shown only up to 5 MiB and 50 million pixels, a larger file answers `large` without being opened and a header that claims more pixels answers `large` after only that probe, with a sentence that names both limits. A file that starts like an image but whose header is not valid, truncated or zero sized answers `binary`, and so does a JPEG whose frame header sits past the first 64 KiB. The bytes go to the page as base64 in one message of at most 6,990,508 characters, with a media type from the closed list of four names. The page builds a `data:` address from the two, which the unchanged policy allows with `img-src 'self' data:`, so no file address, remote address or other scheme is ever built. SVG is never drawn as an image, it opens as text. Only the shown tab mounts an image, so a hidden tab decodes nothing, and a decode that fails shows one sentence. An animated image plays for as long as its tab is on screen with a visible window, at the engine's own cost per frame, since Satellite sets no frame bound.
- **Icons.** Each kind of file and folder has an icon from the icon set, a dev dependency whose licence ships in `third-party-licenses.md`. Its SVG files are bundled as files, never inlined (`assetsInlineLimit` refuses `.svg`), so they load from `app://satellite` under `img-src 'self'`. One lazy chunk holds the set's own name-to-icon tables and loads with the Files tab, so the window's start pays nothing. The set adds 1253 SVG files, 1.03 MB of content that takes about 5 MB as allocated in the unpacked build, and a 390 KB chunk. A name is only ever a key into those tables, held in `Map`s so `__proto__` finds nothing, and a row draws an `<img>` of a bundled file, never markup from a name. A light variant is chosen with `prefers-color-scheme`, which follows the app's theme through `nativeTheme`.
- **Ownership and bounds.** Reads belong to the page that asked, as in Changes. One list, one read and one find run per page, a newer request of a kind stops the older and answers it `refused`, a page that goes stops all three, and archiving a workspace, removing a project and quitting stop the reads inside the folder and wait for them, at most 5 seconds. Files has a read queue of its own, four at once and 16 waiting, so a flood answers `limit` and never starves Changes. Nothing is cached on disk.
- **Saved tabs.** The open tabs of each workspace are saved in `interface.json` (State above) and loaded as untrusted data. A saved path is only a request that the path rule confines when it is read, so a forged file reads nothing a page could not ask for.
- **Refresh.** No file watcher. `useFiles` runs on the schedule `useChanges` uses (Changes, Refresh) and asks for one `files.list` of the open folders and one `files.read` of the active file with the stamp it shows, together, only while the Files tab of the shown workspace is on screen and the window is visible. It stops at once when the tab, the workspace or the window goes away, and restarts at the 2 second floor when a folder opens, a file is chosen, the window takes focus or a session turn finishes. An answer of `same` keeps the shown file, a listing equal to the shown one keeps the shown object, and a list or read that failed, hung or caught a file mid-write keeps the last good answer on screen with its sentence and is asked again on the next tick. A folder that is gone closes quietly, with the folders under it, and a file that is gone says so in its tab until the tab is closed. The Git letters come from the `changes.list` answer for Uncommitted that the page already polls, so the tree adds no probe of its own. An idle visible Files tab with six folders open runs 2 lists, 2 reads and 2 change lists a minute once settled, which is about 22 git runs, 2 ignore checks, none for the reads, which stat the file and answer `same`, and about 20 for the change lists, and a hidden window runs none. The tree's open folders, at most 16, its listings and its scroll stay in memory per workspace, at most 16 workspaces, while the other centre tab shows, and are never written to disk. An image whose stamp did not change is never sent again on a poll, while one that is rewritten on every tick is read and carried over the bridge on every tick, bounded by the schedule's 2 second floor and by the visible window. A read that is replaced or abandoned stops before it opens the file. Folders open only when the user opens them, so a relaunch brings the tabs back with a closed tree.
- **What it cannot do.** It cannot write, rename or delete anything, name an object, a ref, a program or an argument, read through a link at any level, reach `.git`, a file outside the workspace folder or a workspace that is not on record, and the finder offers no name that is not there, or keep more than one read of each kind running per page.

## Pull request

The Pull request tab shows the pull request of the workspace's branch, read through the user's own `gh`. Everything runs in the background process, `src/main/pull-request/`, and the page, `src/renderer/pull-request/`, only asks for an answer or for the failing lines of one check.

- **The runs.** A read is one `gh` run for a plain refresh of a pull request already checked and two on its first sight and for each read while the tab shows. While a stranger's pull request is the newest it is three runs, and four while the tab shows. They run one after the other, from the workspace folder. `gh pr view --json <fields> --jq <projection>` is one constant that reads the pull request of the current branch, whatever its state, and its projection drops what Satellite must not hold, every commit author's name and email above all, and keeps each review's author association. `gh api graphql --hostname <host> -f owner=<owner> -f repo=<repo> -f head=<branch> -F number=<n> -F detail=<bool> -f query=<constant>` names the signed-in account and lists the pull requests of that head branch with who opened each, and brings the reviews, the comments and the review threads only when `detail` is true, which is while the tab shows. It runs on the first sight of a pull request and whenever the tab shows, and a pull request already checked is not asked about again for a plain refresh. `gh pr view <n> --json <fields> --jq <projection>` is the same constant with one checked number, run only when the one `gh` picked was not opened by the signed-in account, an owner, a member or a collaborator. `gh api --hostname <host> repos/<owner>/<repo>/actions/jobs/<id>/logs` runs only when the user opens a failed check and prints that one job's plain log, which `gh` writes to no cache folder, so nothing is left on disk and a run that is ended halfway cannot damage the user's own `gh`. `gh-arguments.ts` builds all the runs and nothing else builds a `gh` argument for a pull request. Nothing a repository, a pull request or the page says reaches an argument except a host, an owner, a repository name, a number and a job id, each checked against a pattern and taken from the pull request's own address (`https`, no user info, port, query or hash, a host that matches the host rule, one owner, one repository and a number), the head branch, which git answered and the branch name rule checked, and one literal boolean that says whether to bring the conversation. Each connection is one page, `totalCount` says how much more is on GitHub, and no run pages, writes, comments, reviews, merges, re-runs a check or fetches.
- **The environment.** Every `gh` run goes through `toolEnvironment("gh", env)`. It drops `GH_DEBUG`, `DEBUG`, `GH_FORCE_TTY`, `CLICOLOR_FORCE`, `GH_HOST`, `GH_REPO`, `GH_PAGER`, `PAGER`, `GH_BROWSER`, `BROWSER`, `GH_EDITOR` and git's repository variables. It sets `GH_PROMPT_DISABLED`, the two update notice switches, `GH_TELEMETRY=false`, `NO_COLOR`, the prompt switches of every git run, `GIT_OPTIONAL_LOCKS=0` and one config entry that sets `core.fsmonitor` empty. The token variables and `GH_CONFIG_DIR` stay, because they are the user's sign in. `runTool` takes a `cwd` for these runs.
- **No other host, no program a repository chose.** `gh pr view` takes its host from the repository's remote and refuses a host it holds no login for before any request, so a remote naming another host answers one sentence and sends nothing. `gh api` takes its host from `--hostname`, never from the repository, so the second run always names the host of the checked address, and `-f` sends a raw string with no file or placeholder meaning. The only programs `gh pr view` starts are `git remote -v`, `git config --get-regexp`, `git symbolic-ref --quiet HEAD`, `git rev-parse --symbolic-full-name <branch>@{push}` and two `git config` reads, and the environment above leaves them no fsmonitor and no optional lock. A repository that names a program for `core.fsmonitor`, `core.pager`, `core.editor`, `core.sshCommand`, `core.gitProxy`, `credential.helper`, `diff.external`, `core.askPass`, `sequence.editor`, `gpg.program`, a pager, an upload pack or an alias starts none of them, and a test runs the real `gh` in such a repository and sees no marker. For an ssh remote `gh` also runs `ssh -G <host>` with the host from the remote's address. A host that starts with a dash reaches ssh as an option, ssh prints its usage and starts nothing, and a repository unpacked from an archive carries its own `.git/config`, so a hostile archive can name such a host. Satellite adds no rule of its own for it, because ssh starts nothing.
- **Whose pull request.** Anyone who can read a public repository can open a pull request from a branch the user pushed, and `gh pr view` answers the newest open one whoever opened it. A pull request shows only when its author is the signed-in account, which the same query names as its `viewer`, or its author's association with the repository is `OWNER`, `MEMBER` or `COLLABORATOR`, read from the head branch's list on the second run. The agent opens pull requests through the user's own `gh`, so the viewer covers the user and their agent, from a fork of a repository they have no standing in too. When the one `gh` picked is not such a pull request, the newest open one that is, else the newest merged or closed one, is read by number and shown, and when none is the tab says there is no pull request. Those are the three or four runs above, only while a stranger's pull request is the newest. A pull request opened by a bot or an app account, such as a dependency bot or a release workflow, reports `CONTRIBUTOR` to a viewer without access and so never shows. A read that cannot learn the author answers `failed` and shows nothing. A stranger's pull request never reaches the tab, the header, the inbox, a notification or a prepared request, and only the newest 100 pull requests of a head branch name, those from forks included, are listed, so a pull request that `gh` picks from further back is answered as none and a flood of strangers' pull requests can hide the real one but never replace it. Among the pull requests the list offers that may show, one whose head is in this repository is preferred to a same-named fork's. The floor stays `gh` 2.18.0, whose reviews already carry `authorAssociation`. In the same slot a read asks git for the branch, whether it is pushed, its upstream, the repository the upstream names and whether the branch is a remote's default, through the one git helper and never a fetch. A branch counts as pushed when a `refs/remotes/*/<branch>` ref or a `branch.<branch>.merge` entry exists, and a detached head or an unpushed branch answers `absent` with no `gh` run. The pull request must then belong to the workspace. A remote's default branch answers `absent` with reason `target` before any `gh` run, and so does a branch that is the base of the pull request `gh` found (a fork's `main` into the base's `main`), and the tab then says pull requests land there with no request to open one, and a pull request from the same repository shows when its head is the branch or its upstream's branch. A pull request from another repository shows only when its head is the upstream's branch and the remote the branch tracks is a repository other than the pull request's own, read from the remote's address, so another repository's same-named branch never shows and an address Satellite cannot read refuses. After the run a read asks for `HEAD`, which is how `atHead` says whether the workspace is at the pull request's last commit.
- **Pace.** The page asks and the background process paces, in `gh-pace.ts`, so a page that misbehaves cannot lean on GitHub. One serial queue runs every `gh` read of the app, 2 seconds apart on a monotonic clock, reads before logs, with 200 reads waiting at most and 4 log reads waiting with 2 per workspace, then `limit`. An answer younger than 10 seconds is reused and a read already running is joined. A read the page marks `fresh` is joined to one already running and otherwise runs again, never answered from a held answer. A workspace whose read failed is not asked again for 60 seconds, doubling to 1,800 and reset by a good read, which a read with the tab's detail and a fresh read skip, except that a signed out, missing, outdated or other host answer is reused for 10 seconds by a detail read that is not fresh. A rate limit answer pauses every `gh` run for 900 seconds and answers `rate-limited` meanwhile. A run has 20 seconds for the view and the threads and 30 for a log, and a read stopped by archive, a removed project or quit leaves the queue at once and costs no gap.
- **Refresh.** The shown workspace runs on `refresh-schedule.ts` with a first wait of 30 seconds, four times what the last read took, doubling while nothing changes and at most 300 seconds. A read is fresh, and runs at once, when the window takes focus or becomes visible, when a session of the workspace finishes a turn and when the tab first shows the detail, so a new pull request or a new sign in shows without waiting for the timer. Every other listed workspace is asked every 300 seconds, one at a time, while the window is visible, and fresh when one of its sessions finishes a turn or the workspace stops being shown. At the pace above that is at most one run every 2 seconds, which is 1,800 runs an hour for a hostile page, and 50 listed workspaces on the ordinary schedule start about 600. A run is not a point, since `gh pr view` pages a long list of reviews itself and a query costs by its connections, so what that spends of the user's hourly GitHub budget is not measured, and the same budget serves the user's own agents. The background process keeps its own slow sweep, checked every 60 seconds, that reads each workspace whose last answer was an open pull request and is older than 360 seconds, one at a time through the same queue, pause and failure hold with the same single run, so a page that is hidden, minimised or covered and asks for nothing still leaves a failed check or a conflict to raise its one notification while the user is away. While the page refreshes a workspace its answers stay younger than that and the sweep reads nothing. There is no file watcher and no webhook.
- **Nothing is stored.** The last answer of each workspace lives in the background process's memory, and the page keeps its own for one page load. Nothing about a pull request reaches a file, a log, the interface state or the Satellite home, and no token is read. The failing lines come from one job's log read through `gh api`, which writes no cache, so no job log is ever left on disk.
- **Bounds.** A title 256 characters, a name (branch, check, workflow, login) 255, an address 2,048 and `https` only with no user info, kept as the normalised address so the dialog shows the true one (and on the pull request's own host for a review, a comment or a thread), a description, review or comment 20,000 characters with `bodyCut` set when cut, the whole conversation 400,000 characters, then cut and counted, 100 checks and 100 commits with the rest counted, 50 reviews and 50 comments, the newest, 100 threads of 20 comments, 40 failing lines of 400 characters. Output past 16 MiB, or a run past its time limit, answers `hung`. Every parser reads loosely, so one odd field costs that field, and the contract repeats each bound, so an answer past one is dropped by the page. The Conversation draws its items in order until their text passes 40,000 characters, at least one, and then offers Show more for the next 40,000, and a thread draws its comments the same way, so a hostile conversation never puts hundreds of thousands of elements on the page at once. A review, a comment or a thread comment that GitHub hides keeps no text and is drawn collapsed as one sentence, with its reason when GitHub names one of abuse, duplicate, off-topic, outdated, resolved or spam.
- **Failures.** `ghFailure` reads stderr once and drops it, so no line of `gh` output reaches the page, a log or a notification. In order, `gh` missing, a stopped or oversize run (`hung`), exit 4 (`signed-out`), no pull request for the branch, a remote on a host `gh` holds no login for, one that makes `gh` ask for `GH_HOST`, or no host configuration at all, which is what a sign in held only in `GH_ENTERPRISE_TOKEN` answers, since Satellite drops `GH_HOST` (`other-host`), no remotes (`not-pushed`), an unknown JSON field or flag (`gh-old`), a sign in prompt (`signed-out`), a rate limit, a network failure (`offline`) and anything else (`failed`). The floor is `gh` 2.18.0, which adds `headRefOid`, and below it the tab says so in one sentence. A transient failure keeps the last answer on the page under a grey strip while the workspace stays on the branch it was read on, and every other failure replaces it. The log download follows GitHub's redirect to its log storage host, which GitHub chooses and no repository does.
- **The check table.** A check run that is not completed is pending, `SUCCESS` passes, `NEUTRAL` and `SKIPPED` are skipped, `FAILURE`, `TIMED_OUT`, `STARTUP_FAILURE` and `ACTION_REQUIRED` fail, and `CANCELLED` and `STALE` are cancelled. A status context passes on `SUCCESS`, fails on `FAILURE` and `ERROR` and is pending on `PENDING` and `EXPECTED`. Anything else is unknown, which shows as unknown and never alerts. Only the newest of the checks that share a workflow and a name counts, and a context counts on its own name, because the JSON has no event to tell two of them apart. The counts, failed, pending, passed (passed and skipped) and total, run over every check kept, before the cut to 100, and the list shows failed first, then pending, then the rest, each by workflow and name.
- **Needs you.** `needsOf` answers nothing unless the pull request is open and not a draft. Then it answers `checks` when a check failed, `review` when the newest deciding review of some reviewer who is an owner, a member or a collaborator (approved, changes requested or dismissed) asks for changes on the head commit, so a request from anyone else counts nowhere. The threads query asks each review, comment and thread comment for its author's association too, and one whose association is known and is none of those three, from someone other than the signed-in account, carries `outside`, which the conversation shows as a quiet outside the repository beside the name, in the dim text colour and no other. A new commit answers the review until the reviewer speaks again, and `conflicts` when GitHub says it conflicts. A merged or closed pull request keeps the tab and never needs the user. Logins serve only that rule and leave no trace.
- **Untrusted Markdown.** A description and every comment is parsed by `unified` with `remark-parse` and `remark-gfm`, turned into an element tree by `remark-rehype` and drawn by `hast-util-to-jsx-runtime`. There is no HTML string and no sanitizer. Raw HTML never becomes an element (`allowDangerousHtml` is off). After the parse each raw HTML node, an HTML comment included, turns into a code node holding its source, so the user reads everything an agent reading the comment through `gh` would read, and every element is React's. The parse runs in one worker, loaded from the app's own origin under the policy's `worker-src 'self'`, so a hostile body can be given up on. It has 500 milliseconds, then the worker is ended, the body draws as its revealed source in plain text under one sentence, and a fresh worker takes the next body. After three misses in a row the remaining bodies draw as plain text for the moment and are parsed again once nothing else waits, so a hostile flood costs about 1.7 seconds before the honest bodies draw. The sentence names the cause, too large for a body over 20,000 characters or a tree past 20,000 nodes or 64 levels, too slow for a miss, and for the moment for a body that waits behind slow ones. A link is a button with no `href`, so only an `https` address without user info opens, and only through the confirmation dialog, which shows the whole address and says it comes from the pull request, and `links.open` checks it again. An image is never an element. It is a text link, `Image <alt>`, because loading a remote image tells its host that the user opened the pull request, and `img-src` allows only the app itself and `data:` as a second layer. Text, code and image descriptions go through `revealLines` after the parse, so hidden and direction characters read as `[U+XXXX]`, and titles, names, branches, logins and headlines go through `visibleText` or `VisibleName`. A task list box is a span, a heading is drawn two levels down and a link title is never drawn. The package `decode-named-character-reference` is aliased to its plain build, since its browser build needs a `document` that a worker has none of.
- **Prepared requests and notifications.** Send to Claude Code carries a pointer and no word of a title, description, comment or check, the number, the run and job ids, which are digits, a thread's address rebuilt from checked parts, with a fixed sentence when a part is missing, and for a conflict or a missing base the base branch's name, which a writer of the repository chose, after it has no space, quote, backtick, hidden character or mention and at most 255 characters. A notification is Satellite's sentence with the cleaned workspace and project names, not even the number. A check name, a path, a comment or a title never reaches an argument, a prompt or a notification.
- **Files.** The Files section is the Branch diff of Changes with the pull request's base branch as the base, computed by git from local objects. `changes.list` and `changes.file` take the optional `base` and Branch resolves `refs/remotes/<remote>/<base>` with the remote the default lookup picks, with no fetch and no `baseRefOid`, and a base the workspace lacks answers `no-base` with a request that asks the agent to fetch it. The note above the list says the files are the workspace's against that base. A remote branch is the last one fetched, so a base that moved shows the older merge base until the next fetch, and a fork's base branch is read from the remote Satellite already picks, so a stale fork ref shows a wider diff. A thread is a mark in the diff's glyph margin and its text is in a panel beside the diff, so hostile Markdown never sits inside the editor. Marks sit only on threads on the new side that are not outdated, and only while the workspace is at the pull request's last commit and the shown file has no uncommitted change, read from a second `changes.list` of the Uncommitted view that runs only while Files shows at the head, so another file's change never turns marks off and an unreadable or cut list does, since a line number of another version would land on the wrong line. Otherwise one calm sentence says why and every thread of the file is listed in the panel, as are a thread on the old side, an outdated one and one with no line. Unchanged regions are unfolded only while the shown file has at least one mark to draw, so a mark is never hidden in a fold and a large file otherwise opens folded on its change. The panel's heading Not on a line here shows only beside marked threads. One key, Cmd+J on macOS and Ctrl+Shift+J elsewhere, goes to the next unresolved thread in file order, in this file or by changing file, and to the Conversation section for a thread with no path.
- **What a page running hostile script can do.** Ask `pullRequest.read` for any workspace Satellite lists and read the title, description, check names, reviews and comments that the user's `gh` already reads for that branch, which the user's own agent reads the same way. Since `projects.drop` takes any path, that reaches any repository on disk it adds first, with the user's token reaching only the host the user is signed in to and only for reads. Ask `pullRequest.log` for the failing lines of a job that is among the last answer's checks of that workspace. It cannot name a host, an owner, a repository, a number, an argument, an environment variable, a program or a flag, cannot make `gh` write, and cannot start more than one run in 2 seconds. It can fill the queue, so other reads then answer `limit`, and can trigger a rate limit by asking at the pace above, which pauses pull requests for 15 minutes. Nothing a pull request says can run a command, read a file, load a resource or reach a prompt unseen.
- **Known limits.** `gh` runs `ssh -G` as above. A signed out `gh` is run again at most every 10 seconds by the tab's reads. A rate limit pauses every workspace, not one. A hidden window asks for nothing, so the background process reads on its own, as Refresh above says, and a pull request that starts failing while Satellite is hidden reaches the notification within about seven minutes. A check with no job on this host, a status context or a foreign check, has no failing lines to read here and offers its details on GitHub. A remote tracking branch of a fork workflow can differ from the pull request's base. A body or a thread over its bound is cut and says where the rest is, and a log past 16 MiB says it is too large to show and points to GitHub. `gh` 2.80.0 sends no token to the log storage host, while 2.18.0 would send an enterprise token (`GH_ENTERPRISE_TOKEN` or `GITHUB_ENTERPRISE_TOKEN`) to it, which Satellite leaves in the environment because it is the user's sign in. While a body waits for its parse it shows as plain source, so its height changes when the drawing arrives. A branch that tracks a fork whose address Satellite cannot read shows no pull request. A remote rewritten by `url.<base>.insteadOf` is read as written while `gh` reads the rewritten address, so for a pull request from another repository the two can name different repositories, which hides it or shows the user's own fork's and never one a stranger opened. A compromised page can diff the worktree against any remote-tracking branch of a repository Satellite lists and start one quarantined conflict trial per distinct base.

## Running processes

`src/main/processes/` decides what is listed and answers the two channels, and `src/renderer/processes/` draws the count and the list. Satellite reads the process table and nothing else, so it never sees an environment, a file or an output, and stores nothing.

- **The listing rule.** From each running session's own process, trusted only while its start lies near the spawn (2 seconds after to 3 before), walk the parent links. Below the first process on a path named `sh`, `bash`, `zsh`, `dash`, `fish`, `ksh`, `powershell` or `pwsh`, list what is not defunct, has a start, is at least 10 seconds old and has no listed ancestor, so a dev server shows once and its workers do not. Claude Code runs each command through a shell that is its direct child, so the program's own helpers beside that shell are never listed, and neither is a process that detached by a double fork, `nohup` or a daemon, which the dialog says. On Windows Claude Code runs commands through Git Bash or PowerShell, so `cmd` is no shell here, since `cmd /c` is how a tool server is launched there. A tool server launched through a shell script, as some plugins do on macOS and Linux, still sits below a shell, so it is listed and can be stopped, which ends it for that session.
- **Two reads.** The table that decides what is listed and signalled holds the short program name and never the command, so no process can push it past its bound. The full command is read again, cut to 2000 characters, only for the ids that will be listed, as numbers, and on Windows through an environment variable, since `-Command` joins trailing arguments into the script text. A row whose command cannot be read shows its short name. When sessions run and the table reads empty, `processes.list` answers `failed`, and the page keeps its last list and shows the sentence.
- **The one promise.** Satellite signals a process only while it descends from one of the asking page's running sessions. `processes.stop` reads a fresh table and accepts an id with its start only when that process is listed or descends from a listed one, so a shell, the session's program, a helper, a stranger and a stale start all answer `not-found`. `endSubtree` reads another table, matches the target by id and start, and signals one id at a time, never a group, never id 1 or Satellite's own, never outside the target's subtree. An unreadable table signals nothing. A stop answers success only after one more read shows nothing of that subtree left under the same id and start, and a survivor answers `failed`.
- **The window that remains.** On macOS a signal follows its table read by tens of milliseconds, and an id reused inside that gap is signalled whatever its start, which ids handed out in sequence make rare. On Linux the start ticks in `/proc/<id>/stat` are recorded right after the stop's table is read and compared again right before each signal, so the window is the same tens of milliseconds between that read and the record, and only from there to the signal is it closed. A Linux without that file refuses the stop. Older `ps` can print a start second off by one, since two listings each work the start out from the boot time, so Linux matches a start from one table against another table's within 1 second, while the signal itself is gated by the exact ticks. On Windows one constant PowerShell script, with no profile and non-interactive, takes the ids and expected starts from an environment variable, opens each process, holds its handle, compares the start to the millisecond and kills through that handle, so only a process that took the id and started in that same millisecond could be mistaken. The journeys prove the stop on Windows, and the hold on the id rests on the handle's documented behaviour.
- **What a compromised page can do.** It can ask for the list, which holds only its own sessions' processes, and name a listed process to stop. It cannot name a signal, a group, an id outside a listed tree, another page's session or Satellite, nor read a command in full or an environment. It cannot flood reads, since one read is shared for 2 seconds, none runs while no session runs, a second stop while one runs is refused and refused stops are judged on one table kept for a second. A forged row cannot appear, since `ps` prints a newline or control character in an argument as an escape and Windows rows are JSON.
- **The address rule.** A port links only for a numeric host that is exactly `0.0.0.0` or `127.0.0.1`, also mapped with `::ffff:`, which opens at `http://127.0.0.1:<port>/`, or `::1` or `::`, which opens at `http://[::1]:<port>/` when no IPv4 one qualifies, built from a parsed number, matched by the contract's pattern and opened only through `links.open` and its question. Port 80 leaves the port out, the text `checkedLink` requires. Every other bind is plain text. Ports come from the whole subtree, at most 4 per row.
- **The command text.** A courtesy and never a boundary. The home folder becomes `~` where it starts a path, in its forward slash form too, so a name passed as an argument still crosses. In the first 1000 characters, whitespace collapses and hiding is best effort. It covers the value of a name ending in `token`, `secret`, `password`, `key`, `cookie`, `auth` and kin however it is written, the user information of an address, the password of `-u` or `--user` and any run of 32 or more characters of letters, digits and `_+=-`. Other shapes, `-pSecret` among them, show. The text is cut to 200 characters and drawn through `visibleText`.
- **Refresh.** The page asks at 10 seconds, backing off to 30 while the list stays the same, only while a session runs and the window is visible, and again when a turn ends, a session starts or ends, the list opens and after a stop. A failed read keeps what was shown. While the list is open one timer redraws the ages every second with no read, and a row hidden after a stop returns when a later read still holds it.
- **Accepted limits.** A process a stopped session left behind is not listed. A table that `ps` or PowerShell cannot deliver in time keeps the last list with a sentence and refuses a stop with one. A system clock stepped more than 3 seconds back or 2 forward after a session starts moves its root out of the trusted band, and that session lists nothing until it restarts. A `busybox` `ps` lists nothing. An address that another program binds more specifically can answer in place of the listed one, and the link still goes through the question. On Windows a clock set backwards, or a child's birth, its parent's death and the reuse of its id inside one millisecond, could join a stranger to a tree. A workspace's 201st process shows as a count with no row, and a process shows up to one poll after its tenth second. The Linux and Windows reads are proven by unit tests on recorded shapes and by each system's run of the journeys.

## First-run guide

`src/renderer/guide/` holds all of it, and the only thing it stores is `guideSeen` in `interface.json` (State above). It adds no channel, event or file, and nothing about the steps a user takes is recorded or sent.

- **Two facts.** The guide reads whether any workspace other than `main` exists in any listed project and whether any session tab is open, counted across every project. `settledStep` turns them into the step, and steps never go back, so a user who is past a step never sees it.
- **Derived open state.** The guide is open while a project is listed and either `guideSeen` is false or Show the guide asked for it. A restart in the middle shows it again from the first step that applies, since it was neither finished nor closed. Removing the last project hides it without ending it, and the welcome screen never holds it. A guide asked for by the command ends for good with Done, the close control or the last project going away, and never starts by itself again for a user who has seen it.
- **Anchors.** The control a step points at carries `data-guide` with the step's name, one element per name. The layer finds it with `document.querySelector` once, holds the element and looks again only when it is disconnected or no longer carries the step's name, so product code depends on no test id.
- **Measuring.** `placeGuide` turns the control's box and the window's size into the ring, the card and the tail, since CSS anchor positioning cannot clamp the card inside the window or tell the tail where the clamp put it, and the inbox ring is a band of a row, not an element's own box. The layer measures after every render, when the window resizes or any element scrolls, when the control's size changes, when the page becomes visible again and when a mutation adds or re-marks an element with the step's name, and it sets state only when a number changed. While a card is on screen it also reads one box per animation frame to follow the control, so the card never lags a layout shift. A control that is not on screen, has no size or lies partly outside the window gives no card, no ring and no announcement, and then no frame loop runs, only those events. Nothing is measured while the window is hidden. A user who has seen the guide runs no observer, listener or timer.
- **The layer.** It is the first child of the window, fixed and over the dividers but under dialogs, the command menu and toasts, so it moves nothing in the layout. While a dialog, the command menu or the link question is open the window passes it `covered`, and the card, ring and tail hide, with no announcement repeated and no focus moved, and come back when it closes. It is first in the tab order, since the terminal keeps Tab for Claude Code.
- **Status and focus.** One `role="status"` region mounted before any text says a step once, when its own card is placed, and does not say it again when the card hides and returns. The card is a `role="group"`, not a dialog, because nothing is blocked. It never takes focus by itself. Only Show the guide moves focus into it, at that moment and never later, and a press with the mouse leaves focus where it was. The card draws the standard focus ring while it holds keyboard focus, from the keyboard only, and so do its buttons. Escape closes it only from inside, so the terminal keeps the key. When the guide ends from the keyboard while focus is in the card, focus goes back to where it came from if that still exists, else into the control or the sidebar. When it ends by a press with the mouse, or when focus is already somewhere else, focus is not moved, so the terminal can never lose it and no row draws a focus ring the user did not ask for. A dialog or the command menu opened from inside the card gives focus back to the card when it closes, while the guide is still open.

## Packaging and fuses

electron-builder packages `out/` and `package.json` into `release/` from `electron-builder.yml`, with the icon from `packaging/`. macOS gets a dmg and a zip for arm64 and x64, Windows an NSIS installer for x64, Linux an AppImage and a deb for x64. The renderer is minified. Main and preload stay readable, since they are small and their stack traces land in logs.

- **Unsigned.** macOS builds are ad-hoc signed after the fuses flip, because an arm64 Mac refuses to launch a modified binary with no signature. Windows and Linux builds carry no signature.
- **ASAR.** The app ships as `app.asar`, and Electron loads it from nowhere else. Only node-pty's native files, its builds and the macOS spawn helper, are unpacked into `app.asar.unpacked`, because they must be real files, so its JavaScript stays inside the archive under integrity validation. Smart unpacking is off, so electron-builder never unpacks a whole module by itself. node-pty is N-API, so packaging never rebuilds it. On macOS and Windows it ships its own builds, and on Linux `npm ci` compiles it on the build machine, so the Linux package links against that machine's glibc and needs a distribution at least as new as the release runner's Ubuntu 24.04. Each package carries only the node-pty build for its own platform and architecture, without node-pty's sources, tests, source maps or `node-addon-api`.
- **Licences.** Vite's `build.license` lists every package bundled into the renderer, and `scripts/third-party-licenses.ts` adds the runtime dependencies that ship outside the bundle, the fonts and Monaco's own third-party notices. The file ships as `third-party-licenses.md` in the app's resources folder and beside the installers in a release. The `app://` protocol's confinement works unchanged inside the archive, because Electron's file system reads the archive's paths like folders.
- **Fuses.** Running as Node, `NODE_OPTIONS`, the Node inspector arguments and extra `file://` privileges are off. ASAR integrity validation and loading the app only from the ASAR are on. Integrity is checked on macOS and Windows, and Linux has no such check. Cookie encryption is off, because Satellite stores no cookies and loads no remote content, and turning it on gives each build a keychain item that an ad-hoc signature, new with every build, can make macOS ask about.
- **Checksums.** `node scripts/checksums.ts <folder> <label>` writes `SHA256SUMS-<label>.txt` in `sha256sum` format for every package directly in the folder.

The release workflow, `.github/workflows/release.yml`, runs `./scripts/check` and packages on macOS, Windows and Linux at once, fails unless each of the seven fuses above reads as `electron-builder.yml` sets it in every packaged app, both macOS processors included, runs the journeys against the packaged app built for each runner's own processor and writes the checksums and the licence notices beside the packages. A failing journey uploads `verify-output/`, which the release never picks up. A pushed version tag runs it, fails at once unless the tag is `v` plus the `version` in `package.json`, and once all three pass drafts a GitHub release with the packages, one `SHA256SUMS.txt` and `third-party-licenses.md`. A push to a `platforms/` branch or a manual run, even on a tag, builds and proves without publishing, and a branch push is how the matrix runs before a merge, because a manual run only exists for workflows on the default branch. On Linux the journeys run under `xvfb`, with unprivileged user namespaces allowed so Chromium keeps its own sandbox on Ubuntu 24.04. A new push to the same branch cancels the run before it, while a tag run always finishes and installs without the shared npm cache. Every step runs in bash, Windows included.

## Decisions

| Chosen | Rejected | Why |
| --- | --- | --- |
| electron-vite | Plain Vite, the Vite plugin of Electron Forge | One config builds main, preload and renderer with hot reload, keeps runtime dependencies out of the main bundle and bundles the sandboxed preload as CommonJS. Plain Vite needs that setup built by hand, and the Forge plugin ties the build to Forge. |
| electron-builder | Electron Forge | It makes the dmg, zip, NSIS installer, AppImage and deb itself, flips the fuses and ad-hoc signs from one file. Forge has no first-party AppImage maker. |
| Stable node-pty with the spawn helper fix in postinstall | The node-pty beta that fixes the helper, forks of node-pty | A stable N-API release with builds for macOS and Windows that runs in Node and Electron alike, compiled at install on Linux. The beta is a beta, and a fork adds another party to trust in a native module. |
| xterm.js's DOM renderer | The WebGL renderer | No extra dependency, and Claude Code's own terminal guidance turns GPU acceleration off in embedded terminals because it garbles text. |
| The unicode11 addon | The graphemes addon | It gives the cell widths Claude Code expects, and the graphemes addon is experimental. |
| A driver over the Chrome DevTools Protocol, `--remote-debugging-port=0` | Playwright's `_electron.launch` | `_electron.launch` waits for the Node inspector, which the inspect arguments fuse turns off, so it could never drive the packaged app the release proves. |
| The `app://` protocol | `file://` | A standard, secure scheme with one handler that confines every path to `out/renderer` and sets the policy on every response. `file://` reaches the whole disk and has no real origin for the sender check. |
| The TypeScript compiler written in TypeScript | The native TypeScript compiler | Typed lint needs the JavaScript compiler API, which only the compiler written in TypeScript offers, and typescript-eslint supports only that one. |
| Terminal ids chosen by the interface, which subscribes before it starts | The background process buffering early output until the interface asks | Nothing is lost and nothing has to be held or bounded in between. |
| Output batching with `terminal.ack` and a paused pseudo terminal | Streaming output with no flow control | It is the only way to bound memory when a command floods the terminal. |
| Only `.exe` and `.com` on Windows | Running `.cmd` and `.bat` shims | A batch file needs a shell that re-parses its arguments, so a branch or file name could become a command. A shim install shows as missing. |
| React state | A state library | The window holds a few independent parts that each own their state, and the bridge client is the only thing they share. |
| Every link from terminal output asks first, naming the site and the full address | Opening a link whose text matches its address at once | Output can hide part of an address, and what is seen must be what opens. One more confirmation per link, the sign-in links Claude Code prints included. |
| Hooks in a settings file in the Satellite home, passed with `--settings` | The same JSON inline on the argument list, editing the user's Claude Code settings | The secret stays out of process listings and the environment, and the user's files stay untouched. The cost is a short-lived `0600` file in Satellite's own home. |
| A secret per launch in an `Authorization` header | One secret per run, none | A leaked file opens one session's status and nothing else, and it is useless once that launch ends. |
| The listener answers `204` with no body, and refuses with a bare status | Answering hook decisions, explaining refusals | Satellite only listens, so it can never approve or block anything for Claude Code, and a caller learns nothing past whether its request was well formed. |
| `UserPromptSubmit`, `PermissionRequest`, the two post-tool events, `Notification`, `Stop` and `StopFailure` | Every hook event, `PreToolUse`, `SessionStart` | Those are the events that change what the pixel shows, and Claude Code runs no HTTP hook at session start. |
| Claude Code gets the user's environment minus a deny list | An allow list | The user's own setup must reach their own `claude`, so only names that point at whatever started Satellite are dropped. |
| One instance per Satellite home | Several windows on the same home | Two apps on one home would fight over its state, and the lock also stops node-pty's forking kill helper from opening a second window. |
| Ad-hoc signing on macOS, no signature on Windows and Linux | Unsigned macOS builds, paid certificates | An arm64 Mac refuses a modified binary with no signature, and Satellite loads no remote content and holds no credentials, so nothing depends on a certificate. |
| The cookie encryption fuse off | On | Satellite stores no cookies, and an ad-hoc signature that changes with every build can make macOS ask about the keychain item. |
| A dropped folder's path read by one preload function and sent through `projects.drop` | Dropping only through the dialog, a drop handled in the background process, a preload function that sends the dropped file itself and keeps its path from the page | Electron answers a dropped file's path only in a preload, and the interface never holds Node. A preload that sent the path itself would follow Electron's advice to keep full paths from web content, but `invoke` could still send any path, so it would close nothing, and the interface loads no remote content. One narrow function that answers a string and the same repository check as the dialog keep the boundary where it was. |
| The theme through `nativeTheme.themeSource` | A data attribute on the root that switches the tokens | One setting reaches the CSS, the terminal, the diff, the native dialog and the window background. An attribute would repeat the dark tokens in CSS and give the terminal and the diff a second signal to rebuild on. |
| Plain JSON files in the Satellite home, validated on read | A database | Readable, small and enough for a list of paths and a few preferences, with no native module. |
| Shortcuts on Cmd on macOS and on Ctrl+Shift on Windows and Linux, everywhere, the terminal included | Plain Ctrl shortcuts that stay with the terminal while it has focus, Satellite taking plain Ctrl+K and Ctrl+P | On Windows and Linux plain Ctrl+K, Ctrl+P and Ctrl+O edit the line in Claude Code, which must keep every key it has, and a keyboard user must always be able to leave the terminal. A terminal cannot tell Ctrl+Shift+letter from Ctrl+letter, so Claude Code loses nothing. A terminal sends no Cmd keys, so on macOS Satellite catches a Cmd shortcut before the terminal sees it. Plain Ctrl+K, Ctrl+P and Ctrl+O do nothing outside the terminal. |
| Our own fuzzy matcher for the command menu, the switcher and the file finder, shared by both processes | A fuzzy search library | A few dozen lines rank a few hundred short titles and up to 200,000 file names, with no dependency to keep current. |
| The branch made with `git branch`, then the worktree added on it | `git worktree add -b` | A failed `add -b` leaves its new branch behind, so making and undoing each on its own is what keeps a failure from leaving anything half made. |
| `git branch --no-track` from a commit id | Letting git track the remote branch the workspace started from | A workspace's branch gets an upstream only when the agent pushes it, so until then its ahead count is its commits on no remote, never its distance from the default branch. |
| Never running `git worktree prune` | Pruning on each list | Prune also forgets the user's own worktrees on a drive that is not mounted, and git prunes on its own schedule. The drop sentence says when to run it. |
| The repository's hooks and filters run during creation | Turning them off for Satellite's git | Setup belongs to the user's hooks, and creation is `git worktree add` exactly as the user would run it in a terminal. The dialog says so before the user creates. |
| A project with workspaces cannot be removed while its folder answers | Forgetting it and leaving its worktrees behind | No worktree is orphaned in the user's `.git`. Archive first, and a project whose folder is gone still leaves the list. |
| Archive refuses unless the inspection's fingerprint still matches | Archiving whatever is there when the user confirms | The user confirms exactly what they saw, and an agent that keeps writing makes the dialog show the latest. |
| Satellite removes every link inside a worktree before git removes it | Trusting git's removal | git on Windows reads a junction as a folder and could empty what it points to. Removing the links first holds on every system for the cost of one bounded walk. |
| `git worktree list -z`, and on a git older than 2.36 newline output with nothing dropped, adopted or archived | Parsing newline output everywhere, refusing an older git outright | A path holding a newline can forge a line in newline output, and listing and making a workspace stay safe on git 2.31 to 2.35. |
| The inbox derived from session statuses on both sides | A stored inbox, a request channel that answers it | A reason ends with its session and every session ends with its page load, so nothing is worth keeping, and both processes already hold the statuses. The cost is rows that can trail the app icon count by the 100 millisecond status gap. |
| One notification when a workspace starts needing you, at most one every 5 seconds, a burst gathered into one | One notification per session or per request | Each notification closes the one before, so the latest one stands for every open need, and a burst across many workspaces never floods the system. A need may be announced up to 5 seconds late. |
| The switch as `notifications` in `interface.json`, flipped by two commands | A settings page | Satellite has no settings pages, the theme is chosen the same way, and the user's choices already live in that file. |
| Polling `changes.list` while the view is visible, backing off when nothing changes | Watching files | A recursive watch walks the tree on Linux and hits the per-user watch limit under a `node_modules`, misses changes on network drives, and sees every write git makes to its own index and refs. A timer behaves the same on three systems, at the cost of a change showing up to 30 seconds late in an idle visible tab. |
| The base is the remote's default branch as git records it locally, else the branch of the project's main folder | A base the user stores or picks | Creation starts from the same place, it needs no network and no new state, and it follows a default branch that changes upstream. A workspace made from another branch compares with the default branch. |
| The conflict check is a trial merge in a scratch bare repository under the Satellite home, with the repository's objects as alternates and none of any config | `merge-tree` in the repository, with `--attr-source` set to the empty tree, or with `--quiet` | Every simpler way ran a merge driver the repository chose or wrote objects into it, which a test shows, so reading must never do either. The cost is a trial that can differ from a real merge in a repository that sets merge options locally. |
| Line references and the conflict request in plain words, with the path in quotes | An `@` mention | Claude Code documents no line range for `@`, and `@` would attach the current file where the user pointed at the committed side. Plain words are read by Claude Code with its own tools. |
| A folder listing by a confined `opendir` and one `git check-ignore` for the dimming | A tree read from `git ls-files` or the commit, a whole repository list on every open | A listing then costs one folder whatever the repository's size and shows what is on disk, staged, untracked and ignored entries alike. `ls-files` over a folder walks its whole subtree, and `ls-tree` reads the commit, not the disk. |
| Ignored files listed dimmed and readable, hidden only from open by name | Hiding and refusing them | The tab shows what is on disk like an explorer, and the user's own agent reads those files already. A name search flooded by dependency folders would be useless. |
| Images as `data:` addresses of PNG, JPEG, GIF and WebP checked from their headers, SVG as text | Loading a file address, drawing SVG | The policy already allows `data:` images and no file address, and an SVG drawn as an image is the one format that can reference more. A closed list of four media types leaves the page nothing to choose. |
| `guideSeen` in `interface.json` | A file of its own | The file exists, is validated and written atomically, and a file of its own would need a new channel, which is a security decision for one boolean. |
| A file from an earlier version reads as guide seen | Treating every saved layout as a new user | Whoever has a saved layout has used Satellite, so an update never shows a first run. Only a missing file is a fresh home. |
| Measuring the control each frame | CSS anchor positioning | The card must stay inside the window and the tail must follow the clamp, and a journey reads the numbers anyway. |
| Open tabs in `interface.json` | A file of their own | The file exists, is validated and written atomically, and one place for what the user left open is simpler. |
| The renderer minified, main and preload readable | Everything minified, nothing minified | The renderer carries Monaco and is large, while main and preload are small and their stack traces land in logs. |
| `gh` for every pull request read | REST calls, a token read from `gh` | `gh` already holds the sign in, the host and the account, so Satellite holds no credential and a host the user never signed in to is refused before a request. Four constant runs are easy to prove and to pin. |
| The page drives refresh and the background process paces it | Polling in the background process, a pace on the page alone | Focus, visibility and turn ends are page facts, and the limits must hold against a page that misbehaves, so one queue, a gap, a reuse and a pause live where every run starts. |
| Thread marks in the glyph margin with the text in a panel | Review comments in view zones inside the diff | A mark cannot break the editor, and view zones holding hostile Markdown can. The cost is one click from a mark to its text. |
| Marks only while the workspace is the pull request's head | Marks on whatever lines the workspace has | A line number of another version lands on the wrong line, so the threads stay listed and a sentence says why. |
| Nothing about a pull request stored | A cache in the Satellite home | An answer is minutes old at best, so a file would only add a place for a pull request's words to live. The cost is one read after a restart. |
| Markdown parsed in a worker with a deadline, drawn as React elements | A sanitizer over HTML, a parse on the page with size budgets | There is no HTML to sanitize, and a deadline is a hard bound where every delimiter budget failed against a new shape. The cost is a worker and plain text for a body that misses it. |
| Prepared requests carry pointers | Pasting comment or log text | The agent has `gh` and fetches the full text itself, and untrusted text never rides into the prompt unseen. |
| The parent chain from the session's process | An environment marker, or a process group | An environment is unreadable without privileges and a group is shared by everything an agent's shell started in one call, so signalling one would reach what is not ours.
