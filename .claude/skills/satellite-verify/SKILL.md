# Satellite verify

One command launches the real app in a scenario, runs steps against the window and prints one JSON object. It is how every change is proven.

```sh
npm run --silent verify -- <scenario> [--dev | --app <executable>] [--real-claude] [--keep] [step ...]
```

`--silent` keeps npm's banner out, so stdout is only the JSON. Build logs go to stderr. With no steps it runs `wait-for=app-window tree shot=window`.

## Targets

| Flag | Target | What runs |
| --- | --- | --- |
| none | built | `electron-vite build`, then Electron with the repo root as the app |
| `--dev` | dev | `electron-vite dev` with hot reload, the interface served from `http://localhost` |
| `--app <executable>` | packaged | a packaged app from `release/`, nothing is built. Name the executable itself, `mac-arm64/Satellite.app/Contents/MacOS/Satellite` on macOS, `win-unpacked/Satellite.exe` on Windows, `linux-unpacked/satellite` on Linux |

Every target runs with the scenario's throwaway repo as its working folder. Claude Code starts in the selected workspace's folder, so a scenario selects a workspace, by clicking its row, before `start-claude`.

Built and dev runs in one checkout must not overlap, because each rewrites `out/`. A second run fails fast while `verify-output/run.lock` names a live run, so parallel work takes its own worktree.

## Steps

Steps run in order. The first failure stops the run, and its entry carries `error` plus `tree`, the window at that moment.

| Step | Does | Value |
| --- | --- | --- |
| `tree` | reads the window | `aria`, the accessibility snapshot of the body, and `testIds`, each `{ testId, visible, text }` with text cut at 2000 characters, a terminal's text being the visible one's screen rows |
| `text=<testid>` | reads one element's text, and for `terminal` the rows on the shown terminal's screen, read from the instance the page hangs on its host only under the driver, and its notice | the text, cut at 2000 characters |
| `box=<testid>` | reads where an element is | `{ x, y, width, height }` of its bounding box in whole pixels, and fails when it is not on screen |
| `focused` | reads where the keys go | the test id nearest the focused element, an empty string when that element has none, and `null` when nothing has focus |
| `click=<testid>` | clicks an element | |
| `type=<text>` | types into the focused element, failing when nothing has focus | the focused test id |
| `press=<key>` | presses a key, such as `Enter`, `Shift+Enter` or `Control+C` | |
| `hover=<testid>` | moves the pointer over an element, which opens its tooltip after its delay | |
| `select=<testid>:<label>` | opens the kit's select, picks the option with exactly that label and waits for its menu to close, split at the first `:` | |
| `paste=<text>` | dispatches a paste event with the text on the focused element, failing when nothing has focus | the focused test id |
| `paste-size=<n>` | pastes `n` generated characters, `abc…xyz0…9` repeated, up to 1000000 | the focused test id |
| `resize=<width>x<height>` | sets the viewport size | |
| `theme=light` or `theme=dark` | emulates the system color scheme, which also hides the theme chosen in Satellite. Without it the window shows the theme the scenario seeds, or the real system's when it seeds none | |
| `wait=<ms>` | waits, up to 60000 | |
| `wait-for=<testid>` | waits up to 60 seconds for an element to be visible | |
| `wait-text=<testid>:<text>` | waits up to 60 seconds until the element's inner text, or for `terminal` its screen as `text` reads it, holds the text, split at the first `:`, and fails naming what it last read | |
| `wait-state=<testid>:<state>` | waits up to 60 seconds until the element's `data-state` equals the state, split at the first `:`, and fails naming the state it last read. Session tabs carry the session status (`idle`, `working`, `needs-you`, `done`, `stopped`), and each workspace row's `-status` pixel carries the pixel state, where a stopped session reads `idle` | |
| `send=<text>` | sends the text to Claude Code as the app's own Send to Claude Code does, through the same window event, so the pane cleans it and types it into the shown session without submitting | |
| `diff-lines=<side>:<start>-<end>` | selects those lines on `original` or `modified` in the shown diff by clicking the line number of `start` and then, with Shift held, that of `end` | |
| `file-lines=<start>-<end>` | selects those lines in the file open in the centre by clicking the line number of `start` and then, with Shift held, that of `end` | |
| `shot=<name>` | saves a screenshot, the name in kebab-case | its path |
| `mark=<name>` | writes an empty file `<name>` into the Satellite home, so a `gh` entry with that `after` starts answering. The name is kebab case, up to 41 characters | |
| `log` | reads what the stand-ins recorded | the events |
| `links` | reads the addresses `links.open` would have opened, which the driver records instead of opening a browser | the addresses |
| `notices` | reads what the app would have shown the system, each notification, close and app icon count, and the quit question, which it answers as Quit Satellite. Every launch first records a count of 0, so a run can tell the recorder answers before anything could notify. The recorder appends a moment after the change, so a CLI proof may wait a second first | `{ kind: "notice", title, body }`, `{ kind: "close" }`, `{ kind: "badge", count }` and `{ kind: "question", message }` in order |
| `choose-folder=<target>` | sets what the next folder dialog answers. `repo` is the working repo, `cancel` cancels, anything else is `folders/<target>` in the temp folder, such as `alpha`, `alpha/src` or a folder that does not exist | |
| `drop=<target>` | drops a folder on the middle of the centre through the protocol's drag events, as Finder would. Targets are those of `choose-folder` except `cancel` | |
| `restart` | closes the app and launches it again on the same home, repo and log, so saved state can be read back | |

A command shortcut is `press=Meta+K` on macOS and `press=Control+Shift+K` on Windows and Linux, apart from Settings on `press=Control+Comma` there, so a journey picks the modifier from the platform, as `projects` does. The driver emulates `prefers-reduced-motion: reduce` from launch, so transitions are off and a screenshot never catches one halfway. Wait for a settled state with `wait-for` rather than a fixed `wait`, as `check-count` appears only once the first run check has answered.

`consoleErrors` holds console errors, uncaught errors and unhandled rejections from the first render on, because the driver attaches before the page runs or, when the page already ran, the protocol replays what it buffered.

`wait` gets its own length plus 15 seconds, and `wait-for`, `wait-text`, `wait-state` and `restart` get 75 seconds. Every other step fails after 15 seconds. Paste goes through a synthetic event because the app denies the clipboard permission.

The output is `{ scenario, home, repo, steps: [{ step, ok, value?, error?, output?, tree? }], consoleErrors, screenshots, leftover? }`. When arguments, the build or the launch fail, `steps` holds one entry named `arguments`, `build` or `launch`, and a failed launch adds the app's last output and the window tree when one exists. `home` and `repo` are `null` until the temp folder exists. A failed close adds a `close` entry, and `leftover` names a temp folder that could not be deleted. The exit code is 1 when any step failed or something was left over. It does not count `consoleErrors`, so read them.

## Scenarios

A scenario is `verify/scenarios/<kebab-name>/scenario.json`, checked by `scenarioSchema` in `verify/scenario.ts`, and `verify/scenario.test.ts` loads every one, so a scenario no journey runs still cannot rot.

- `description` says what world it sets up.
- `repo` builds the throwaway repo in order. `{ "write": { "path", "content" | "base64", "executable"? } }` writes a file inside it, text from `content` or bytes from `base64` for a binary file such as an image, with mode `0o755` when `executable` is true, such as a hook in `.git/hooks`, and `{ "git": [args] }` runs the real `git` there, with no system config and a global config naming `Satellite Verify`.
- `home` optionally lists `{ path, content }` files written inside the Satellite home before launch, with the same confinement as the repo's writes, such as a cut off `interface.json`. A scenario seeds `interface.json` with `"theme": "light"` unless its description says otherwise, so its screenshots never depend on the machine's own setting. The first-run guide shows only for a home with no `interface.json` or one at version 4, 5 or 6 with `"guideSeen": false`, so every scenario stays quiet unless it seeds neither. `first-run` seeds none.
- `folders` optionally lists `{ name, steps }`, each built like `repo` in `folders/<name>` beside it, with a kebab-case name. They are built before `repo`, so a repo step can clone one with `../folders/<name>`, and they are the folders a `choose-folder` step can pick.
- `workspaces` optionally lists `{ name, steps }` with a kebab-case name. After `repo` is built, each gets `git branch --no-track <name> HEAD` and `git worktree add <home>/worktrees/repo/<name> <name>` in the repo, then its steps inside the new folder. The driver then writes `projects.json` as version 2 with the repo as the one project and a record per workspace, so a scenario that also seeds `projects.json` under `home` is refused.
- `userHome` optionally lists `{ path, content }` files written inside the run's temporary user home, with the same confinement, such as the user's own `.claude/settings.json` and `.claude.json`.
- `gh` lists canned answers. An entry is `{ args, stdout?, stderr?, exitCode? }`, which the stand-in matches first against its own arguments exactly, or `{ call, number?, json?, stdout?, stderr?, exitCode?, after? }` where `call` is `pull-request`, `threads` or `failed-log`, the pull request runs the app builds, and `number` names the one pull request a `pr view <number>` run asks for while an entry without it answers the plain `pr view`, so a scenario can hold two pull requests on one branch. A call is told apart by the app's own argument builders, so a scenario cannot drift from them. Among the entries of that call the stand-in takes the last whose `after` mark file exists in the Satellite home, else the first with no `after`, and prints `json` as one JSON line when it is set, with every `@head` in it replaced by the commit the stand-in's folder is at, so a pull request can sit exactly on a workspace's head. `after` is a kebab case name that the `mark` step writes. With no entry `pull-request` answers `no pull requests found for branch "stand-in"` with exit 1 and the other two exit 1 with no output. Any other `pr`, `api` or `run` arguments print `stand-in gh got arguments Satellite must never send` and exit 97.
- `claude` holds the `version` line and a `script` played when the stand-in starts. `{ "print": text }` prints, `{ "wait": ms }` waits, `{ "flood": chars }` prints that many characters as numbered lines as fast as the terminal takes them, then `flood done <lines> lines`, `{ "spin": ms }` redraws a working line every 100 milliseconds for that long, as Claude Code's spinner does, `{ "child": "ignores-hangup" }` starts a child process that ignores `SIGHUP`, `{ "child": "dev-server" }` starts a command shell as its child, which runs `verify/stand-ins/dev-server.ts`, a server on a loopback port the system chose with one idle child that ends when the server does, and since a run's home is a temporary folder, the tilde for the home folder never shows in a run, which `command-text.test.ts` covers, `{ "hook": <event>, "fields"?: { ... } }` posts that hook event as Claude Code would, `{ "await": text }` waits until the input not yet consumed holds the text and consumes it through the match, `{ "trust": true }` asks whether to trust the folder and waits for Enter, like Claude Code's trust dialog, and `{ "exit": <code> }` exits with that code, as a crash does when the code is not 0. `"resumeFails": true` beside `script` makes every `--resume` print `No conversation found with session ID: <id>` and exit 1, as Claude Code does for a session it cannot find. In a script with a trust step, hooks before it post nothing. `{ "missing": true }` instead points `SATELLITE_CLAUDE` at a path that does not exist, so the app finds no Claude Code.

## Stand-ins

`verify/stand-ins/gh.ts`, `verify/stand-ins/claude.ts` and, for a scenario that sets `gitStandIn`, `verify/stand-ins/git.ts` (real git, except that `merge-tree --write-tree` fails with git's usage exit 129, as a git older than 2.38 does, when `<home>/git-version` exists) run with the Node that runs the driver, passed to the app through `SATELLITE_GH`, `SATELLITE_CLAUDE` and `SATELLITE_GIT`. They find their scenario through `SATELLITE_VERIFY_SCENARIO`.

- **gh** prints its answer and exits with its code. Without an answer to other arguments it prints `stand-in gh has no answer for <args>` and exits 1.
- **claude** prints `version` for `--version`. Otherwise it puts stdin in raw mode, so nothing typed is line edited, echoes every chunk but a lone Escape, which would swallow the next letter printed (ESC then CR echoes as a new line) and exits on Ctrl+C or Ctrl+D, all while it plays the script. With `--resume <id>` it first prints `Resumed session <id>`, or fails as `resumeFails` says. It reads the file after `--settings` once at start, as Claude Code does, and a `hook` step posts `{ session_id, transcript_path, cwd, hook_event_name, ...fields }` to that event's URL with its headers, `session_id` being the value after `--session-id` or `--resume`. Without a settings file, without that event in it, before trust or when the request fails it posts nothing and logs status `0`.

Both append JSON lines to `SATELLITE_VERIFY_LOG`, read back by the `log` step. Events are `start` with `tool`, `pid` and `args`, and for `gh` also its `cwd` and its `call` (null when no pull request call builds those arguments), `input` with `data`, `resize` with the stand-in's `pid`, `cols` and `rows`, once at start and on every change, `child` with the `pid` of a started child, `server` with the `pid`, the `port` and the `child` process id of the dev server, and `hook` with the `event` and the `status` the listener answered. Startup calls such as `gh --version` appear once on the built and packaged targets. The dev target runs React in development mode, whose strict mode runs every effect twice, so count events on a built run.

## Home, output and cleanup

Each run makes `satellite-verify-*` in the system temp folder, its real path, with `home/` as `SATELLITE_HOME`, `repo/`, `user-home/` as `HOME`, and `USERPROFILE` on Windows, on every run but `--real-claude`, `folders/`, `gitconfig`, an empty `git-ignore` the gitconfig names as `core.excludesFile`, `stand-ins.jsonl`, `folder-dialog.txt` and `notices.jsonl`, which `SATELLITE_VERIFY_NOTICES` names, so no run ever raises a real notification or app icon count and the window always counts as not in front. `SATELLITE_VERIFY_FOLDER_DIALOG` points the app at `folder-dialog.txt`, so the folder dialog never opens and its trimmed content is the chosen folder, a missing or empty file meaning canceled. The user's own `~/.satellite` is never touched, and with the user home redirected neither is anything Satellite or the stand-ins would find through `homedir()`, the user's own Claude Code settings included. What the system finds through the account itself rather than those variables, such as Electron's own folders on macOS, still points at the real account. The app gets the driver's environment without `GIT_*`, `CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_CONFIG_DIR`, `NODE_OPTIONS` and `ELECTRON_RUN_AS_NODE`, then gets `GIT_CONFIG_GLOBAL` pointing at the recipe's `gitconfig` and `GIT_CONFIG_NOSYSTEM=1`, so its git never reads the user's own git config, ignore file or hooks. The recipe's `git` runs without the inherited `GIT_*` too. The run closes the window, kills the process tree once it exits or after 10 seconds, and deletes the temp folder unless `--keep` is set. SIGINT, SIGTERM and SIGHUP, plus SIGBREAK on Windows, stop the build or the app and delete the temp folder the same way. Any other exit of the driver, an uncaught error included, kills every app it started, and the app starts quitting within a second of the driver's process going away, so even a `SIGKILL` leaves no app behind.

Never leave an app running. A script over the driver closes its session in a `finally`, and after a batch of runs no process from this repo's `node_modules/electron` may remain.

On macOS a run is quiet by default, which needs the driver's own process alive, so a leftover variable never hides a real app. The app takes no Dock icon, never comes to the front and keeps its window unshown while it still renders, and the driver emulates focus, so every step proves the same things without taking the user's screen. Set `SATELLITE_VERIFY_FOREGROUND=1` to watch a run in a normal window. The platforms workflow sets it, and Windows and Linux always show the window. A quiet window is not clamped by the display, so it keeps the 1440 by 900 the app opens at. Screenshots land in `verify-output/<scenario>-<timestamp>/`, which Git ignores.

## Real Claude Code

`--real-claude` leaves `SATELLITE_CLAUDE` out and keeps the user's home and `CLAUDE_CONFIG_DIR`, so the app runs the user's own Claude Code with its own sign-in, which updates its own state in the user's home. Ask the user every time before using it, and only in a throwaway scenario repo. Its trust question for the new folder starts on No, exit, so press the down arrow, once Claude Code shows the question and takes keys, and read that Yes is selected before Enter. Claude Code holds back every hook until trust is answered and runs no HTTP hook at session start, so the pixel and Send to Claude Code wake at the first prompt.

## In code

`verify/driver.ts` exports `launchApp({ scenario, target, realClaude?, keep? })`, which returns an `AppSession` with the Playwright `page`, `home`, `repo`, `userHome`, the run's temporary user home, `consoleErrors`, `standInEvents()`, `screenshot(name)`, `folder(name)`, the path of `folders/<name>`, `gitEnv`, the clean git environment the recipe runs with, `answerFolderDialog(path | undefined)`, `dropFolder(path)`, which drops a path like the `drop` step, `selectDiffLines(side, start, end)`, which selects those lines in the shown diff like the `diff-lines` step, `selectFileLines(start, end)`, which does the same in the file open in the centre like the `file-lines` step, `mark(name)`, which does what the `mark` step does, `openedLinks()`, the addresses `links.open` would have opened, read from the file the driver names in `SATELLITE_VERIFY_LINKS`, so no run ever opens a browser, `notices()`, what the `notices` step answers, `relaunch(whileClosed?)`, `quit()`, which sends the app `SIGTERM`, which Electron turns into a real quit through the quit question, and waits for it to exit, off Windows only, since the driver's own close closes the page and skips that question, and `close()`, which answers `{ exitedOnItsOwn, leftover? }`, where `exitedOnItsOwn` says the app quit within 10 seconds of its window closing, before any kill. `relaunch(whileClosed?)` closes the app, runs `whileClosed` while no app runs, so a journey can change the disk without a list seeing it halfway, and launches it again in the same temp folder, after which `page` answers the new page, so a wrapper forwards `page` with a getter rather than copying it. A second `close()` answers the first one's result. A failed launch throws `LaunchFailure` carrying `output`, `consoleErrors`, `tree`, `home` and `repo`. It also exports `buildApp()`, `readTree(page)`, `withTimeout`, `errorReason`, `outputDir`, `isProcessAlive(pid)`, which counts a process it may not signal as alive, `pasteIntoFocus(page, text)` and `generatedText(size)`, the text `paste-size` sends. Journeys use it directly. The WebGL renderer draws the terminal on a canvas with no text in the page, so `verify/terminal-screen.ts` reads the shown terminal through the xterm.js instance its host carries as `terminal`. `readTerminal(page)` answers the rows on screen, the column each character of a row sits in, the cell size and the screen's position, so a journey can point at a character, and `terminalText(page)` answers those rows plus the notice. Playwright's `setViewportSize` also drops the emulated device scale to 1 while the WebGL canvas keeps counting the screen's real pixels, so the terminal draws at half size in a shot taken after it. To judge how the terminal looks at another size, resize through the DevTools `Emulation.setDeviceMetricsOverride` with `deviceScaleFactor: 0` instead.

## Journeys

Journeys are fixed scripts over the driver, one per row of the table below. They run against the built app here and against each packaged app in the platforms workflow. A pull request runs the smoke journeys there, `launch`, `boundary` and `quit`, and a push to `main` and a release run them all. `npm run journeys` runs them all and `npm run journeys -- files sessions` only the ones named, which is how to prove the area a change touches.

```sh
npm run --silent journeys -- [--app <executable>] [journey ...]
```

To prove a packaged app on macOS, run `npm run build`, then `npx electron-builder --mac --arm64 --dir --publish never`, then the journeys with `--app release/mac-arm64/Satellite.app/Contents/MacOS/Satellite`. Windows and Linux are proven by the pull request itself, whose CI runs the same steps there with `release/win-unpacked/Satellite.exe` and `release/linux-unpacked/satellite`.

It builds once for the built target, runs the chosen journeys in order, each in a fresh launch of its scenario, and prints `pass <name>` or `fail <name> <reason>`, the whole reason with Playwright's call log, so a timed out click names the readiness check it waited on, each followed by its screenshot paths. A failing journey saves `<name>-failure` when the window is still open. The exit code is 1 when any journey failed or left its temp folder behind.

A journey is `{ name, scenario, run(session), then?, skip? }`, where `skip` names why a part cannot run on this system, which the runner prints as `skipped <scenario>, <reason>` under the journey's line instead of launching it, and `then` lists further parts that each launch their own scenario under the same name, as `pull-request` does in `verify/journeys/<name>.ts`, listed in `verify/journeys.ts`. A journey picks an option with `chooseOption` and reads a select's shown label with `shownOption`, both from `verify/driver.ts`. It asserts with `node:assert/strict` and a message that says what went wrong, and waits on conditions with `waitUntil` from `verify/journeys/conditions.ts`, not on fixed sleeps, because CI runners and Windows are slower. A fixed wait is right only to check that something stays refused or unchanged, or to pass a timer the app runs, such as the 10 second age a process needs before it is listed, the 5 second gap between notifications or a read's backoff. The boundary journey routes `https://example.com` to a local empty reply, so a guard that lets a request through is caught at once with no network, and a refusal is read from a `securitypolicyviolation` event or a permission state rather than from a failed load. Process checks use `processGone`, which works on all three platforms.

A journey step proves a flow that needs the real app, real processes and files working together. How the window looks or moves, focus, tooltips, colours, sizes and layout, and how fast it runs are proven by the agent looking at the real window while it makes the change, never by a journey step. A step that fails with no fault in the app is cut or rewritten the same day. Keep the suite short, since it runs on three systems for every push to `main` and every release.

Before trusting a new check, turn its guard off for one run and see the journey fail with a legible reason. Note that two guards back each other up in places. Navigation is refused by `will-navigate` and `will-frame-navigate` alike, and the URL parser already folds `%2e%2e` segments, so only an encoded slash such as `..%2f` reaches the protocol's path confinement. `..%5c` means something only on Windows, and Chromium refuses a `file:` navigation from `app://` by itself, so neither proves a guard on its own. `sandbox` and `nodeIntegration` cannot be seen from the page, and the protocol's host and method checks and the sender check cannot be reached from it, so unit tests beside them pin those. The paste is a synthetic event, so it proves the terminal and the bridge carry it, not the platform's paste shortcut.
